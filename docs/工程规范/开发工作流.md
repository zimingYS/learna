# 开发工作流

## 1. 编码前检查

开始修改代码前必须：

1. 阅读 `AGENTS.md`、任务相关设计文档和本目录相关规范。
2. 检查当前模块目录结构。
3. 阅读同模块至少两个具有代表性的现有源文件；若模块不足两个，则检查全部相关文件。
4. 识别现有命名、注释、格式、错误处理、类型定义和模块组织风格。
5. 搜索项目中已有的相似实现、接口、数据模型和测试。
6. 明确本次任务修改范围。

不得在没有检查现有实现的情况下直接创建新文件或重新实现已有功能。

## 2. 实施方案

涉及多个文件、数据库、API 或模块边界的任务，开始编码前必须提供实施方案，至少包括：

- 修改目标
- 预计修改的文件
- 预计新增的文件
- 现有模块复用情况
- 数据库影响
- API 影响
- 模块依赖变化
- 测试方案
- 潜在风险

等待项目负责人批准后再实施。范围明确、风险较低的局部修改可以直接执行，但不得扩大任务范围。

## 3. 编码中

必须：

- 保持修改范围明确。
- 优先复用已有实现。
- 遵循现有代码风格，尤其是注释语言、格式和密度。
- 保持模块职责单一。
- 避免重复代码和无关文件修改。
- 为重要业务规则补充测试。
- 同步维护必要文档。
- 不得为了完成当前任务擅自重构整个模块。

## 4. 编码后

完成后必须：

1. 检查完整 Git Diff。
2. 检查是否存在重复实现。
3. 检查是否存在无用代码。
4. 检查文件长度和函数复杂度。
5. 检查注释是否准确，是否延续现有风格，是否过度注释。
6. 运行格式检查。
7. 运行静态检查。
8. 运行相关测试。
9. 检查是否引入架构或接口不一致。
10. 按 `交付报告模板.md` 提供完整交付报告。

## 5. Agent 任务执行协议

### Step 1 — Understand

阅读任务、设计文档和现有代码，确认业务目标与技术边界。

### Step 2 — Inspect

检查现有实现，搜索可复用模块，确认是否存在重复功能。

### Step 3 — Plan

中大型任务提供实施方案，明确文件修改范围和潜在影响。

### Step 4 — Implement

只实现当前任务要求的内容，遵循现有代码风格，保持职责清晰和模块化。

### Step 5 — Refactor

只进行与当前任务直接相关的必要重构。检查重复代码、过长函数、过长文件、无意义抽象、不必要依赖、无用代码和不准确注释。

### Step 6 — Verify

执行格式检查、静态检查和测试，检查 Git Diff，确认没有意外修改。

### Step 7 — Report

提供完整交付报告，完成后停止，等待下一项任务。
