# 代码风格与质量规范

## 1. 遵循现有风格

仓库已有代码是新增代码风格的首要参考。

必须遵循同模块现有代码的：

- 缩进、换行、空行习惯
- import 顺序
- 命名方式
- 注释语言、注释格式、注释密度
- 函数组织顺序
- 类型声明方式
- 错误处理方式
- 测试组织方式

如果现有模块已有明确且一致的风格，不得自行改变。

如果现有代码存在明显不一致：

1. 不要在当前任务中顺手格式化整个模块。
2. 优先遵循当前文件或相邻文件的主流风格。
3. 将风格问题记录为独立技术债务。
4. 如确实需要统一，单独提出重构方案。

## 2. 格式化与静态检查

必须使用项目已经配置的格式化和静态检查工具。不得通过修改规则迁就不规范代码，不得为了通过检查大规模修改与任务无关的文件。

建议工具以仓库现有配置为准：

- Rust：rustfmt、Clippy
- TypeScript / Vue：Prettier、ESLint、vue-tsc
- Python：Ruff、pytest

未经批准不得随意替换现有工具链。

## 3. 命名规范

命名必须准确表达业务含义，优先使用完整、清晰、可理解的名称。

避免无意义缩写、过短变量名、模糊通用名称、同一业务概念在不同模块使用不同名称、使用技术实现名称代替领域概念。

推荐：

- `learning_session`
- `mastery_level`
- `review_schedule`
- `project_id`
- `user_id`

不推荐：

- `ls`
- `ml`
- `data1`
- `temp2`
- 职责不明确时的 `process_data`

允许在循环索引等局部场景使用简短变量。必须保持领域术语一致性。

## 4. 注释规范（重点）

必须维持现有项目代码的注释风格，不得借当前任务批量重写、统一或重排注释。

### 4.1 基本要求

- 新增或修改注释时，注释语言、格式、位置和密度必须与同文件或相邻文件的主流风格一致。
- 现有模块注释少，不要新增大量解释性注释；现有模块注释详细，按同风格补充必要说明。
- 不得批量把英文注释改为中文、把中文注释改为英文，或重排无关注释。
- 不得为每一行代码、简单赋值、简单 getter 添加无意义注释。
- 不得保留与实际代码不一致的旧注释。
- 不得使用注释掩盖糟糕的代码结构。

### 4.2 注释应解释什么

注释主要解释：

- 为什么这样设计
- 为什么采用这种处理方式
- 哪些业务规则不能改变
- 哪些边界条件需要特别注意
- 哪些实现存在特殊约束
- 哪些代码看起来不直观但具有必要性

不推荐：

```rust
// 将用户 ID 赋值给 user_id
let user_id = claims.sub;
```

推荐：

```rust
// 从已验证的 JWT Claims 中获取用户身份，后续资源访问必须基于该身份进行授权。
let user_id = claims.sub;
```

### 4.3 业务规则注释

涉及重要业务规则时必须添加必要注释，例如：

- 只有主要项目计入学习时长。
- 关联项目不能重复累计学习时间。
- 个人总体掌握度不能覆盖项目上下文掌握度。
- AI Proposal 必须经过业务校验后才能应用。
- 历史学习记录不能被静默覆盖。

注释应解释规则，而不是机械复制设计文档。

### 4.4 文档语言

项目文档和业务说明默认使用中文。代码标识符使用英文。代码注释优先延续所在模块的现有语言和表达风格，不得在同一个文件中无必要地混用中英文注释。

公共 API、公共类型和复杂业务接口应提供必要文档说明。

## 5. 代码格式

- 保持合理空行和缩进。
- 避免超长表达式、过长参数列表。
- 对复杂条件使用明确中间变量或辅助函数。
- 对复杂数据转换适当拆分步骤。
- 不要将大量逻辑压缩为一行，也不要通过过度拆行破坏可读性。
- 格式化应服务于可读性，而不是追求最少行数。

## 6. 复用与效率

新增以下内容前必须先检查是否已有相同或相近实现：

- 函数、业务服务、数据访问方法、API 接口
- DTO、TypeScript 类型、Vue 组件、Composable、Store
- Python Service、通用工具

同一业务规则不得在多个位置分别维护。用户权限判断、统一响应格式、错误码、时间日期处理、API 请求、AI Proposal 校验应使用统一机制。

满足以下任一条件时可以考虑提取公共模块：

1. 多处代码确实存在相同逻辑。
2. 逻辑具有明确且稳定的业务含义。
3. 多个模块需要统一使用同一规则。
4. 抽取后可以明显降低耦合或提高可测试性。

不要仅因为代码相似就强制抽象。如果两个逻辑未来可能独立演进，允许暂时保留独立实现。

## 7. 死代码与运行效率

禁止提交未使用函数、变量、类型、模块、依赖、永远不执行的分支、仅为预留未来需求创建的空模块、已被替代但未清理的旧实现。

注意避免不必要数据库查询、N+1 查询、重复序列化、不必要数据复制、无意义全量加载、循环中重复昂贵操作、不必要网络请求和无意义前端响应式状态。优化必须有明确依据，不得为追求性能牺牲可读性或提前引入复杂优化。

## 8. 文件长度与函数复杂度

文件长度默认控制标准：

| 文件规模 | 处理要求 |
|---|---|
| 1-200 行 | 正常，无特殊要求 |
| 201-300 行 | 检查职责是否集中 |
| 301-400 行 | 优先评估是否需要拆分 |
| 401-500 行 | 原则上应拆分，特殊情况需说明 |
| 超过 500 行 | 必须进行拆分评估，未经说明不得直接交付 |

上述标准适用于主要业务源代码，不适用于自动生成代码、Migration、锁文件、数据文件和特殊配置文件。

函数参考标准：

- 30 行以内：优先。
- 30-50 行：检查是否可以合理拆分。
- 50-80 行：原则上需要进行拆分评估。
- 超过 80 行：必须说明原因，并优先重构。

不得为了满足行数限制机械拆分代码。拆分应按照职责进行，而不是单纯按照行数拆分。

## 9. 语言规则

### 9.1 Rust

- 优先使用 rustfmt，保持 Clippy 通过。
- 可恢复错误优先使用 Result。
- 不得无理由使用 `unwrap()` 或 `expect()` 处理业务错误。
- 避免不必要 `clone()`、`Arc`、`Mutex`、锁、泛型、宏、类型转换和不安全代码。
- 明确区分领域模型、数据库模型和 API DTO。
- 公共 API 提供必要文档注释。
- 错误必须在适当层次处理，不得随意吞掉。
- 异步函数不得执行不必要阻塞操作。
- 数据库访问必须遵循现有 Repository 设计。
- 不得将复杂业务逻辑放入 Axum Handler。

### 9.2 TypeScript / Vue

- 优先使用 TypeScript 类型约束，避免随意 `any`。
- 不得通过类型断言掩盖真实类型问题。
- 复杂类型应提取到合理位置。
- 统一使用项目现有 Composition API 风格。
- 保持组件职责单一，避免大型 `script setup`、大型模板和模板中复杂表达式。
- 业务逻辑优先提取到 Composable 或 Store。
- API 请求必须经过统一请求封装。
- 避免组件之间不必要紧耦合。
- 避免不必要 `watch` 和响应式状态，派生状态优先使用 `computed`。
- Props 和 Emits 必须具有明确类型。
- 不得为了组件复用过度抽象。

### 9.3 Python

- 使用明确类型注解。
- 输入输出模型优先使用 Pydantic。
- 避免过长函数，避免多个 Workflow 堆积在一个文件。
- Provider 适配必须保持统一接口。
- 错误处理必须明确，不得通过宽泛 `except Exception` 隐藏异常。
- 避免不必要全局状态和模块导入副作用。
- 保持异步调用方式一致。
- Prompt 与业务代码合理分离。
