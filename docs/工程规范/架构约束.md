# 架构约束

## 1. Monorepo 边界

Learna 使用 Monorepo。Frontend、Backend、AI Service 和 Deployment 分别承担明确职责。不得因为局部开发便利破坏现有项目边界。

## 2. 后端模块化

Rust Backend 应优先按业务领域组织模块。建议领域包括：

- user
- auth
- project
- goal
- roadmap
- task
- learning_content
- learning_session
- mastery
- review
- question
- schedule
- ai
- analytics

实际目录以现有仓库为准，不得为了符合示例机械创建所有模块。

模块内部可根据复杂程度拆分：

- model
- dto
- repository
- service
- handler
- tests

不是每个模块都必须包含全部层次。简单模块应保持简单，复杂模块才需要进一步拆分。

## 3. 后端依赖规则

- Handler 负责 HTTP 请求与响应适配。
- Service 负责业务流程与规则。
- Repository 负责数据访问。
- DTO 负责外部数据结构。
- Model 负责领域或持久化模型，具体边界遵循现有设计。

禁止 Handler 直接承担复杂业务逻辑。禁止跨领域模块随意访问其他模块 Repository。模块之间优先通过公开 Service 或明确接口协作。禁止循环依赖。

## 4. 前端模块化

Vue Frontend 优先按照 Feature 组织代码。建议 Feature 包括：

- auth
- dashboard
- projects
- goals
- roadmaps
- learning-content
- learning-sessions
- mastery
- reviews
- questions
- schedule
- ai-assistant

Feature 可包含 api、components、composables、stores、types、views。不要求每个 Feature 都创建全部目录。

前端规则：

- 页面负责页面级组合与交互。
- 通用组件放入公共组件目录。
- 业务组件放入对应 Feature。
- 可复用响应式逻辑放入 Composables。
- 状态共享放入 Pinia Store。
- API 请求通过统一 API Client。
- 类型定义集中维护，避免重复声明。
- 页面组件不得承担大量 API、数据转换和复杂业务逻辑。
- 禁止为了拆分而把简单页面拆成大量微小组件。

## 5. AI Service 模块化

Python AI Service 应保持清晰分层。建议职责：

- api：内部 HTTP API
- core：核心配置和基础设施
- providers：模型供应商适配
- context：AI 上下文构建
- workflows：AI 工作流
- schemas：输入输出结构
- prompts：Prompt 管理
- services：应用级服务
- evaluation：AI 输出质量评估

AI Workflow 不得直接承担所有数据库或业务写入职责。Python AI Service 不直接连接业务数据库。
