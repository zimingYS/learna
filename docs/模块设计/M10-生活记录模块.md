# M10 生活记录模块

**契约状态：** §4.7 `/life-records` ⬜ 规划中；健康数据 AI 授权 ❓ 未设计
**实现状态：** ⬜ 目录不存在（需新建 `modules/life_log`）
**依据：** PRD §12（生活记录与健康数据）、§18 第 14 项（授权粒度未定）；TAD §3.11（四类记录）；ERD **无本域表定义**

## 1. 职责与边界

**做什么**：

| 能力 | 状态 |
|---|---|
| 手动记录睡眠（入睡 / 起床 / 时长） | ❓ 未设计 |
| 手动记录运动（类型 / 时长 / 距离） | ❓ |
| 手动记录饮食（餐次 / 内容 / 备注） | ❓ |
| 手动记录身体数据（体重等） | ❓ |
| 基础数据导入（手动记录之外的批量导入） | ❓ |
| 健康数据对 AI 的授权管理（默认关闭、按类别、总开关、可撤销） | ❓ |
| 生活数据的基础统计（供 M11） | ❓ |

**不做什么**（这些属其他模块，勿塞进本域）：

| 不做 | 归属 | 理由 |
|---|---|---|
| 学习时间与学习活动 | M05 | 生活记录是「学习之外」的数据，不参与学习时长统计 |
| 生活数据的可视化 | M11 | 本域只提供数据，图表归 M11（PRD §13.1「生活数据分析」一行） |
| 健康数据与学习的关联分析 | M12 | PRD §13.2 列为「最终目标」，且需用户授权 |
| 第三方设备同步（体重秤 / 手环 / HealthKit） | 后续版本 | PRD §3.2 明确「后续版本」，首版只做手动记录与基础导入 |
| 通用生活事务管理 | 暂不纳入 | PRD §3.2「未来可扩展，但不改变学习核心定位」 |

**本模块的架构级约束（PRD §12.1，最重要的一条）**：

> 生活记录是**可选模块**，不是 Learna 的核心使用前提。用户不开启生活记录，也应完整使用学习管理功能。

这条约束的工程含义有三层，实现时必须守住：

| 层 | 约束 |
|---|---|
| 表 | 其他模块**不得**有指向生活记录表的外键，也不得 `JOIN` 它 |
| 代码 | M01~M09、M11 的核心路径不得 `use` 本模块；M11 的生活统计必须是**可选分节**，数据为空时返回空数组而非报错 |
| 前端 | 路由与导航项按开关条件渲染；关闭时 `/life` 路由应 404 或重定向，而不是空白页 |

违反任何一层，都会让「可选模块」变成「关不掉的核心依赖」。

## 2. 目录与文件形态

```text
modules/life_log/             ⬜ 待建
├── mod.rs
├── dto.rs                    # 四类记录的 DTO + 统一的 LifeRecordQuery
├── handler.rs                # 分类 CRUD、批量导入、授权管理
├── service.rs                # 记录 CRUD + 导入
├── consent.rs                # 健康数据 AI 授权（独立于记录本身）
└── rules.rs                  # 纯函数：时间区间合法性、单位换算、类别枚举

modules/life_log/import/      ⬜ 待建（若做批量导入）
├── mod.rs
├── csv.rs                    # CSV 导入
└── json.rs                   # JSON 导入
```

**为什么 `consent.rs` 要独立于 `service.rs`**：授权是**账号级设置**，生命周期与记录完全不同——记录可以删光，授权状态仍需保留（否则用户删完数据后授权被"重置"为默认，属于隐性授权）。混在一起容易写成「查记录时顺带判授权」，把授权降级成查询条件。

## 3. 契约映射

`接口清单.md` §4.7 当前形态（**仅一行占位**）：

| 方法 | 路径 | 状态 | 说明 |
|---|---|---|---|
| GET / POST | `/api/v1/life-records` | ⬜ | 列表（按类别 / 日期区间）/ 创建 |
| GET / PATCH / DELETE | `/api/v1/life-records/{id}` | ⬜ | 详情 / 更新 / 删除 |
| POST | `/api/v1/life-records/import` | ⬜ | 批量导入（格式未定） |
| GET / PUT | `/api/v1/life-consents` | ❓ | 健康数据 AI 授权（按类别） |
| GET | `/api/v1/life-records/summary` | ❓ | 基础统计（或并入 M11） |

**九项待决策**（建议编号接续 D-70 起）：

| # | 待决策 | 影响 |
|---|---|---|
| 1 | **单表 + 类型 + JSONB，还是四张类型表** | 见 §5，这是本域最核心的建模选择 |
| 2 | **是否需要一个「模块开关」** | PRD 说「用户不开启生活记录」——开关存哪？`users` 加列？还是靠「有没有数据」隐式判断？ |
| 3 | **`record_date` 与时间戳的关系** | 睡眠跨午夜（23:00 睡、07:00 起）算哪一天？PRD §16.2 要求「创建时间与实际发生时间分开」 |
| 4 | **单位与精度** | 体重 kg/lb？距离 km/mile？时长分钟？是否需要单位偏好在账号级配置 |
| 5 | **导入格式** | CSV / JSON / 两者？字段映射如何配置 |
| 6 | **授权粒度** | PRD §12.4「按数据类别授权」——类别是四类记录，还是更细（睡眠的入睡时间是否单独授权）？ |
| 7 | **撤销授权后已用数据怎么办** | PRD §18 第 14 项明确未定：「撤销后的数据处理」 |
| 8 | **数据保留期限** | 生活数据是否永久保留？账号注销时怎么删 |
| 9 | **统计口径** | 「基础统计」（PRD §13.1）具体指标：周均睡眠时长？运动频次？体重趋势？ |

## 4. 调用链与分层

**创建一条睡眠记录**：

```text
POST /api/v1/life-records
  { record_type: "sleep", record_date: "2026-11-27", sleep: { bed_at, wake_at }, note: "…" }
  → service::create(&db, user_id, req)
      1. rules::validate_sleep(bed_at, wake_at)?     -- wake > bed，跨午夜按 +1 天处理
      2. rules::resolve_record_date(record_date, bed_at)?  -- 见 §5 决策 3
      3. INSERT INTO life_records (owner_id, record_type, record_date, payload, note)
         VALUES (…) RETURNING …
    → ApiReply(Ok(LifeRecordItem), req_id)
```

**查授权状态（供 M12 调用，不经 HTTP）**：

```text
M12 生成分析请求前：
  consent::can_use(&db, user_id, DataCategory::Sleep) -> bool
    1. 查总开关（allow_all）
    2. 查类别级授权（category = sleep）
    3. 两者都需 granted = true，且 revoked_at IS NULL
    4. 默认（无记录）= 拒绝
```

**关键设计：默认拒绝**。PRD §12.4「默认不向 AI 暴露健康数据」意味着授权表里**没有行 = 未授权**，不能反过来（有行才拒绝）。这一点与大多数权限系统的「默认允许」直觉相反，必须显式写在代码注释与测试里。

## 5. 数据与不变量

**V1.2 已按路线 A 建模（ERD §5.9）**，共 5 张表：

| 表 | 关键字段 |
|---|---|
| `sleep_records` | `record_date`、`sleep_start_at`、`wake_at`、`duration_minutes`；`record_date` 口径固定为**起床日** |
| `exercise_records` | `record_date`、`exercise_type`（自由文本）、`duration_minutes`、`distance_meters` |
| `meal_records` | `record_date`、`meal_type` 四值、`content`、`note` |
| `body_measurements` | `measured_at`、`weight_kg`（只落体重） |
| `ai_data_permissions` | `data_category` 五值、`granted`、`purpose`、`granted_at`、`revoked_at` |

三条硬约束（对应 ERD §5.9 的前置约束）：

1. **可选模块不得被反向依赖**：本域表不得被核心学习流程外键引用；本域可以有指向 `users` 的外键。
2. **路线 A 的四张类型表**：四类记录是「四种不同的东西」，JSONB 统一会让「体重必须 > 0」退化为应用层校验，统计也要写 `payload->>'weight'`。
3. **默认拒绝**：`ai_data_permissions` 无有效行即不允许 AI 读取；`revoked_at` 非空的行保留，撤销不删行。

`body_measurements` 只落体重：PRD §12.2 只写「体重等」，没有列举体脂率、围度，按 ADR-007 的最小承诺原则不为「等」预留 JSONB 槽（ERD §12 第 15 项）。

**必须保证的不变量**：

| 不变量 | 依据 |
|---|---|
| **默认拒绝**：无授权行 = 不允许 AI 使用 | PRD §12.4 |
| 总开关不能绕过必要的权限校验、数据最小化和安全措施 | PRD §12.4 明文 |
| 授权状态与用途可查看 | PRD §12.4 |
| 撤销后保留历史（`revoked_at` 非空，不删行） | 否则无法回答「什么时候授权过」 |
| 生活数据不参与学习时长统计 | PRD §12.1（可选模块不污染核心指标） |
| 其他模块不得有指向生活表的外键 | 见 §1 三层约束 |

## 6. 状态与副作用

**记录本身无状态机**。授权有一处「状态」但很简单：

| 当前 | 动作 | 目标 | 副作用 |
|---|---|---|---|
| （无行） | 授权 | granted | `granted_at = now()`、`revoked_at = NULL` |
| granted | 撤销 | 未授权 | `revoked_at = now()`、`granted = false`（**保留行**） |
| 未授权 | 重新授权 | granted | 复用行，`granted_at` 更新，清 `revoked_at` |

**副作用**：

| 动作 | 写入 |
|---|---|
| 创建记录 | 类型表行；`created_at` |
| 修改记录 | 行更新；**是否保留修改历史未定**（健康数据变更有追溯价值，但 ERD 无表） |
| 删除记录 | 物理删（PRD §15 允许用户删数据）；授权行不受影响 |
| 授权 / 撤销 | 授权表行；**不删任何生活数据**（撤销授权≠删除数据） |

## 7. 错误映射

| 场景 | 变体 | HTTP | 备注 |
|---|---|---|---|
| 记录不存在 / 非本人 | `NotFound` | 404 | |
| 睡眠 `wake_at <= bed_at`（且未跨午夜） | `Validation` | 422 | |
| 运动时长为负、距离为负 | `Validation` | 422 | |
| 体重超出合理范围（如 0 或 500kg） | `Validation` | 422 | 阈值需决策 |
| `record_date` 与 `bed_at` 矛盾 | `Validation` | 422 | 见 §5 决策 3 |
| 导入文件格式错误 | `Validation` | 422 | 需返回逐行错误 |
| 授权类别非法 | `Validation` | 422 | |
| 模块未开启却调用本域 | 404 / 403 | — | 建议 404（模块不存在），需决策 2 |

## 8. 事务边界

| 操作 | 事务 |
|---|---|
| 单条记录 CRUD | 单语句 |
| 批量导入 | **必须单事务**（全成功或全失败）；若数据量大则分批 + 幂等键，避免长事务 |
| 授权 / 撤销 | 单语句 |
| 删除账号时清理 | 由 M01 的注销事务统一处理（本域表 `FK → users ON DELETE CASCADE`） |

**批量导入的取舍**：单事务保证一致性，但一万行会持锁数秒。建议限制单次导入行数（如 1000 行），超出则要求分文件——比做分批幂等简单得多。

## 9. 测试策略

待建 `backend/tests/life_log_flow.rs`：

| 用例组 | 断言 |
|---|---|
| 四类记录 CRUD | 各自字段回显；跨类别字段混用 → 422 |
| 睡眠跨午夜 | 23:00 入睡、07:00 起床 → 时长 8 小时，`record_date` 按决策 3 落在正确日期 |
| 单位与边界 | 体重 0 / 负数 → 422；距离负数 → 422 |
| 导入 | 合法 CSV 全量导入；含错误行 → 整体回滚且返回行号 |
| **默认拒绝** | 无授权行时，`consent::can_use` 返回 false |
| 授权 / 撤销 | 授权后 true；撤销后 false 但**记录仍在**；重新授权后 true |
| 总开关边界 | `allow_all = true` 但某类别显式拒绝 → 按决策 6 的优先级（建议类别级优先） |
| 可选模块隔离 | 关闭模块后，学习相关端点全部正常（**跨模块回归**） |
| 越权 | 他人记录 detail / patch / delete 均 404 |

**最该测的一条**：关闭生活记录后，M11 的 Dashboard 仍能正常返回学习统计（生活分节为空）。这条测试防的是「可选模块变成隐性依赖」。

## 10. 实现状态与缺口

**已实现**：无。ERD V1.2 已建 5 张表（§5.9），代码无目录。

**阻塞项（按解除顺序）**：

| # | 阻塞 | 说明 |
|---|---|---|
| 1 | ~~ERD 无本域表~~ **已完成** | V1.2 建了四类记录表 + `ai_data_permissions`，共 5 张（§5.9） |
| 2 | ~~建模路线未定~~ **已完成** | V1.2 采纳路线 A（四张类型表），理由见 §5 |
| 3 | ~~授权模型未设计~~ **已完成** | `ai_data_permissions`（§5.9）：类别级 + 总开关，`purpose` 必填，撤销保留行。ERD §12 第 8 项的「健康数据授权边界」仍指**附件跨项目查看权限**，与本表无关 |
| 4 | **撤销后的数据处理未定** | PRD §18 第 14 项明确未定 |
| 5 | **模块开关形态未定** | 见 §3 决策 2 |
| 6 | **跨午夜与记录日期规则未定** | 见 §3 决策 3；这条不定，睡眠统计永远算不准 |
| 7 | 目录 `modules/life_log` 不存在 | 需新建 |

**建议**：本模块排 **P3 且最后做**，甚至可以在 P0~P2 全部完成后重新评估是否值得做。

理由不是「不重要」，而是：

1. PRD §12.1 明确它是可选模块，不阻塞任何核心功能；
2. 它的价值依赖「有学习数据可对比」——生活数据与学习数据的关联分析（PRD §13.2）属最终目标，单看睡眠时长对备考的指导意义有限；
3. 它是唯一一个**需要新授权模型**的模块，这部分设计成本不低于功能本身。

**若要做，最小切片**：只做睡眠 + 身体数据两类（字段最简单：两类都是「两个时间点」或「一个数值」），单表 + JSONB 或两表皆可，不碰导入、不碰授权（M12 也不能读）。先把「记录得下来」解决，授权与关联分析留到 M12 真正落地时。
