**契约状态：** §4.1 中属项目的 13 项 ✅ 已冻结并实现（`openapi.yaml` 1.6.0，`x-learna-status: designed`）
**实现状态：** ✅ 后端 `modules/project` 全部端点可用 + 迁移 `0004`；前端 `/projects` 列表与详情页已接真数据（2026-11-27）
**依据：** PRD §4.2（项目）、§4.3（生命周期）、§4.6（截止日期类型）、§5.1~§5.4（优先级与投入保障）；ERD §5.1 `LearningProject`、§8（删除策略）、§8.1（彻底删除流程）；ADR-005、ADR-006

## 1. 职责与边界

**做什么**：

| 能力 | 契约 | 状态 |
|---|---|---|
| 项目 CRUD（列表 / 创建 / 详情 / 部分更新） | 5 项 | ✅ 已实现 |
| 六态生命周期：activate / pause / resume / complete / reopen / archive | 6 项 | ✅ 已实现 |
| 固定截止日期改期（`extend-deadline`） | 1 项 | ✅ 已实现 |
| 草稿项目物理删除 | 1 项 | ✅ 已实现 |
| 强制删除（`purge`，重输项目名） | 1 项 | ✅ 已实现 |
| 项目重要程度 I1~I5 与手动覆盖期限 | 并入 PATCH | ✅ 已实现 |
| 临时标记（本周重点 / 冲刺 / 最低投入 …） | 无 | ⬜ 建表未开放接口（PRD §5.3，P3） |
| 投入保障规则（每日/周/月目标） | 无 | ⬜ 建表未开放接口（PRD §5.4，P3） |
| 动态调度优先级计算 | 无 | ❓ 未设计（PRD §5.2，归 M04 算法 + M12 AI） |

**不做什么**（这些属其他模块，勿塞进本域）：

| 不做 | 归属 | 理由 |
|---|---|---|
| 目标、路线、阶段、里程碑、任务 | M04 | 它们是容器里的**结构**，生命周期与项目不同粒度。合并会让「项目暂停」与「阶段跳过」两套状态机挤在一个 service |
| 学习时长统计、实际投入 | M05 | 项目只声明「想要多少」，不记录「实际做了多少」 |
| 学习内容与项目关联 | M03（`project_contents`） | 内容关联带项目上下文的掌握状态，独立生命周期 |
| 今日计划与时间段安排 | M04（`scheduled_activities`） | 调度是「依据过去推未来」，与项目本体无关 |
| 掌握度评价 | M06 | 评价作用于 `project_contents`，不作用于项目行 |

**边界的关键判断**：项目是**容器**，它只回答三件事——这个项目处于什么阶段、它有多重要、它的截止与投入约束是什么。凡是「容器里装了什么」的问题，一律不属 M02。

## 3. 契约映射

`openapi.yaml` 中 `/api/v1/projects` 前缀下属 M02 的 **13 个 designed 操作**：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/projects` | 列表；`status` 过滤；`include_archived` 覆盖默认排除；排序 `updated_at DESC` |
| POST | `/api/v1/projects` | 创建，初始 `status=draft`；`importance_level` 默认 3、`project_type` 默认 `study`、`deadline_type` 默认 `none` |
| GET | `/api/v1/projects/{id}` | 详情 |
| PATCH | `/api/v1/projects/{id}` | 部分更新（不含 status）；`deadline_type=fixed` 时改 `deadline_at` → 422 |
| DELETE | `/api/v1/projects/{id}` | **仅 draft**，级联物理删除；非 draft → 409 引导归档 |
| POST | `/api/v1/projects/{id}/activate` | draft → active |
| POST | `/api/v1/projects/{id}/pause` | active → paused |
| POST | `/api/v1/projects/{id}/resume` | paused → active |
| POST | `/api/v1/projects/{id}/complete` | active / paused → completed |
| POST | `/api/v1/projects/{id}/reopen` | completed / archived → active，写 `reopened_at` |
| POST | `/api/v1/projects/{id}/archive` | draft / active / paused / completed → archived，写 `archived_at` |
| POST | `/api/v1/projects/{id}/extend-deadline` | 必带 `new_deadline_at` + `reason` |
| POST | `/api/v1/projects/{id}/purge` | 必带 `confirm_name`（等于项目名） |

**状态变更为什么不用 `PATCH status`**：`reopen` 与 `archive` 有 `reopened_at` / `archived_at` 副作用，而且「完成→暂停」这类非法边需要在动作层面拒绝。把状态塞进 PATCH 会让「一个字段不同值触发不同副作用」的隐式规则扩散到前端。动作端点把意图显式化。

## 4. 调用链与分层

以「项目归档」为例：

```text
POST /api/v1/projects/{id}/archive
  request_id_middleware → auth_middleware → Extension<UserId>
  router/project.rs → handler::archive
    → service::archive(&db, user_id, project_id)
        1. SELECT status FROM learning_projects
            WHERE id = $1 AND owner_id = $2
            FOR UPDATE                       -- 动作端点串行化同项目
        2. 无行 → NotFound（不存在与越权不可区分）
        3. rules::ensure_project_transition(status, Archived)?   -- 非法边 → 409
        4. UPDATE learning_projects
              SET status = 'archived', archived_at = now(), updated_at = now()
            WHERE id = $1 AND owner_id = $2
            RETURNING …
        5. 不触碰任何子数据（归档 ≠ 删除，PRD §4.3 保留历史）
    → ApiReply(Ok(ProjectItem), req_id)
```

**分层约束**：

- `PATCH` 的动态 SET 用 `QueryBuilder`（与 `learning_record` 同构），空对象 → 422 `no fields to update`。
- 状态判定抽到 `rules.rs`（纯函数），可无 DB 单测。
- handler 只做提取器与 `ApiReply` 包装。

## 5. 数据与不变量

**表 `learning_projects`**（ERD §5.1）：

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | UUID | PK |
| `owner_id` | UUID | FK → `users`，NOT NULL |
| `name` | VARCHAR(160) | NOT NULL |
| `description` | TEXT | NULL |
| `project_type` | VARCHAR(30) | `study / skill_development / challenge / deliverable` |
| `status` | VARCHAR(20) | 六值枚举，见 §6 |
| `importance_level` | SMALLINT | `BETWEEN 1 AND 5` |
| `importance_override_until` | TIMESTAMPTZ | 手动重要程度生效期限 |
| `deadline_type` | VARCHAR(20) | `none / soft / fixed` |
| `deadline_at` | TIMESTAMPTZ | 可空，受 `deadline_type` 约束 |
| `archived_at` | TIMESTAMPTZ | 归档时间 |
| `reopened_at` | TIMESTAMPTZ | 最近一次重新开启时间 |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL |

**DB 可独立保证的约束**：`importance_level BETWEEN 1 AND 5`；`deadline_type = none → deadline_at IS NULL`；`deadline_type IN (soft, fixed) → deadline_at IS NOT NULL`。**建议全部下放到 DB CHECK**，不要只靠服务层——这类约束一旦漏校验就是永久脏数据。

**服务层必须保证的规则**：

| 规则 | 为何 DB 无法独立保证 | 依据 |
|---|---|---|
| `fixed` 改期必须走 `extend-deadline` 且带 `reason` | 需区分请求来源，CHECK 看不出意图 | PRD §4.6 |
| `purge` 的 `confirm_name` 与项目名一致 | 跨列比较可在 CHECK 做，但需要先取到旧值；且 `trim` 语义属应用层 | ADR-006 |
| 状态迁移合法性 | 迁移矩阵含「谁调用」的语义，非纯字段约束 | ADR-005 D-01 |
| 常规写入不得把 `status` 置 `deleting` | 需要区分「常规动作」与「purge 内部动作」 | ADR-005 |

**模型缺口（V1.2 已补齐）**：

| 缺口 | ERD V1.2 落地 | 依据 |
|---|---|---|
| `theory_enabled` / `practice_enabled` | `learning_projects` 两列（§5.1），`BOOLEAN NOT NULL DEFAULT true` | PRD §6.1；关闭模块只停新增，不删历史 |
| **`ProjectPriorityOverride`**（临时标记） | `project_priority_overrides`（§5.6）：`marker_type` 五值、`effective_from/until`、`status` 三值 | PRD §5.3；历史标记保留，到期按 `effective_until` 实时判定 |
| **`ProjectCommitmentRule`**（投入保障） | `project_commitment_rules`（§5.6）：`period_type` × `metric_type` × `target_value` + 生效期 | PRD §5.4；多条独立判断；**达标进度不落表**（派生值） |
| **`ProjectEvent`** | `project_events`（§5.6）：`event_type` 十值 + `from/to_value` JSONB + `actor` | TAD §3.1；随项目 purge 级联删除 |

两点必须记住：

1. **`project_events` 与审计表的外键方向相反**。它是业务可追溯记录，项目没了它就该没（`ON DELETE CASCADE`）；审计表若加指向业务表的外键，`purge` 会连审计一起删掉，审计即失效（ADR-008）。
2. **四张表都不新增软删列**：规则用 `enabled`、标记用 `status`、事件只追加（延续 ADR-006 的分层原则）。

**实现现状（2026-11-27，与本节原计划的偏差已记录）**：

| 项 | 落地情况 |
|---|---|
| `theory_enabled` / `practice_enabled` | ✅ 列已建、默认 true；**未进 API**——openapi 1.6.0 的 `ProjectItem` 未收录这两个字段，按「契约最小承诺」不擅自扩字段，等 M04/M06 需要读取时再开 |
| `project_priority_overrides` / `project_commitment_rules` | ⬜ **未建表**。二者在 v1 没有写入方（P3 调度阶段才用），建空表违反「禁止无调用路径的预留模块」；等 M04 调度落地时随接口一起补 |
| `project_events` | ⬜ **未建表**。字段集与事件语义尚未定（见 §10 缺口 5）；`purge` 与改期的结构化快照暂落 WARN 日志 |

## 6. 状态与副作用

**状态机（ADR-005 D-16 六值 + D-01 三条边缘决策）**：

| 当前 | 动作 | 目标 | 副作用 |
|---|---|---|---|
| `draft` | `activate` | `active` | — |
| `active` | `pause` | `paused` | — |
| `paused` | `resume` | `active` | — |
| `active` / `paused` | `complete` | `completed` | — |
| `completed` | `reopen` | `active` | `reopened_at = now`，清 `archived_at` |
| `draft` / `active` / `paused` / `completed` | `archive` | `archived` | `archived_at = now`，**不级联删除子数据** |
| `archived` | `reopen` | `active` | `reopened_at = now`，清 `archived_at` |
| `draft` | `delete` | （行消失） | 级联物理删除规划数据（单事务） |
| 任意 | `purge` | （行消失） | `status=deleting` 拦并发写 → 级联删 → 删项目行 |

**必须遵守的三条**：

1. **未定义迁移一律 409**，不猜测意图。
2. **`deleting` 不对外持久可见**：只作为 `purge` 事务内的并发写保护标记存在。任何常规写入（PATCH / 动作端点）把 `status` 置 `deleting` 都必须被拒绝，否则产生僵尸态——既不能操作，也不会被清理。
3. **`complete` 不写 `completed_at`**：本项目表没有该列（ERD 未设），完成时间如需统计，只能从审计或 `ProjectEvent` 取。这是已知的表达力缺口。

**副作用汇总**：

| 动作 | 写入 |
|---|---|
| `activate` / `pause` / `resume` | 仅 `status` + `updated_at` |
| `complete` | `status` + `updated_at` |
| `reopen` | `status` + `reopened_at = now` + `archived_at = NULL` |
| `archive` | `status` + `archived_at = now` |
| `extend-deadline` | `deadline_at`；`reason` 入审计（当前只能进结构化 WARN 日志） |
| `purge` | 级联删全部规划域数据 + 审计行（`action = project.purge`） |

## 7. 错误映射

| 场景 | 变体 | HTTP | 备注 |
|---|---|---|---|
| 项目不存在 / 非本人 | `NotFound` | 404 | 二者不可区分（防 ID 探测） |
| 项目状态迁移非法（如 `completed → paused`） | `Conflict` | 409 | ADR-005 D-01 |
| 非 `draft` 项目走 `DELETE` | `Conflict` | 409 | 引导归档或 `purge` |
| `purge` 的 `confirm_name` 不匹配 | `Validation` | 422 | 参数错误，不是状态冲突 |
| `fixed` 项目经 `PATCH` 改 `deadline_at` | `Validation` | 422 | 须走 `extend-deadline` |
| `extend-deadline` 缺 `reason` 或 `new_deadline_at` 早于当前 | `Validation` | 422 | |
| `importance_level` 越界（非 1–5） | `Validation` | 422 | DB CHECK 兜底，错误需映射为 422 而非 500 |
| `deadline_type=none` 却传 `deadline_at` | `Validation` | 422 | 字段组合非法 |

## 8. 事务边界

| 操作 | 事务内容 |
|---|---|
| 单条 CRUD | 单语句，无需事务 |
| **`draft` 删除** | 单事务，级联顺序：`task_dependencies` → `learning_tasks`（含已软删行）→ `milestones` → `stages` → `goal_stages` → `roadmaps` → `project_goals` → 项目行 |
| **`purge`** | 单事务：校验 `confirm_name` → `SELECT … FOR UPDATE` + `status=deleting` → 同上全量级联 → 写审计 → 删项目行 |
| `extend-deadline` | 校验 `deadline_type=fixed` → 更新 → 写审计，三步同事务 |

**跨模块级联的处理（重要）**：级联要删的 7 张表全属 M04，但 `draft` 删除与 `purge` 在 M02。约定 **M02 在自己事务内直接执行级联 SQL**，不调用 M04 的 service——跨模块调 service 会各自 `begin()`，事务边界立刻失效（见 `README.md` §2 依赖规则 2）。

代价是 M02 需要知道 M04 的表结构，这是一处**刻意的耦合**。若将来级联逻辑变复杂（如增加软删、增加审计快照），应改为「M04 暴露纯函数式 SQL 片段」或「把删除编排上提到 M01 级别的账号级服务」，而不是让两个 service 互相调用。

**锁策略**：`purge` 与所有动作端点用 `SELECT … FOR UPDATE` 锁项目行（动作端点也锁，是为了让「两个并发 pause」中的第二个读到最新状态而不是双双成功）。普通 CRUD 靠 `WHERE owner_id = $2` 的条件更新实现，不加锁。

## 9. 测试策略

`backend/tests/project_flow.rs`（13 个用例，`#[sqlx::test]` 真库）：

| 用例 | 断言 |
|---|---|
| `create_applies_contract_defaults` | D-19 默认值（study / I3 / none / draft）、名称 `trim` |

| `lifecycle_actions_follow_the_matrix` | draft → active → paused → active → completed → reopen → archived → reopen，逐步校验 `status` 与 `archived_at` / `reopened_at` |
| `list_excludes_archived_by_default` | 默认排除 archived；`include_archived=true` 含；**`status=archived` 直接可查**；`status=active` 只回活跃 |

| `project_isolation_hides_other_users_projects` | 他人项目 detail / patch / delete / 各动作一律 404 |
| `draft_delete_cascades_but_non_draft_requires_purge` | 草稿删除成功且子数据物理清空；非草稿 DELETE 409；`purge` 名称错 422 且数据仍在 |
| `archive_keeps_planning_children` | 归档后 goals / roadmaps / stages / tasks 全部 `total = 1`（归档 ≠ 删除） |
| `purge_only_removes_the_target_project` | 同用户另一项目及其目标不受影响（级联范围不越界） |
| `deleting_achieved_goal_returns_conflict` | `achieved` 目标删除 409、终态之间不直转 |
| `unknown_project_returns_404` | 不存在与越权同码；失败响应仍带 `request_id` |
