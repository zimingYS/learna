**三处拆分判断**：

1. **`roadmap` 与 `task` 分开**。任务的 `stage_id` 与 `milestone_id` **都可空**（D-05 决策），意味着任务可以直挂项目、不属任何路线。塞进 `roadmap` 会让该模块同时依赖项目与路线两个上层，且「无路线的任务」变成例外分支。任务独立成模块后，`project_id` 是唯一必需归属，语义干净。
2. **`schedule` 不装任务**。原计划里 `schedule` 曾被考虑作为任务目录，现明确留给 P3 的 `DailyLearningGoal` / `ScheduledActivity`。任务属规划，日程属调度，两者的时间语义不同。
3. **`goal` 不单独建目录**。目标（7 项）与项目是 1:N 强从属，且 `GoalStage` 整体替换要校验「阶段属同一项目」，需要读 `roadmaps`。放 `project` 会让 `project` 反向依赖路线；放 `roadmap` 则是现状——路线模块读项目归属、写目标，依赖方向一致（向下读项目表，不 import 项目 service）。

## 4. 调用链与分层

以「阶段完成」为例，展示跨模块的准入校验：

```text
POST /api/v1/projects/{pid}/roadmaps/{rid}/stages/{sid}/complete
  router/roadmap.rs
    → handler::stage_complete(State, Extension<UserId>, Extension<RequestId>, Path(pid,rid,sid))
      → stage_service::complete(&db, user_id, pid, rid, sid)
          1. SELECT s.*, r.status AS roadmap_status
               FROM stages s
               JOIN roadmaps r ON r.id = s.roadmap_id
               JOIN learning_projects p ON p.id = r.project_id
              WHERE s.id = $1 AND r.id = $2 AND r.project_id = $3
                AND p.owner_id = $4
             -- 一次查询同时完成：存在性、归属、父链一致性（越权 = 空行 = 404）
          2. rules::ensure_roadmap_active(roadmap_status)?    -- 非 active → 409
          3. rules::ensure_stage_transition(current, Complete)?
             -- 仅 active 可 complete：pending / completed / skipped 一律 409
             -- 若 current == completed 则提前返回 200，且不刷新任何时间戳（同态幂等）
          4. UPDATE stages
                SET status = 'completed', completed_at = now(),
                    completion_method = 'user', updated_at = now()
              WHERE id = $1 RETURNING …
      → ApiReply(Ok(StageItem), req_id)
```

**分层约束**：

- handler 只做提取器与 `ApiReply` 包装，不出现 `if`。
- 归属校验一律写进 SQL 的 `JOIN` + `WHERE`，不做事先 SELECT 再判断（避免 TOCTOU 与两次往返）。
- 状态判定抽到 `rules.rs`（纯函数），可无 DB 单测。
- `sequence_no` 分配用 `COALESCE(MAX(sequence_no), 0) + 1`，配 `UNIQUE(roadmap_id, sequence_no)` 重试一次。**不重试会在并发插入时 500**。

## 5. 数据与不变量

**表清单**：`project_goals`、`roadmaps`、`stages`、`milestones`、`learning_tasks`、`task_dependencies`、`goal_stages`（规划 7 张）+ `daily_learning_goals`、`scheduled_activities`（调度 2 张）。

> **Migration 已落地**：`migrations/20261127210000_0004_learning_planning.sql` 建 9 张表与全部索引，13 根外键的 `ON DELETE` 按 §5 逐条照写；`learning_tasks` 的列表索引带 `WHERE deleted_at IS NULL` 部分条件。ERD V1.2 已含 `project_goals.parent_goal_id`、`learning_tasks.stage_id`、`learning_tasks.deleted_at` 三列。

**必须由服务层（而非 DB）保证的规则**：

| 规则 | 为何 DB 无法独立保证 | 依据 |
|---|---|---|
| 一个项目最多一个 `active` 路线 | 可用部分唯一索引兜底，但 confirm 需先降级旧 active，必须事务内有序执行 | ERD §5.1；ADR-004 |
| 一个项目最多一个主目标（`parent_goal_id IS NULL`） | 需部分唯一索引断言「同项目内 parent 为 null 的行 ≤ 1」；v1 走服务层 | D-06 |
| 目标层级上限两层、不得成环、不得跨项目 | 递归约束，SQL 表达成本过高 | D-06 |
| 任务 `stage_id` 与 `milestone_id` 同时存在时，阶段须与里程碑所属阶段一致 | 跨两表一致性 | D-05 |
| 依赖两端须同项目且不得成环 | 图算法 | PRD §4.5 |
| `sequence_no` 在路线内唯一 | 可用 `UNIQUE(roadmap_id, sequence_no)`，但分配需应用层配合重试 | §4 |

**外键删除行为（Migration 必须逐条照写，不要留默认 `NO ACTION`）**：

| 子表.列 | 父表 | `ON DELETE` | 理由 |
|---|---|---|---|
| `roadmaps.project_id` | `learning_projects` | `CASCADE` | 路线不能脱离项目存在 |
| `roadmaps.created_by` | `users` | `SET NULL` | ERD 允许按系统操作语义为空 |
| `project_goals.project_id` | `learning_projects` | `CASCADE` | 目标不能脱离项目存在 |
| `project_goals.parent_goal_id` | `project_goals` | **`CASCADE`** | **不能写 `SET NULL`**：删主目标会把子目标升格为主目标，直接破坏「每项目最多一个主目标」（D-06） |
| `stages.roadmap_id` | `roadmaps` | `CASCADE` | 阶段是路线内结构，draft 路线删除即物理删阶段 |
| `milestones.stage_id` | `stages` | `CASCADE` | `stage_id` NOT NULL，不存在「无阶段的里程碑」 |
| `learning_tasks.project_id` | `learning_projects` | `CASCADE` | **唯一绕过软删的路径**：项目是任务的归属根（`NOT NULL`） |
| `learning_tasks.stage_id` | `stages` | **`SET NULL`** | 任务不随上层结构消失（L3），只能解挂 |
| `learning_tasks.milestone_id` | `milestones` | **`SET NULL`** | 同上 |
| `task_dependencies.task_id` | `learning_tasks` | `CASCADE` | 纯关联行，无独立历史 |
| `task_dependencies.depends_on_task_id` | `learning_tasks` | `CASCADE` | 同上 |
| `goal_stages.goal_id` | `project_goals` | `CASCADE` | 纯关联行 |
| `goal_stages.stage_id` | `stages` | `CASCADE` | 纯关联行 |

**三条必须理解的交互（否则 Migration 或 service 会写错）**：

1. **`CASCADE` 是安全网，不是主路径**。删阶段时 DB 会连锁做三件事：`CASCADE` 删 `milestones` → 后者的 `ON DELETE` 再把 `learning_tasks.milestone_id` 置 NULL；同时 `SET NULL` 掉 `learning_tasks.stage_id`、`CASCADE` 删 `goal_stages`。但服务层**仍须显式按 §8 顺序执行**——因为影响面计数（`DeletionConflict.impact`）必须在删之前算出来，而 DB 级联不给你这个数。
2. **软删行也会被 `SET NULL`**。外键不看 `deleted_at`：一条 `deleted_at IS NOT NULL` 的任务只要还引用着被删阶段，就必须被置 NULL，否则删阶段会外键违约（500）。这**不损害执行历史**——`completed_at` / `deleted_at` / `title` 不变，「挂在哪个阶段」是可重建的归属信息，不是执行事实。
3. **软删不触发 `CASCADE`**。软删是 `UPDATE` 不是 `DELETE`，所以「软删任务时物理清理其依赖行」（§6）**必须服务层显式做**；DB 的 `CASCADE` 只在项目 `purge` 真正 `DELETE` 任务行时才生效。

**软删除的唯一对象**：`learning_tasks.deleted_at`（ADR-006 / ERD V1.2 §5）。**软删行不参与应用层的**：列表、依赖环路检测、`DeletionConflict` 的 `impact` 计数、结构解挂候选集（ADR-007 §6）。这条连带规则必须写进每个查询，漏一处就会出现「删了阶段但提示还有 3 个任务」。

## 6. 状态与副作用

**四个状态机，实现时不得自行扩展边**：

| 对象 | 规则来源 | 迁移驱动 | 要点 |
|---|---|---|---|
| 目标（三值） | ADR-006 §3 | `PATCH status` | `active → achieved / cancelled`；允许 `achieved → active`、`cancelled → active`；**拒绝 `achieved → cancelled`**（409）；`achieved` 删 409 |
| 路线（三值） | ADR-004 + ADR-006 §6 | 动作端点 | `draft → active`（confirm，写 `confirmed_at`）；active 被新版本确认时被动 → `superseded`；**superseded 全程只读**（任何写操作 409） |
| 阶段（四值） | PRD §4.4 + 设计记录 §2.4 | **四动作端点** | 表见下。**不走 `PATCH status`**，迁移集固定四条边 |
| 里程碑 / 任务 | ADR-007 §1 | `PATCH status` | 统一规则，见下 |

**阶段：四条边固定，`pending` 不能直达 `completed`**

| 当前 | 动作 | 目标 | 副作用 |
|---|---|---|---|
| `pending` | `start` | `active` | `started_at = now`（首次写入） |
| `pending` / `active` | `skip` | `skipped` | — |
| `active` | `complete` | `completed` | `completed_at = now`、`completion_method = user` |
| `completed` / `skipped` | `reactivate` | `active` | 原态为 `completed` 时清 `completed_at`；`started_at` 不变 |

**否定边（一律 409，实现时不要把统一规则套上来）**：`pending → completed`（须先 `start`，PRD §4.4 把「提前进入」独立成动作）、`completed → skipped`、`skipped → pending`、`pending → reactivate`。同态提交幂等 200 的判据是「**动作的目标态 == 当前态**」：`active` 上 `start`、`completed` 上 `complete` 返回 200 且不刷新任何时间戳；`pending` 上 `reactivate` **不是**同态（`reactivate` 源态集只有 `completed` / `skipped`），是 409。理由见 ADR-007 §1 的「Stage 的两条例外」。

**ADR-007 统一迁移规则**（仅适用于以 `PATCH status` 驱动的里程碑与任务，一条规则替代 5×5 矩阵）：

> 允许跳过中间态 + 允许向未完态回退 + **终态之间不直转**（`completed ↔ cancelled` / `completed ↔ skipped` 必须先回退）+ 同态提交幂等 200（不报 409）。

**时间戳副作用**（`completed_at` 三资源同构；`started_at` 仅 Stage 有此列）：

| 事件 | 写入 |
|---|---|
| 进入 `completed` | `completed_at = now()` |
| 离开 `completed` | `completed_at = NULL` |
| 首次 `start`（阶段） | `started_at = now()`；后续 start **不覆盖**，也不因回退清空 |

**已知损失**：`completed_at` 离开即清空 + 无状态历史表 → **v1 无法统计「这个阶段完成过几次」**。已登记 ADR-007，不要以为能统计（与 ADR-006 §3 目标达成时间不可追溯同类）。

**其他副作用**：

| 动作 | 写入 |
|---|---|
| 路线 confirm | `confirmed_at = now()`；同项目旧 active → `superseded`；**单事务** |
| 阶段 complete | `status` + `completed_at` + `completion_method = 'user'` |
| 目标置 `achieved` | `status`；**无 `achieved_at` 列**（ERD 未设），达成时间不可追溯 |
| 任务软删 | `deleted_at = now()`；**显式**物理删 `task_dependencies` 两端行（软删是 `UPDATE`，不触发 `ON DELETE CASCADE`） |
| GoalStage 替换 | 删旧行 → 批量插入；不动目标与阶段 |

**调度部分的状态（未设计）**：`ScheduledActivity.status` 五值 `proposed / scheduled / completed / skipped / cancelled`。关键约束：**标记 `completed` 不代表已产生 `LearningSession`**——完成状态应以实际记录为依据，或要求关联实际 session（ERD §5.5）。这是「计划 ≠ 实际」的硬边界。

## 8. 事务边界

严格按 `设计记录` §7 执行，**必须单事务的十一类**：

| 操作 | 事务内容 |
|---|---|
| 项目 draft 删除 | 校验 `status=draft` → 级联物理删 `task_dependencies` → `learning_tasks`（**含已软删行**）→ `milestones` → `stages` → `goal_stages` → `roadmaps` → `project_goals` → 删项目行 |
| 项目 purge | 校验 `confirm_name == name` → 置 `deleting` 并加行锁拦截并发写 → 同上顺序级联 → 删项目行 → 结构化快照日志 |
| 路线 confirm | 锁同项目 active 行 → 降级 → 目标置 active + `confirmed_at` |
| 跨版本状态动作 | 读 `roadmaps.status` 与目标行必须在同一事务内，否则并发 confirm 会让动作通过已失效的准入 |
| GoalStage 整体替换 | 校验全部 stage 同项目且无重复 → 删旧行 → 批量插入 |
| 阶段删除 | `milestones` → 任务解挂（清 `stage_id` **与** `milestone_id`）→ `goal_stages` → 阶段行 |
| 里程碑删除 | 任务解挂（只清 `milestone_id`，保留 `stage_id`）→ 里程碑行 |
| 路线删除 | `milestones` → 任务解挂（清 `stage_id` **与** `milestone_id`）→ `goal_stages` → `stages` → 路线行 |
| 任务软删 | 置 `deleted_at` + **显式**物理删 `task_dependencies` 两端行（软删不会触发 `CASCADE`） |
| 目标删除 | `achieved` 拒绝 409 → 删 `goal_stages` → 有子目标须 `?cascade=true` 并级联删子目标（否则 409 带 `impact.goals`）→ 删目标行 |
| 依赖建立 | 校验同项目 → 环检测 → 插入（防并发成环） |

**锁策略**：`confirm` 用 `SELECT … FOR UPDATE` 锁同项目路线行；其余靠 `WHERE status = 期望值` 的条件更新实现乐观并发（`rows_affected = 0` → 409），不额外加锁。

**`confirm` 的死锁风险**：两个并发 confirm 会争同项目行。用**固定顺序**加锁（先锁 `project_id` 对应行，按 `id` 排序），不要按「当前 active 行」加锁——若两个请求锁的是不同版本，会互相等待。
