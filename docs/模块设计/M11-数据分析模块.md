# M11 数据分析模块

**契约状态：** §4.8 的 `/analytics` ⬜ 规划中，无 DTO、无 openapi 条目
**实现状态：** 🟡 `modules/report` 只有空 `mod.rs`；前端 `ReportsView.vue` 是静态占位（5 行）
**依据：** PRD §13（数据可视化与分析）、§18 第 9 项（多时区策略，在 ERD §12）；ERD §7（索引建议）、§12 第 9 项；TAD §5

## 1. 职责与边界

**做什么**（PRD §13.1 五层）：

| 层级 | 首版内容 | 数据源 | 状态 |
|---|---|---|---|
| 个人 Dashboard | 总学习时间、学习趋势、活跃项目 | `learning_sessions` / `projects` | ❌ 主数据源不存在 |
| 项目分析 | 项目进度、时间投入、阶段完成情况 | `learning_sessions` + `stages` | ❌ 两张表都不存在 |
| 学习内容分析 | 知识点分布、掌握情况、薄弱项 | `project_contents` + `mastery_assessments` | ❌ 三张表都不存在 |
| 学习计划分析 | 计划时间与实际时间对比、任务完成趋势 | `scheduled_activities` + `learning_sessions` + `tasks` | ❌ 全不存在 |
| 生活数据分析 | 基础统计（启用生活模块后） | 生活记录表 | ❌ 表未定义 |
| （过渡可用） | 总时长 / 按日时长 / 按科目分布 | `learning_records` | ✅ 唯一可算 |

**不做什么**（这些属其他模块，勿塞进本域）：

| 不做 | 归属 | 理由 |
|---|---|---|
| 调度（今天该学什么） | M04 | 调度是「依据过去推未来」，报表是「总结过去」。方向相反，共用数据源但不能合并 |
| 掌握度计算 | M06 | 本域只**展示** `recognized_level`，不判定 |
| AI 分析文案 | M12 | PRD §13.2 的「AI 深度分析」属最终目标；本域只出数字与图表数据 |
| 生活数据采集 | M10 | 本域只在有数据时读 |
| 数据导出 | M01（账号数据权利） | PRD §15「用户拥有学习数据导出能力」是账号级能力，不是报表能力。两者格式诉求不同：导出要全量原始，报表要聚合 |

**本模块最重要的一个事实**：

> 报表域不是「还没写」，是「**没有数据可算**」。

这不是抱怨，是排期依据。M11 的代码量在所有模块里最小（无写路径、无事务、无状态机），但它的依赖面最宽——需要 M02/M04/M05/M06/M07/M10 全部落地才有意义。**先做 M11 只能得到一堆空图表**。

## 2. 目录与文件形态

```text
modules/report/               🟡 空 mod.rs
├── mod.rs                    # 仅声明 + re-export
├── dto.rs                    # 各报表的查询参数与响应结构
├── handler.rs                # 只读 GET，无 POST/PATCH/DELETE
├── service.rs                # 编排多查询、拼装响应
└── queries.rs                # 聚合 SQL 集中（报表 SQL 长且易变，不与 CRUD 混放）
```

**为什么单独 `queries.rs`**：报表 SQL 平均长度是 CRUD 的 5~10 倍，且随指标口径反复调整。混在 `service.rs` 里会让该文件在半年内变成 800 行。集中放还有一个好处：可以一眼看出哪些查询依赖哪张表，便于在表结构变更时评估影响面。

## 4. 调用链与分层

**Dashboard 聚合**：

```text
GET /api/v1/analytics/dashboard?from=2026-11-01&to=2026-11-27
  request_id_middleware → auth_middleware → Extension<UserId>
  handler::dashboard(State, Extension<UserId>, Extension<RequestId>, Query<RangeQuery>)
    → service::dashboard(&db, user_id, range)
        1. rules::validate_range(range)?        -- to >= from，跨度 <= 上限
        2. queries::total_minutes(&db, …)        -- 单条聚合
        3. queries::daily_series(&db, …)         -- GROUP BY date_trunc('day', started_at)
        4. queries::active_projects(&db, …)
        5. queries::stage_completion(&db, …)
        6. 拼装 → DashboardDto
    → ApiReply(Ok(dto), req_id)
```

**分层约束**：

- **聚合必须在 DB 内完成**。不要 `SELECT *` 拉到 Rust 再用 `HashMap` 分组——数据量到十万级后这是灾难。
- 时间区间用参数化 `QueryBuilder` 拼，**不字符串拼接**。
- 所有查询都要带 `owner_id` 条件。报表最容易越权：`WHERE project_id = $1` 而忘了校验项目归属，就会泄漏他人数据。**每个查询的 `WHERE` 里都必须出现 owner 条件或经由 owner 校验的子查询**。
- 无写路径，**不开启事务**。

## 5. 数据与不变量

**本域无自有表**。它是纯读者，依赖以下数据源：

| 指标 | 数据源 | 依赖模块 | 就绪 |
|---|---|---|---|
| 总学习时长 | `learning_sessions.duration_minutes` | M05 | ❌ |
| 按日时长序列 | `learning_sessions.started_at` | M05 | ❌ |
| 项目时间投入 | `learning_sessions.primary_project_id` + `session_projects` | M05 | ❌ |
| 项目进度 | `stages.status` / `milestones.status` | M04 | ❌ |
| 任务完成趋势 | `learning_tasks.status` + `completed_at` | M04 | ❌ |
| 知识点分布 | `project_contents` + `learning_contents.content_type` | M03 | ❌ |
| 掌握情况 / 薄弱项 | `mastery_assessments.recognized_level` | M06 | ❌ |
| 计划 vs 实际 | `scheduled_activities.planned_minutes` vs `learning_sessions.duration_minutes` | M04 + M05 | ❌ |
| 复习负荷 | `review_items.next_review_at` | M07 | ❌ |
| 生活基础统计 | 生活记录表 | M10 | ❌ |
| **总时长 / 按日 / 按科目**（过渡） | `learning_records` | `/records` | ✅ |

**不变量**：

| 不变量 | 说明 |
|---|---|
| 只读 | 本域**不得有任何写操作**。若某个指标需要「预先算好存起来」，那也是加缓存表/物化视图，不是业务写入 |
| 越权隔离 | 每个查询必须按 `owner_id` 过滤；不得出现「先查全量再过滤」 |
| 数字自洽 | 同一响应内的数字必须能对上（见 §8） |
| 空数据表达一致 | 见 §3 决策 5 |
| 不虚构 | PRD §17 第 13 条「项目投入保障未达标时，系统提醒并建议，不虚构学习记录」——报表同样不得为「看起来好看」而补零或估算 |

## 6. 状态与副作用

**无状态、无写入、无副作用**。唯一成本是查询的 CPU 与 IO。

这也是它与其他模块最大的不同：本域的 bug 不会污染数据，只会显示错误的数字。**但错误的数字比没有数字更危险**——用户会据此调整学习计划。

## 7. 错误映射

| 场景 | 变体 | HTTP | 备注 |
|---|---|---|---|
| 时间区间非法（`to < from`） | `Validation` | 422 | |
| 区间过大（超上限） | `Validation` | 422 | 上限需决策 2；不要静默截断，用户会以为看了全年 |
| 日期格式非法 | `Validation` | 422 | |
| 项目不存在 / 非本人（项目分析） | `NotFound` | 404 | |
| 无数据 | **200 + 空结构** | 200 | **不是 404**：没学过不是错误 |
| 生活模块未开启 | 200 + 空分节 | 200 | 见决策 8 |

**注意最后一组**：本域绝大多数「异常」是正常状态（新用户零数据、模块未开启）。用 4xx 表达会让前端无法区分「出错了」与「还没开始学」。

## 8. 事务边界

**不需要事务**。但有一处需要在意：

**多查询的数字自洽**。若响应里同时有「总时长」与「按日时长序列」，两者分开查且不在同一快照，理论上会出现「序列求和 ≠ 总数」（期间有新数据写入）。三种处理：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 接受轻微不一致 | 零成本；个人工具可接受 |
| B | 一次查询 + 窗口函数 | 需要把多个指标塞进一条 SQL，可读性下降 |
| **C** | `BEGIN ISOLATION LEVEL REPEATABLE READ` 只读事务包住多查询 | 每条连接多一次快照开销，但改动最小 |

推荐 **C**：报表是只读的，可重复读快照不会有锁竞争，且能从根上消除不一致。**不要**用 `SERIALIZABLE`——对只读场景是过度设计。

## 9. 测试策略

待建 `backend/tests/report_flow.rs`：

| 用例组 | 断言 |
|---|---|
| 区间边界 | `from=to` 单日正确；`from` 为当天 00:00、`to` 为 23:59:59 均包含 |

| 空数据 | 新用户 Dashboard → 200，所有数值为 0 或空数组（不是 null，不是 404） |

| 区间上限 | 超出上限 → 422，且 message 说明上限值 |
| 生活分节 | M10 无数据时 Dashboard 正常返回，`life` 分节为空 |

单测落 `rules.rs`：区间校验、时区换算（`chrono-tz` 的边界日期）。

**分阶段策略（重要）**：

| 阶段 | 做法 | 理由 |

| **现在** | **不建 `report` 模块**。若前端需要「看得见的进展」，在 `ReportsView.vue` 里基于 `/records` 做两个统计卡片（总时长 / 按日），**临时在前端算** | 为过渡数据源建正式模块，等于承认 `learning_records` 是长期模型，与 M05 的演进路径冲突 |

| M07+M10 落地后 | 加「复习负荷 / 生活统计」 | 最后 |

**不要做的事**：不要在报表里做「预测」或「建议」。PRD §13.2 明确这些属「AI 深度分析」与「最终目标」，且要求「分析结果应提供数据依据、时间范围和可信程度，避免将相关性表述为因果关系」。本域的职责是**如实呈现已发生的事实**，任何推断都应交给 M12 并标注为建议。
