# M05 学习活动与证据模块

**契约状态：** §3 过渡实现 5 项 ✅ 可用（`x-learna-status: interim`）；§4.3 正式 `LearningSession` ❓ 未设计
**实现状态：** `learning_record` ✅ 过渡可用 ｜ `learning_session`(待建) ⬜ 未开始 ｜ `evidence`(待建) ⬜ 未开始
**依据：** PRD §11.2（学习活动记录）、§11.3（每日学习时间）、§16.2（计划/实际/创建时间分离）；ERD §5.3（`LearningSession` / `SessionProject` / `SessionContent` / `TaskSession` / `LearningEvidence`）、§12 第 4 项（计时规则未锁定）

## 1. 职责与边界

**做什么**：

| 能力 | 表 | 状态 |
|---|---|---|
| **过渡**：记录一次学习（标题/正文/时长/科目） | `learning_records` | ✅ 5 端点可用 |
| 正式学习活动：一个主要项目 + 多个关联项目 + 时间区间 + 四段式描述 | `learning_sessions` | ❓ 未设计 |
| 一次活动关联多个学习内容 | `session_contents` | ❓ 未设计 |
| 一次活动关联多个任务（含贡献分摊） | `task_sessions` | ❓ 未设计 |
| 学习证据（笔记 / 代码 / 图片 / 文件 / 链接 / 测试结果） | `learning_evidence` | ❓ 未设计 |
| 计时（开始 / 暂停 / 结束 / 事后补录 / 修改实际时长） | — | ❓ 未设计 |

**不做什么**（这些属其他模块，勿塞进本域）：

| 不做 | 归属 | 理由 |
|---|---|---|
| 计划活动（今天打算学什么） | M04 `scheduled_activities` | **计划 ≠ 实际**。PRD §16.2「原始计划、实际安排、实际活动和延期历史分开保存」 |
| 每日目标分钟数 | M04 `daily_learning_goals` | 目标是「想达到」，本域是「已发生」 |
| 复习反馈 | M07 `review_records` | `ReviewRecord` 可关联 `learning_session_id`，但复习状态归 M07 |
| 掌握度评价 | M06 | 证据是评价的**输入**，评价本身独立 |
| 题库作答 | M08 | `Attempt` 可关联 session，但判分归 M08 |
| 实践成果档案 | M09 | 证据是一次活动的附件；成果是长期档案，生命周期不同（PRD §10.2） |

**三个时间概念必须分开（PRD §16.2）**：

| 概念 | 字段 | 含义 |
|---|---|---|
| 创建时间 | `created_at` | 什么时候录入系统的（可能是补录，远晚于实际） |
| 实际发生时间 | `started_at` / `ended_at` | 什么时候真的在学 |
| 有效时长 | `duration_minutes` | 服务端根据区间或用户确认生成，不等于 `ended_at - started_at` |

## 2. 目录与文件形态

```text
modules/learning_record/      ✅ 过渡实现
├── mod.rs                    # 声明三文件 + pub use handler::*（通配，风格不一致，见 §10）
├── dto.rs                    # CreateRecordRequest / UpdateRecordRequest / RecordResponse / RecordQuery
├── handler.rs                # create / list / detail / update / delete
└── service.rs                # 5 个函数 + RecordRow(FromRow)

modules/learning_session/     ⬜ 待建
├── mod.rs
├── dto.rs                    # SessionItem / CreateSessionRequest / UpdateSessionRequest
│                             # SessionContentItem / SessionProjectItem / TaskSessionItem
├── handler.rs                # 主资源 + 三类关联子资源
├── service.rs                # 创建（含时长生成）、跨项目/内容归属校验
├── timer.rs                  # 计时状态（形态未定，见 §10 缺口 7）
└── rules.rs                  # 时长上限、区间合法性、有效学习日判定

modules/evidence/             ⬜ 待建
├── mod.rs
├── dto.rs                    # EvidenceItem / CreateEvidenceRequest（含 multipart 或预签名 URL）
├── handler.rs
└── service.rs                # 元数据落库 + 对象存储 key 管理
```

**为什么 `learning_record` 不直接改造为 `learning_session`**：改造意味着给过渡表加 `project_id`、加时间区间、加多内容关联——每一步都会让 `/records` 的既有数据需要迁移，且前端在迁移期间必须同时支持两套字段。正确路径是**新建表 + 新建模块 + 数据迁移脚本 + 一次性切换**，旧模块与旧表在切换后下线。在正式模型冻结前，**不得**给 `/records` 增加项目关联或时长校验（那会让迁移成本翻倍，也会让「过渡实现」变成事实标准）。

## 4. 调用链与分层

**创建正式学习活动（设计草案）**：

```text
POST /api/v1/learning-sessions
  request_id_middleware → auth_middleware → Extension<UserId>
  handler::create(State, Extension<UserId>, Extension<RequestId>, Json<CreateSessionRequest>)
    → service::create(&db, user_id, req)
       -- 单事务
       1. 校验 primary_project_id 与 related_project_ids 全部属当前用户
            SELECT id FROM learning_projects
             WHERE id = ANY($1) AND owner_id = $2
            -- 数量不符 → NotFound（不区分「项目不存在」与「不是你的」）
       2. 校验 content_ids 全部属当前用户
       3. rules::derive_duration(started_at, ended_at, client_reported)?  -- 时长生成
       4. INSERT INTO learning_sessions (…) RETURNING …
       5. INSERT INTO session_projects / session_contents / task_sessions  -- 批量
       6. UPDATE learning_tasks SET status='completed' … （可选，须用户显式请求）
```

**时长生成的三条候选规则（未决策）**：

| 方案 | 规则 | 风险 |
|---|---|---|
| A | `duration_minutes = (ended_at - started_at)` 分钟数，忽略客户端上报 | 计时段内去喝水也计入，用户无法修正 |
| B | 服务端只校验 `client_reported <= 区间时长`，超出则 422 | 客户端可信度依赖前端，但至少不出现「10 分钟区间报 3 小时」 |
| **C** | 服务端算出区间时长作为**上限**，用户上报值取 `min` 且允许事后修正 | 兼顾可信与可改；`duration_minutes` 与区间可以不等（有暂停） |

推荐 C。ERD 原文「应由服务端根据时间区间或用户确认的有效学习时长生成，不能仅信任前端」正是这个意思——「或」字给了两条路径，C 是两者的组合。

**分层约束**：

- handler 只做提取器与 `ApiReply` 包装。
- 归属校验走 `WHERE … owner_id = $n`，不做事先 SELECT。
- 时长推导放 `rules.rs` 纯函数，可单测边界（跨午夜、零长度、负数、超 24 小时）。

## 5. 数据与不变量

**表清单**（ERD §5.3）：

| 表 | 关键字段 | 关键约束 |
|---|---|---|
| `learning_sessions` | `owner_id`、`primary_project_id`（可空）、`title`、`activity_type`（theory/practice/review/mixed/other）、`started_at`、`ended_at`、`duration_minutes`、`summary`/`what_done`/`problems`/`next_steps`、`created_source`（user/timer/imported） | `ended_at >= started_at`；`primary_project_id` 非空时 owner 必须一致；**主要项目最多一个** |
| `session_projects` | `session_id`、`project_id`、`relation_role`（primary/related） | `UNIQUE(session_id, project_id)`；**实现上只存 related**，primary 以 `learning_sessions.primary_project_id` 为权威（ERD 明确推荐此方案，避免双重事实） |
| `session_contents` | `session_id`、`content_id`、`contribution_type`（primary/covered/practiced）、`note` | 复合主键 `(session_id, content_id)`；两者同属一个用户 |
| `task_sessions` | `task_id`、`session_id`、`contribution_minutes`、`note` | 复合主键 `(task_id, session_id)`；**同一 session 的分摊总和 ≤ 有效时长**（服务层校验） |
| `learning_evidence` | `owner_id`、`session_id`（可空）、`evidence_type`、`storage_key`、`external_url`、`mime_type`、`size_bytes` | 附件二进制在对象存储，DB 只存元数据与 key |
| `learning_records` | 过渡表：`user_id`、`title`、`content`、`duration_minutes`、`subject` | `user_id FK → users ON DELETE CASCADE` |

**必须由服务层保证的规则**：

| 规则 | 为何 DB 无法独立保证 |
|---|---|
| 主要项目最多一个，且必须出现在 `session_projects` 的 primary 里 | ERD 建议干脆不存 primary 关联行，只存 related；但若存了就要一致 |
| 同一 session 的 `contribution_minutes` 总和 ≤ `duration_minutes` | 聚合比较，CHECK 无法跨行 |
| `session_contents` 的 content 与 session 同 owner | 跨表 |
| `task_sessions` 的 task 必须属 session 的某个关联项目 | 跨三表 |
| 证据的 `storage_key` 与 `external_url` 至少有一个 | 可 CHECK，建议下放 DB |
| 时长上限（如单次 ≤ 24 小时） | 业务规则，可 CHECK 但阈值可能变 |

**ERD 已发现的一处冗余**：`SessionProject.relation_role` 有 `primary` 值，但同一份 ERD 又说「更推荐只保留 `LearningSession.primary_project_id` 作为权威字段」。**实现时按推荐方案**：`session_projects` 只存 related，`relation_role` 列可以保留但只写入 `related`，或干脆去掉该列。不要两种都写。

## 6. 状态与副作用

**无状态机**。`LearningSession` 一旦写入即为事实，不可「状态流转」。

**副作用**：

| 动作 | 写入 |
|---|---|
| 创建 session | 主表行 + 三类关联行；`created_source` 标记来源（`user` / `timer` / `imported`） |
| 修改时长 | `duration_minutes` + `updated_at`；**建议保留修改痕迹**（PRD §16.2 要求「实际学习发生时间与创建时间分开」，但没要求改时长留痕；若要审计需 `ProjectEvent` 同族的事件表） |
| 删除 session | 级联删 `session_contents` / `session_projects` / `task_sessions`；`learning_evidence.session_id` 置 NULL 还是删证据？**未定**（证据可能独立价值） |
| 任务标记完成 | 由 session 触发时**必须由用户显式请求**，不能「记录了学习就自动完成任务」——那会把「学习」与「任务完成」两个语义混起来 |

**与 M04 `ScheduledActivity` 的关系（硬边界）**：计划的 `completed` **不代表**已产生 session。ERD §5.5 明确「完成状态应以实际记录为依据或要求关联实际 session」。实现上建议：计划完成时若未关联 session，只把 `status` 改为 `completed`，不伪造任何时长。

## 7. 错误映射

| 场景 | 变体 | HTTP | 备注 |
|---|---|---|---|
| 记录 / session 不存在或非本人 | `NotFound` | 404 | 过渡实现文案不一致：detail 用「未查询到此数据」，update 用「未查询到此纪录」——统一掉 |
| PATCH 无任何字段 | `Validation` | 422 | `no fields to update` |
| `ended_at < started_at` | `Validation` | 422 | |
| 上报时长 > 区间时长（方案 C） | `Validation` | 422 | 提示「上报 180 分钟，但区间只有 60 分钟」 |
| `primary_project_id` 不属当前用户 | `NotFound` | 404 | 不区分「不存在」与「不是你的」 |
| `task_sessions` 分摊总和超时长 | `Validation` | 422 | |
| 内容跨用户 | `Validation` | 422 | 防御性，理论上不可达 |

## 8. 事务边界

| 操作 | 事务 |
|---|---|
| 过渡 `/records` 全部操作 | 单语句，无显式事务 |
| 正式 session 创建 | **必须单事务**：主表 + 三类关联行。任一关联校验失败则整体回滚，否则会出现「session 存在但关联缺失」 |
| session 更新 + 关联整体替换 | 单事务：删旧关联 → 校验新关联 → 插入 |
| session 删除 | 单事务：清关联 → 删主表（或软删） |
| 证据上传 | **外部存储不进事务**。正确顺序：事务1 校验权限并占位 → 事务外上传对象 → 事务2 写元数据。若上传成功但事务2 失败，会产生孤儿对象（需定期清理或改用预签名 URL 让客户端直传后再登记） |

**过渡实现的已知不一致**：`/records` 列表的「数据 + 计数」两个查询不在同一事务，理论上 `total` 与 `items` 可能轻微不一致。个人工具可接受；正式实现建议改用窗口函数 `COUNT(*) OVER ()` 一次查完。

## 10. 实现状态与缺口

**已实现（过渡）**：5 个端点、动态 SET 的 PATCH、分页与计数、越权 404、前端 API 封装与两个纯函数测试。

**过渡实现的六个缺陷**：

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | **PATCH 无法把可空字段置 null** | `Option<String>` 的 `None` 同时表示「未传」与「传 null」，用户无法清空 `content` / `subject`。修复需 `Option<Option<String>>` + 双重 Option 反序列化 |
| 2 | **`duration_minutes` 类型不一致** | DB 是 `INT4 NOT NULL`，查询恒为 `Some`，但 Rust 与 TS 都声明可空——类型声明在说谎。建议统一为 `i32` |
| 3 | `mod.rs` 用 `pub use handler::*` 通配 | 与 `auth` 的显式 re-export 风格不一致，通配会随 handler 增加而扩大门面 |
| 4 | 错误文案不一致 | 见 §7 |
| 5 | `RecordQuery` 用 `Option<i64>` | 负值靠 `.max(1)` 兜，可接受但不精确 |
| 6 | 列表两查询不同事务 | 见 §8 |

**正式模型的阻塞项（按解除顺序）**：

| # | 阻塞 | 解除条件 |
|---|---|---|
| 1 | **正式模型未设计** | 需一轮契约设计，把 §3 的 7 项待决策拍板；ERD §12 第 4 项（计时规则）必须先定 |
| 2 | **计时形态未定** | 四种候选：① 纯前端计时，结束时一次性提交起止时间 ② 后端存 timer 状态（需 `active_timers` 表） ③ 事后补录（用户手填区间） ④ 混合。①+③ 最简单，②能防「前端崩溃丢计时」但引入新表与新状态机 |
| 3 | **删除语义未定** | 学习记录是统计基础，物理删会让历史报表数字变化。建议软删（`deleted_at`）+ 所有聚合查询过滤，但这与 M04 任务软删的连带规则要一致 |
| 4 | **`LocalStorage` 是 stub** | 证据文件功能完全不可用，调用即 500 |
| 5 | **D-20 未决** | 项目 `purge` 时「主要归属学习记录」是删还是解挂保留？这是本模块与 M02 的交界，ERD §12 第 5 项明确列为待补 |
| 6 | **无 `ProjectEvent` 同族事件表** | 改时长、删记录无法追溯 |
| 7 | **`/records` 下线时点未定** | 数据迁移脚本（`learning_records` → `learning_sessions`）未写；`subject` 字段在新模型里无对应物，需决定映射到 `summary` 还是丢弃 |

**建议**：正式模型排 P1，但**不要在设计未冻结时给 `/records` 加功能**。若前端急需「按项目筛选学习记录」，也应等正式表落地后一次性切换，而不是在过渡表上加 `project_id`——那等于把过渡模型固化成事实标准，迁移成本会翻倍。
