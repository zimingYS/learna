## 1. 职责与边界

**做什么**：

| 能力 | 表 | 状态 |
|---|---|---|
| **过渡**：记录一次学习（标题/正文/时长/科目） | `learning_records` | ✅ 5 端点可用（冻结，待下线） |
| 正式学习活动：一个主要项目 + 多个关联项目 + 时间区间 + 四段式描述 | `learning_sessions` | ✅ 契约已定 |
| 一次活动关联多个学习内容 | `session_contents` | ✅ 契约已定（`PUT` 整体替换） |
| 一次活动关联多个任务（含贡献分摊） | `task_sessions` | ✅ 契约已定（`PUT` 整体替换，总和 ≤ 时长） |
| 学习证据（笔记 / 链接 / 测试结果） | `learning_evidence` | ✅ 契约已定（v1 不开文件类） |
| 计时（开始 / 暂停 / 结束 / 事后补录 / 修改实际时长） | — | ✅ 已定：客户端计时 + 补录，**无服务端 timer**（ADR-010 §2） |

**不做什么**（这些属其他模块，勿塞进本域）：

| 不做 | 归属 | 理由 |
|---|---|---|
| 计划活动（今天打算学什么） | M04 `scheduled_activities` | **计划 ≠ 实际**。PRD §16.2「原始计划、实际安排、实际活动和延期历史分开保存」 |
| 每日目标分钟数 | M04 `daily_learning_goals` | 目标是「想达到」，本域是「已发生」 |
| 复习反馈 | M07 `review_records` | `ReviewRecord` 可关联 `learning_session_id`，但复习状态归 M07 |
| 掌握度评价 | M06 | 证据是评价的**输入**，评价本身独立 |
| 题库作答 | M08 | `Attempt` 可关联 session，但判分归 M08 |
| 实践成果档案 | M09 | 证据是一次活动的附件；成果是长期档案，生命周期不同（PRD §10.2） |

**三个时间概念必须分开（PRD §16.2）**：

| 概念 | 字段 | 含义 |
|---|---|---|
| 创建时间 | `created_at` | 什么时候录入系统的（可能是补录，远晚于实际） |
| 实际发生时间 | `started_at` / `ended_at` | 什么时候真的在学 |
| 有效时长 | `duration_minutes` | 服务端根据区间或用户确认生成，不等于 `ended_at - started_at` |

## 2. 目录与文件形态

```text
modules/learning_record/      ✅ 过渡实现
├── mod.rs                    # 声明三文件 + pub use handler::*（通配，风格不一致，见 §10）
├── dto.rs                    # CreateRecordRequest / UpdateRecordRequest / RecordResponse / RecordQuery
├── handler.rs                # create / list / detail / update / delete
└── service.rs                # 5 个函数 + RecordRow(FromRow)

modules/learning_session/     🟡 空 shell（契约已定）
├── mod.rs                    # 只做声明与 re-export，不写逻辑
├── dto.rs                    # SessionItem / SessionDetailItem / CreateSessionRequest / UpdateSessionRequest
│                             # SessionContentItem / SessionTaskItem
├── handler.rs                # 主资源 + 三个 PUT 整体替换子资源
├── service.rs                # 创建（单事务）、跨项目/内容/任务归属校验、软删
└── rules.rs                  # 时长生成（min 规则）、区间合法性、分摊总和校验

modules/evidence/             🟡 空 shell（契约已定）
├── mod.rs
├── dto.rs                    # EvidenceItem / CreateEvidenceRequest
├── handler.rs                # 列表 / 新建 / 详情 / 删除
├── service.rs                # 元数据落库 + 归属校验
└── rules.rs                  # 按 evidence_type 校验必填字段（note/link/test_result）

**没有 `timer.rs`**：计时状态完全在客户端，服务端不做 timer（ADR-010 §2）。若将来真要做服务端计时，那会是一张新表 + 一套新状态机，届时另立 ADR，不在这条路线上渐进。
```

**为什么 `learning_record` 不直接改造为 `learning_session`**：改造意味着给过渡表加 `project_id`、加时间区间、加多内容关联——每一步都会让 `/records` 的既有数据需要迁移，且前端在迁移期间必须同时支持两套字段。正确路径是**新建表 + 新建模块 + 数据迁移脚本 + 一次性切换**，旧模块与旧表在切换后下线。在正式模型冻结前，**不得**给 `/records` 增加项目关联或时长校验（那会让迁移成本翻倍，也会让「过渡实现」变成事实标准）。

## 4. 调用链与分层

**创建正式学习活动（设计草案）**：

```text
POST /api/v1/learning-sessions
  request_id_middleware → auth_middleware → Extension<UserId>
  handler::create(State, Extension<UserId>, Extension<RequestId>, Json<CreateSessionRequest>)
    → service::create(&db, user_id, req)
       -- 单事务
       1. 校验 primary_project_id 与 related_project_ids 全部属当前用户
            SELECT id FROM learning_projects
             WHERE id = ANY($1) AND owner_id = $2
            -- 数量不符 → NotFound（不区分「项目不存在」与「不是你的」）
       2. 校验 content_ids 全部属当前用户
       3. rules::derive_duration(started_at, ended_at, client_reported)?  -- 时长生成
       4. INSERT INTO learning_sessions (…) RETURNING …
       5. INSERT INTO session_projects / session_contents / task_sessions  -- 批量
       6. UPDATE learning_tasks SET status='completed' … （可选，须用户显式请求）
```

**时长生成规则（D-32 / ADR-010 §1 已定）**：

| 输入 | 结果 |
|---|---|
| 只给区间 | `duration_minutes = ⌊(ended_at − started_at) / 60⌋` |
| 区间 + 上报值（≤ 区间） | 采信上报值（区间内有暂停是正常预期） |
| 区间 + 上报值（> 区间） | **422**，message 写明「上报 N 分钟，但区间只有 M 分钟」 |

即 `duration_minutes = min(用户上报, 区间分钟数)`，用户上报可选。ERD 原文「应由服务端根据时间区间或用户确认的有效学习时长生成，不能仅信任前端」正是这个意思——「或」字给了两条路径，本规则是两者的组合：上界由服务端算，区间内的真实值由用户确认。

**分层约束**：

- handler 只做提取器与 `ApiReply` 包装。
- 归属校验走 `WHERE … owner_id = $n`，不做事先 SELECT。
- 时长推导放 `rules.rs` 纯函数，可单测边界（跨午夜、零长度、负数、超 24 小时）。

## 5. 数据与不变量

**表清单**（ERD §5.3）：

| 表 | 关键字段 | 关键约束 |
|---|---|---|
| `learning_sessions` | `owner_id`、`primary_project_id`（可空）、`title`、`activity_type`（theory/practice/review/mixed/other）、`started_at`、`ended_at`、`duration_minutes`、`summary`/`what_done`/`problems`/`next_steps`、`created_source`（user/timer/imported）、**`created_at` / `updated_at` / `deleted_at`（ADR-010 补）** | `ended_at >= started_at`；`duration_minutes ≤ 区间`；`primary_project_id` 非空时 owner 必须一致；**主要项目最多一个**；软删过滤 `deleted_at IS NULL` |
| `session_projects` | `session_id`、`project_id`、`relation_role`、`created_at` | `UNIQUE(session_id, project_id)`；**只存 related**，`relation_role` 恒写 `related`；primary 以 `learning_sessions.primary_project_id` 为权威（ERD 明确推荐） |
| `session_contents` | `session_id`、`content_id`、`contribution_type`（primary/covered/practiced）、`note` | 复合主键 `(session_id, content_id)`；两者同属一个用户；整体替换写入 |
| `task_sessions` | `task_id`、`session_id`、`contribution_minutes`、`note` | 复合主键 `(task_id, session_id)`；**同一 session 的分摊总和 ≤ 有效时长**（服务层校验）；任务须属于该 session 的关联项目 |
| `learning_evidence` | `owner_id`、`session_id`（可空）、`evidence_type`（v1 只开 note/link/test_result）、`title`、`description`、`external_url`、`created_at` | v1 无 `storage_key` / `mime_type` / `size_bytes`（无生产者）；`note`/`test_result` 需 `description`，`link` 需 `external_url` |
| `learning_records` | 过渡表：`user_id`、`title`、`content`、`duration_minutes`、`subject` | `user_id FK → users ON DELETE CASCADE`；**冻结待下线**（D-34） |

**必须由服务层保证的规则**：

| 规则 | 为何 DB 无法独立保证 |
|---|---|
| 主要项目最多一个，且**不重复出现在** `session_projects` 里 | ERD 推荐只存 related；`PUT /projects` 传主要项目 → 422 |
| 同一 session 的 `contribution_minutes` 总和 ≤ `duration_minutes` | 聚合比较，CHECK 无法跨行 |
| `session_contents` 的 content 与 session 同 owner | 跨表 |
| `task_sessions` 的 task 必须属 session 的某个关联项目 | 跨三表 |
| 证据按类型必填（`note`/`test_result` 需 `description`，`link` 需 `external_url`） | DB CHECK 可表达，服务层同时校验以给出可读 message；`storage_key` 系列不在 v1 契约内（D-36） |
| 时长上限（如单次 ≤ 24 小时） | 业务规则，可 CHECK 但阈值可能变 |

**ERD 已发现的一处冗余**：`SessionProject.relation_role` 有 `primary` 值，但同一份 ERD 又说「更推荐只保留 `LearningSession.primary_project_id` 作为权威字段」。**实现时按推荐方案**：`session_projects` 只存 related，`relation_role` 列可以保留但只写入 `related`，或干脆去掉该列。不要两种都写。

## 6. 状态与副作用

**无状态机**。`LearningSession` 一旦写入即为事实，不可「状态流转」。

**副作用**：

| 动作 | 写入 |
|---|---|
| 创建 session | 主表行 + 三类关联行（单事务）；`created_source` 标记来源（`user` / `timer`，`imported` 仅迁移） |
| 修改时长 | `duration_minutes` + `updated_at`；新值同样受「≤ 区间」约束。**不留审计**（审计表未设计，ADR-010 待补齐第 1 项） |
| 删除 session | **软删**：`deleted_at = now()`。三类关联行与 `learning_evidence.session_id` **全部保留**（ADR-010 决策 3）；软删后详情 404、列表与聚合排除 |
| 删除证据 | 物理删除（无下游引用）；session 软删不解挂证据 |
| 任务标记完成 | 由 session 触发时**必须由用户显式请求**，不能「记录了学习就自动完成任务」——那会把「学习」与「任务完成」两个语义混起来 |

**与 M04 `ScheduledActivity` 的关系（硬边界）**：计划的 `completed` **不代表**已产生 session。ERD §5.5 明确「完成状态应以实际记录为依据或要求关联实际 session」。实现上建议：计划完成时若未关联 session，只把 `status` 改为 `completed`，不伪造任何时长。

## 7. 错误映射

| 场景 | 变体 | HTTP | 备注 |
|---|---|---|---|
| 记录 / session / evidence 不存在、非本人、已软删 | `NotFound` | 404 | 过渡实现文案不一致：detail 用「未查询到此数据」，update 用「未查询到此纪录」——统一掉；软删对客户端表现为不存在 |
| PATCH 无任何字段 | `Validation` | 422 | `no fields to update` |
| `ended_at < started_at` | `Validation` | 422 | |
| 上报时长 > 区间时长（D-32） | `Validation` | 422 | 提示「上报 180 分钟，但区间只有 60 分钟」 |
| `primary_project_id` 不属当前用户 | `NotFound` | 404 | 不区分「不存在」与「不是你的」 |
| `related_project_ids` 含主要项目 | `Validation` | 422 | 主要项目只由主字段表达 |
| `task_sessions` 分摊总和超时长 / 任务不属于关联项目 | `Validation` | 422 | |
| 内容跨用户 | `Validation` | 422 | 防御性，理论上不可达；内容不存在则 404 |
| `created_source = imported`（API 提交） | `Validation` | 422 | 仅迁移脚本可用 |
| 证据类型为 `code` / `image` / `file` | `Validation` | 422 | v1 未开放（D-36） |
| 证据 `note`/`test_result` 缺 `description`、`link` 缺 `external_url` | `Validation` | 422 | |

## 8. 事务边界

| 操作 | 事务 |
|---|---|
| 过渡 `/records` 全部操作 | 单语句，无显式事务（已冻结，不再改动） |
| 正式 session 创建 | **必须单事务**：主表 + 三类关联行。任一关联校验失败则整体回滚，否则会出现「session 存在但关联缺失」 |
| 三类关联 `PUT` 整体替换 | **必须单事务**：删旧关联 → 校验新关联 → 插入 |
| session PATCH | 单语句（条件更新带 `deleted_at IS NULL`）；时长校验先 `SELECT … FOR UPDATE` 取当前区间 |
| session 删除 | 单语句 `UPDATE … SET deleted_at`；**不碰关联行**（ADR-007 §6：软删不触发级联） |
| 证据创建 / 删除 | 单语句。v1 无文件上传，因此**不存在**「对象存储不进事务」的三段式问题；将来开文件类证据时再引入「占位 → 上传 → 登记」或预签名直传 |

**过渡实现的已知不一致**：`/records` 列表的「数据 + 计数」两个查询不在同一事务，理论上 `total` 与 `items` 可能轻微不一致。个人工具可接受；正式实现建议改用窗口函数 `COUNT(*) OVER ()` 一次查完。

| # | 缺陷 | 影响 |

| 1 | **PATCH 无法把可空字段置 null** | `Option<String>` 的 `None` 同时表示「未传」与「传 null」，用户无法清空 `content` / `subject`。修复需 `Option<Option<String>>` + 双重 Option 反序列化（正式模型直接用 `shared/patch.rs` 的三态工具） |
| 2 | **`duration_minutes` 类型不一致** | DB 是 `INT4 NOT NULL`，查询恒为 `Some`，但 Rust 与 TS 都声明可空——类型声明在说谎。建议统一为 `i32` |
| 3 | `mod.rs` 用 `pub use handler::*` 通配 | 与 `auth` 的显式 re-export 风格不一致，通配会随 handler 增加而扩大门面 |
| 4 | 错误文案不一致 | 见 §7 |
| 5 | `RecordQuery` 用 `Option<i64>` | 负值靠 `.max(1)` 兜，可接受但不精确 |
| 6 | 列表两查询不同事务 | 见 §8 |
