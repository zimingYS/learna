# M01 用户与权限模块

**契约状态：** §1 认证 2 项 ✅ 已实现；`/users/me` 系列 ⬜ 未设计
**实现状态：** `auth` ✅ 可用 ｜ `user` 🟡 空壳 ｜ 账号注销与数据导出 ⬜ 未设计
**依据：** PRD §15（账号、隐私与数据权利）、§16.1（安全）；ERD §5.1 `User`；ADR-003（request_id 注入）

## 1. 职责与边界

**做什么**：

| 能力 | 状态 | 说明 |
|---|---|---|
| 邮箱 + 密码注册 | ✅ | 重复邮箱拦截 + 唯一约束兜底 |
| 登录与 JWT 签发 | ✅ | HS256，`Claims { sub, exp }`，有效期 7 天 |
| 请求认证（受保护路径） | ✅ | `auth_middleware` 产出 `Extension<UserId>` |
| 当前用户资料读取 / 更新 | ⬜ | PRD §15 的「多设备使用」隐含需要此端点 |
| 账号注销与数据删除 | ⬜ | PRD §15「用户可以申请删除账号及其个人数据」 |
| 个人数据导出 | ⬜ | PRD §15「用户拥有学习数据和个人记录的导出能力」 |

**不做什么**（这些属其他位置，勿塞进本模块）：

| 不做 | 归属 / 理由 |
|---|---|
| 角色与 RBAC | v1 是个人工具，只有「本人的数据 / 非本人」两态；越权一律 404。引入共享或协作前必须先设计权限模型，不得在 service 里散写 `if role == …` |
| 会话管理（refresh token、黑名单、强制下线） | JWT 无状态的必然结果，PRD 未要求。若需真正失效，须引入 token 表或缩短有效期 + refresh |
| 邮箱验证、找回密码、第三方登录 | PRD 未要求，v1 不做 |
| 登录日志与操作审计 | 审计是横切能力，见 `README.md` §6.4。登录日志对无状态 JWT 无关联价值 |
| 健康数据授权开关 | 属 M10（PRD §12.4），它管的是「数据能否给 AI 用」，不是「谁能登录」 |

**边界判断**：`auth` 管「怎么证明你是你」，`user` 管「你这份账号里有什么」。两者共用 `users` 表但职责不同——`auth` 的 service 不应出现 `display_name` 的业务规则，`user` 的 service 不应出现密码哈希。

## 2. 目录与文件形态

```text
modules/auth/                 ✅ 已实现
├── mod.rs                    # 声明三文件 + 显式 re-export handler::{register, login}
├── dto.rs                    # RegisterRequest / LoginRequest / AuthResponse / UserResponse
├── handler.rs                # 两个 handler：State + RequestId + Json → service → ApiReply
└── service.rs                # UserRow / generate_token / hash_password / register / login

modules/user/                 🟡 只有空 mod.rs
├── mod.rs                    # 待建：声明 dto / handler / service
├── dto.rs                    # 待建：UserProfile / UpdateProfileRequest / DeleteAccountRequest
├── handler.rs                # 待建：me / update_me / delete_me / export
└── service.rs                # 待建：资料读写、注销事务编排

router/auth.rs                ✅ /auth/register、/auth/login（免认证）
shared/middleware.rs          ✅ auth_middleware（横切，M01 是唯一使用方）
```

**`auth` 与 `user` 不合并的理由**：`auth` 的依赖是 `bcrypt` + `jsonwebtoken`（纯计算），`user` 的依赖是业务表与跨模块级联（注销要扫全部表）。合并会让「登录」这个高频纯计算路径与「注销」这个低频全库操作挤在同一 service，测试与审阅成本都会上升。

**契约缺口**：`/users/me` 系列在 `接口清单.md` 里连 ❓ 行都没有——不是「待决策」，是「未登记」。实现前必须先补契约，不得先写 handler 再补文档。

## 4. 调用链与分层

**注册**：

```text
POST /api/v1/auth/register
  router/auth.rs → post(modules::auth::register)
  handler::register(State, Extension<RequestId>, Json<RegisterRequest>)
    → service::register(&db, &config, req)
        1. SELECT id::text FROM users WHERE email = $1        -- 预查重
        2. hash_password(pwd)                                 -- spawn_blocking(bcrypt, cost=12)
        3. INSERT … RETURNING id::text, email, display_name…  -- UserRow
        4. generate_token(user.id, jwt_secret)                -- exp = now + 7d
    → ApiReply(Ok(AuthResponse { token, user }), req_id)
```

**登录**：

```text
POST /api/v1/auth/login
  service::login
    1. SELECT … FROM users WHERE email = $1
    2. 无行 → Unauthorized("invalid credentials")    ← 不区分「用户不存在」与「密码错」
    3. bcrypt::verify                                  ← 同步执行，见 §10 缺口 1
    4. generate_token → AuthResponse
```

**受保护请求**（所有其他模块都走这条）：

```text
request_id_middleware  → Extension<RequestId>
auth_middleware        → authenticate() 同步解 JWT → Extension<UserId>
handler(State, Extension<UserId>, Extension<RequestId>, …)
```

**分层约束**：

- handler 只做提取器与 `ApiReply` 包装，不出现 `if`。
- bcrypt 是 CPU 密集操作（cost=12 约 250ms），**必须** `spawn_blocking`，否则阻塞 tokio worker。
- `authenticate()` 必须是同步 fn（详见 `README.md` §6.7）。

## 5. 数据与不变量

**表 `users`**（`migrations/…_0002_auth.sql`）：

| 列 | 类型 | 约束 |
|---|---|---|
| `id` | UUID | PK，`DEFAULT gen_random_uuid()` |
| `email` | TEXT | NOT NULL UNIQUE；另有 `idx_users_email` |
| `password_hash` | TEXT | NOT NULL，bcrypt `DEFAULT_COST` |
| `display_name` | TEXT | NOT NULL |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() |

**ERD 与实际实现的三处偏差**（写 Migration 前必须知道，不要照 ERD 直接生成 DDL）：

| 偏差 | ERD §5.1 | 实际 | 处置 |
|---|---|---|---|
| 密码字段 | 「认证凭据应放入独立凭据表或由认证模块管理，**不在此重复设计密码字段**」 | `password_hash` 直接在 `users` 上 | 可接受（单凭据类型），但需在 ERD V1.2 补记，避免后续有人按 ERD 再建一张凭据表 |
| 账号状态 | 有 `status`（`active / disabled / deleting`） | **无此列** | 账号注销设计前必须先补列或改方案，见 §6 |
| 邮箱长度 | `VARCHAR(320)` | `TEXT` | 无功能差异，`TEXT` 更宽松；若要加长度校验应在应用层 |

**服务层保证的规则**：

- 邮箱重复 → `Validation("邮箱已存在")`；DB 唯一冲突（SQLSTATE `23505`）同样映射为 `Validation`，防止并发注册穿透。
- `UserRow.id` 声明为 `String`，SQL 用 `id::text` 取值；JWT `sub` 存同一字符串。**不改这个约定**——`UserId(Uuid)` 在中间件里 `Uuid::parse_str` 解析，两处必须一致。
- `updated_at` 当前无更新路径（无改资料端点），因此不设触发器。

## 6. 状态与副作用

| 动作 | 副作用 |
|---|---|
| register | 插入 `users` 行；签发 JWT；无邮件、无审计 |
| login | 无写操作；仅签发 JWT |
| JWT | `exp = now + 7d`；过期后任何受保护请求 401，前端拦截器清 localStorage 并跳登录页 |
| 改资料 | `display_name` / `updated_at`（待实现） |
| 账号注销 | 见下 |

**账号注销的设计约束（PRD §15）**：

PRD 要求「删除前应明确提示影响范围；需要保留的法定或安全日志应在隐私政策中说明」，这与 ERD 的 `status = deleting` 一致——说明账号注销是**受控流程**，不是一条 `DELETE FROM users`。

三条必须满足的不变量：

1. **级联覆盖全部业务表**。当前只有 `learning_records.user_id FK … ON DELETE CASCADE`；M02~M12 的 `owner_id` 外键落地时都必须选择 `CASCADE` 或显式清理，不能留孤行。
2. **审计行必须保留**。审计表无指向业务表的外键（`README.md` §6.4），`actor_id` 是裸 UUID——注销后审计行天然不级联，正好满足「保留安全日志」。
3. **必须单事务**。跨 10+ 表的删除不能分多次提交，否则中途失败会留下半删账号（能登录但数据不全）。

注销形态建议（未决策）：`DELETE /users/me` + `confirm_email`，事务内 `status=deleting` 加行锁 → 级联清理 → 删 `users` 行 → 写审计。与 `purge` 项目的形态对齐。

## 7. 错误映射

| 场景 | 变体 | HTTP / 码 |
|---|---|---|
| 邮箱已存在（预查或 23505） | `Validation` | 422 `VALIDATION_ERROR` |
| 密码错误 / 用户不存在 | `Unauthorized` | 401 `UNAUTHORIZED`，message 统一 `invalid credentials` |
| 无 token / token 非法 / 过期 | `Unauthorized` | 401（中间件内直接返回，**同样带 request_id**） |
| bcrypt 运算失败 | `Hash` | 500 `HASH_ERROR` |
| JWT 编解码失败 | `Token` | 401 `TOKEN_ERROR` |
| 字段缺失或类型错 | axum `Json` 拒绝 | **非统一信封**，见 §10 缺口 3 |
| 注销确认邮箱不匹配 | `Validation` | 422（参数错误，不是状态冲突） |

## 8. 事务边界

| 操作 | 事务 |
|---|---|
| register | **不开显式事务**。查重与插入之间有并发窗口，由唯一约束兜底（冲突返回 422 而非脏数据）。显式事务只会把错误变复杂（还要处理 `23505` 的中断回滚），当前设计更简单且正确 |
| login | 无需事务（只读 + 计算） |
| 改资料 | 单语句，无需事务 |
| **账号注销** | **必须单事务**，见 §6 不变量 3 |

若将来注册需要「插入 users + 插入默认项目」，则必须改为单事务。

## 10. 实现状态与缺口

**已实现**：注册、登录、JWT 签发、bcrypt 哈希（注册路径）、重复邮箱检测（含唯一约束兜底）、认证中间件。

**缺口（按修复优先级）**：

| # | 缺口 | 影响 | 处置 |
|---|---|---|---|
| 1 | **`bcrypt::verify` 未包 `spawn_blocking`** | cost=12 约 250ms 同步阻塞 tokio worker；并发登录会拖慢其他请求 | 与 `hash_password` 同构包装即可，改动 3 行 |
| 2 | **`UserResponse::from_row(id: i64, …)` 是死代码且签名错误** | 实际 `UserRow.id` 是 `String`，该方法从未被调用；后来者可能误用 | 直接删除 |
| 3 | **JSON 解析失败不走统一信封** | axum `Json` extractor 拒绝时返回纯文本 422/400，body 不是 `{code,message,data,request_id}` | 需自定义 `Json` 包装类型的 `FromRequest`，属横切改动，影响所有模块 |
| 4 | **`user` 模块完全为空** | 无 `/users/me`、无改密码、无改 `display_name`；前端 `SettingsView.vue` 只能静态占位 | 先补契约再实现 |
| 5 | **无密码强度与邮箱格式校验** | 数据库只保证非空与唯一，`a@` 可注册成功。当前无邮件功能故不阻塞，但导出/通知功能上线后是坑 | 至少做 `@` 与最小长度校验 |
| 6 | **无登出端点** | 前端 `logout()` 只清 localStorage，token 在有效期内仍可用 | JWT 无状态的必然结果；需要真失效须引入 token 表 |
| 7 | **无账号注销与数据导出** | PRD §15 明确要求，但契约、表结构、级联方案全部缺位 | 需先补 ERD `users.status` 列 + 契约，再实现 |

**与 M02 的边界待决**：账号注销时用户的项目怎么处置？PRD 只说「删除账号及其个人数据」。建议沿用 `purge` 的四层级联语义（ADR-006），即全部物理删除、审计行保留。此项与 D-20（项目删除时学习记录的处置）是同一族问题，应在 LearningSession 设计时一并定。
