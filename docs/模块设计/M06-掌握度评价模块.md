# M06 掌握度评价模块

**契约状态：** §4.4 的 `/mastery-assessments` ⬜ 规划中，无 DTO、无 openapi 条目
**实现状态：** ⬜ 目录不存在（需新建 `modules/mastery`）
**依据：** PRD §7（学习评价体系）、§18 第 7/8 项（阈值与证据充分程度未定）；ERD §3.2（项目掌握度 vs 个人总体掌握度）、§5.4（`MasteryAssessment` / `OverallMasteryAssessment` / `OverallMastery`）、§12 第 6 项

## 1. 职责与边界

**做什么**：

| 能力 | 表 | 状态 |
|---|---|---|
| 记录一次项目级评价事件（自评 / 系统 / 认定，三方分离） | `mastery_assessments` | ⬜ 未设计 |
| 计算个人总体掌握（跨项目聚合，历史 + 当前快照） | `overall_mastery_assessments`、`overall_mastery` | ⬜ 未设计 |
| 生成「等级变化建议」（系统评价与自评明显不同、大幅变化、阶段测试后） | 无表（建议是瞬态还是持久化未定） | ❓ |
| 展示证据充分程度（证据不足 / 有限 / 较充分 / 充分） | 无表（由算法算出） | ❓ |

**不做什么**（这些属其他模块，勿塞进本域）：

| 不做 | 归属 | 理由 |
|---|---|---|
| 内容本体与项目关联 | M03 | 本域的评价**指向** `project_content_id` / `content_id`，不拥有它们 |
| 学习活动与证据 | M05 | 证据是评价的**输入**，本域不采集、不上传 |
| 复习调度 | M07 | 复习反馈可作为评价输入，但复习状态归 M07 |
| 题库作答与判分 | M08 | 客观题正确率是评价输入之一 |
| 实践成果档案 | M09 | 成果是技能类评价的重要证据，但档案归 M09 |
| 项目粗粒度状态（`learning` / `achieved`） | M03 `project_contents.current_status` | 见 §6 的协同规则 |

**核心判断：为什么评价要独立成模块而不是塞进 M03**：

`project_contents` 需要存「当前认定等级」，但**认定等级是评价的结果，不是内容的属性**。如果只有一张 `current_mastery_level` 列，就无法回答「这个等级是谁给的、依据是什么、什么时候变的、用户是否认同」。PRD §7.2 明确要求「必须分别保存用户自评等级、系统评价等级、当前认定等级」——**三个字段就等于三条独立的事实线**，只有事件表能承载。

ERD §3.2 又把掌握度分成两层：**项目掌握度**（`project_content` 上下文，同一内容在不同项目可不同）与**个人总体掌握度**（跨项目聚合，`content_id` 级）。两层各有历史与当前，共三张表。这不是过度设计，是 PRD §6.4「不能仅因在另一个项目中关联过该内容，就自动判定新项目的目标已完成」的必然结果。

## 2. 目录与文件形态

```text
modules/mastery/              ⬜ 待建
├── mod.rs
├── dto.rs                    # AssessmentItem / CreateAssessmentRequest
│                             # OverallMasteryItem / EvidenceAdequacy
├── handler.rs                # 项目级评价 CRUD、总体掌握查询、建议列表
├── service.rs                # 记录评价、确认认定等级、总体聚合
├── project_mastery.rs        # 项目级：三方等级、分歧状态、认定确认
├── overall_mastery.rs        # 个人级：跨项目聚合、快照更新
└── rules.rs                  # 纯函数：分歧判定、证据充分程度分级
```

**是否该拆 `rules.rs`**：是。分歧判定（`none / mild / significant`）与证据充分程度分级是**纯函数**，依赖阈值配置而非 DB。这类逻辑最需要单测，且阈值一定会变（PRD §18 第 7 项明确说「不同内容类型的具体判定阈值未定」），把阈值抽到 `rules.rs` 才能在调参时不碰 SQL。

## 4. 调用链与分层

**记录一次评价（POST）**：

```text
POST /api/v1/mastery-assessments
  request_id_middleware → auth_middleware → Extension<UserId>
  handler::create(State, Extension<UserId>, Extension<RequestId>, Json<CreateAssessmentRequest>)
    → project_mastery::create(&db, user_id, req)
       -- 单事务
       1. SELECT pc.id, pc.target_mastery_level, p.owner_id
            FROM project_contents pc
            JOIN learning_projects p ON p.id = pc.project_id
           WHERE pc.id = $1 AND p.owner_id = $2
          -- 一次校验内容关联存在 + 归属
       2. 无行 → NotFound
       3. rules::disagreement(self_level, system_level)   -- → none/mild/significant
       4. INSERT INTO mastery_assessments (…) RETURNING …
       5. 若请求带 `confirm_now = true` → UPDATE 认定等级（同一行或新行，见 §6）
    → ApiReply(Ok(AssessmentItem), req_id)
```

**关键设计：认定等级是「新行」还是「更新旧行」**。ERD 说「该表是历史记录，原则上只追加，不覆盖」。那么用户确认系统评价时：

| 方案 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| **A** | 追加一行，`recognized_level` 为新值、`confirmed_at = now()`；当前认定 = 最新 `confirmed_at` 非空的行 | 完整历史，符合「只追加」 | 查当前认定要 `ORDER BY assessed_at DESC LIMIT 1`，需索引 |
| B | 更新原行的 `recognized_level` 与 `confirmed_at` | 一行搞定 | 违背「只追加」；无法回答「用户改过几次」 |
| C | 追加一行 + 在 `project_contents` 加快照列 | 读快，写两次 | 快照可能漂移，需要重建工具 |

推荐 **A**（v1 不加快照）。理由是数据量小（个人工具，单内容每年几十条评价），一次 `ORDER BY … LIMIT 1` 走 `(project_content_id, assessed_at DESC)` 索引即可；而 B 会让「评价历史」这个唯一的价值消失。

**总体掌握的读路径**：

```text
GET /api/v1/overall-mastery/{content_id}
  → overall_mastery::get(&db, user_id, content_id)
      1. SELECT * FROM overall_mastery WHERE owner_id=$1 AND content_id=$2
         -- 快照表，O(1)
      2. 若不存在 → 空（不即时计算）
```

**快照 vs 实时计算**：`overall_mastery` 是快照表（ERD 明确「该表为当前快照；历史以 `overall_mastery_assessments` 为准」）。写入时机是「有新的 `OverallMasteryAssessment` 时同步更新」。查询读快照，不实时聚合——实时聚合要扫全部 `project_contents` 与 `mastery_assessments`，随数据增长会变慢。

## 5. 数据与不变量

**三张表（ERD §5.4）**：

| 表 | 粒度 | 关键字段 | 性质 |
|---|---|---|---|
| `mastery_assessments` | 项目内容级 | `owner_id`、`project_content_id`、`system_level`（0–4 可空）、`self_level`（0–4 可空）、`recognized_level`（0–4 **必填**）、`confidence`（0–1）、`disagreement_status`、`assessment_reason`、`assessment_method`、`assessed_at`、`confirmed_at` | **历史，只追加** |
| `overall_mastery_assessments` | 内容级 | `owner_id`、`content_id`、`system_level`、`confidence`、`assessment_method`、`evidence_cutoff_at`、`explanation`、`evaluated_at` | **历史，只追加** |
| `overall_mastery` | 内容级 | `(owner_id, content_id)` 复合主键、`latest_assessment_id`、`current_level`、`confidence`、`evaluated_at` | **当前快照，可重建** |

**三条核心不变量**：

1. **`recognized_level` 必填，`system_level` / `self_level` 可空**。首次评价时系统可能无证据（`system_level = NULL`），此时 `recognized_level` 初始采用用户自评（PRD §7.2）。
2. **系统评价变化只生成建议，不自动覆盖 `recognized_level`**。PRD §7.2 明文：「后续系统评价变化只生成建议，不自动覆盖当前认定等级。用户确认后才修改。」
3. **分歧必须保留，不得伪造一致**。`disagreement_status` 记录 `self_level` 与 `system_level` 的差异；PRD §7.2「系统必须保留分歧状态和系统证据，不能伪造一致性」。这意味着**任何算法都不得为了「好看」而把 self 收敛到 system**。

**服务层必须保证的规则**：

| 规则 | 为何 DB 无法独立保证 |
|---|---|
| `project_content_id` 的 owner 与 `owner_id` 一致 | 跨三表（assessments → project_contents → projects） |
| `confidence` 与 `disagreement_status` 的对应关系（置信度低时不应判 significant？） | 语义规则，需决策后再定 |
| `overall_mastery.latest_assessment_id` 必须指向该 `(owner_id, content_id)` 的最新评估 | 跨行一致性，需事务内保证 |
| 同一 `project_content_id` 在同一毫秒不得有两条评价 | 可用 `UNIQUE(project_content_id, assessed_at)` 兜底，但会误伤批量导入；v1 走服务层 |

## 6. 状态与副作用

**本模块无状态机**（评价事件不可「流转」）。但有一处**跨模块协同状态**必须写清：

**`project_contents.current_status` 与 `recognized_level` 的关系**（与 M03 的交界）：

| 内容状态 | 触发条件 | 由谁写 |
|---|---|---|
| `not_started` | 刚加入项目 | M03（`linked_at` 时） |
| `learning` | 首次产生学习活动或首次评价 | M03（用户操作）或 M05（有 session 时） |
| `reviewing` | 进入复习队列 | M07 |
| `achieved` | **`recognized_level` 达到 `target_mastery_level`** → M06 写入；或用户显式确认 | **M06 独占写入**（M03 的 §6 已约定用户不得手改） |
| `waived` | 用户放弃 | M03 |

**这条规则的意义**：M03 里 `achieved` 只能由 M06 写，这里就要给出**判定条件**——`recognized_level >= target_mastery_level`。若 `target_mastery_level` 为空（未设目标），则 `achieved` 只能由用户显式确认，不能自动推断。

**副作用**：

| 动作 | 写入 |
|---|---|
| 记录评价 | 插入 `mastery_assessments`；若带确认 → 追加确认行 + 可能更新 `project_contents.current_status = 'achieved'` + `achieved_at` |
| 系统评价生成 | 插入 `mastery_assessments`（`system_level` 非空、`recognized_level` 沿用当前值、`confirmed_at = NULL`）；**不改认定等级** |
| 总体评估 | 插入 `overall_mastery_assessments` → `UPSERT overall_mastery`（同事务） |
| 用户拒绝系统建议 | **不改任何行**？还是要记一条「用户拒绝」？建议记（否则同一建议会反复出现），但 ERD 无字段，需决策 |

## 7. 错误映射

| 场景 | 变体 | HTTP | 备注 |
|---|---|---|---|
| `project_content_id` 不存在 / 非本人 | `NotFound` | 404 | |
| 等级超出 0–4 | `Validation` | 422 | DB CHECK 兜底 |
| `confidence` 超出 0–1 | `Validation` | 422 | |
| 三个等级全为 NULL | `Validation` | 422 | 至少要有一个等级 |
| 重复确认同一条评价 | `Conflict` | 409 | 或幂等 200（需决策） |
| 总体掌握查询无记录 | 200 + `data: null` | — | **不是 404**：内容存在但从未评估，是正常状态 |
| 争议：确认一个与系统评价差 3 级的值 | 200 但带警告 | — | 建议在响应里带 `disagreement_status=significant`，不拒绝 |

**注意最后两条**：本模块的大部分「异常」不是错误，是**需要如实呈现的状态**。用 4xx 表达「证据不足」「分歧很大」会把正常的认知状态变成错误，这是设计陷阱。

## 8. 事务边界

| 操作 | 事务 |
|---|---|
| 记录单条评价 | 单语句 |
| 评价 + 确认 + 更新 `project_contents` | **必须单事务**：插入评价行 → 更新认定 → 若达成立刻改 `current_status`。任一步失败都会出现「等级已认定但状态还是 learning」 |
| 总体评估 + 快照 UPSERT | **必须单事务**：插入历史 → UPSERT `overall_mastery`。否则历史与快照不一致，且 `latest_assessment_id` 可能指向不存在的行 |
| 批量重算总体掌握 | 单事务（若数据量大则分批 + 幂等，避免长事务锁表） |

**并发**：两个请求同时确认同一评价时，用 `WHERE confirmed_at IS NULL` 的条件更新实现乐观并发（`rows_affected = 0` → 409）。

待建 `backend/tests/mastery_flow.rs`：

| 用例组 | 断言 |
|---|---|
| 首次评价 | `system_level = NULL`、`self_level = 3` → `recognized_level = 3`（采用自评，PRD §7.2） |

| 目标为空 | `target_mastery_level IS NULL` → **不自动置 achieved**（必须用户显式确认） |
| 总体掌握 | 两个项目同内容分别 L2/L4 → 聚合结果是定义好的规则值（规则定后才能写断言） |
| 快照一致性 | 插入新 `overall_mastery_assessments` → `overall_mastery.current_level` 同步更新，`latest_assessment_id` 指向新行 |

单测落 `rules.rs`：分歧三档边界（差值 0/1/2/3）、证据充分程度四档映射、`confidence` 边界（0、0.5、1）。

## 10. 实现状态与缺口

**已实现**：无。目录都不存在。

**阻塞项（按解除顺序，前两项是硬阻塞）**：

| # | 阻塞 | 影响 |
|---|---|---|
| 1 | **L0–L4 判定阈值未定**（PRD §18 第 7 项） | 「系统评价」无法实现。没有阈值时只能做「用户自评 + 手填系统值」，等于把算法责任推给用户 |
| 2 | **总体掌握算法未定**（ERD §12 第 6 项） | `overall_mastery` 的计算规则缺失，三张表里有两张无法写入 |
| 3 | 证据充分程度分级未定（PRD §18 第 8 项） | `confidence` 能存，但无法解释「为什么是 0.6」 |
| 4 | 无契约、无 Migration | 三张表均未落 DDL |
| 5 | 目录 `modules/mastery` 不存在 | 需新建并在 `modules/mod.rs` 声明 |
| 6 | 建议是否持久化未定 | 若要持久化需新增表（ERD 无） |
| 7 | 依赖 M03 / M05 / M07 / M08 数据 | 评价的输入全部来自其他模块，P2 中应排在它们之后 |

**建议的实现策略**：M06 的**完整形态**（自动系统评价 + 总体聚合）依赖算法设计与多模块数据，短期内不可能全部落地。但可以做一个**最小可用切片**：

1. 只做「用户自评 + 认定等级」：`POST /mastery-assessments`（`self_level` 必填、`system_level` 为 null）、`POST /{id}/confirm`。这不需要任何阈值，立刻可用。
2. 第二阶段接「系统评价建议」：等阈值（阻塞 1）与证据来源（M08 判分、M07 反馈）就绪后，由算法写 `system_level`，用户确认。
3. 第三阶段做「个人总体掌握」：等跨项目数据积累足够、聚合规则（阻塞 2）定稿后启用。

**不要**在第一阶段就建三张表——`overall_mastery_assessments` / `overall_mastery` 在算法未定时建出来只会是两张空表，反而让人误以为功能已具备。
