# M07 复习管理模块

**契约状态：** §4.4 的 `/reviews` ⬜ 规划中，无 DTO、无 openapi 条目
**实现状态：** ⬜ 目录不存在（需新建 `modules/review`）
**依据：** PRD §8（复习与遗忘管理）、§18 第 9 项（间隔算法未定）；ERD §3.4（默认独立、显式共享）、§5.4（`ReviewItem` / `ReviewRecord` / `ReviewShare`）、§12 第 7/9 项；TAD §3.6

## 1. 职责与边界

**做什么**：

| 能力 | 表 | 状态 |
|---|---|---|
| 复习队列项（按内容 / 项目内容，按复习类型） | `review_items` | ⬜ 未设计 |
| 每次复习的记录与类型化反馈 | `review_records` | ⬜ 未设计 |
| 跨项目复习证据共享（默认仅证据） | `review_shares` | ⬜ 未设计 |
| 逾期重排建议与延期历史 | 缺表（仅 TAD §3.6 有概念） | ❓ |
| 复习策略配置（全局 / 项目 / 内容三级） | 缺表（仅 TAD §3.6 有概念） | ❓ |
| 复习资格判定（eligible / L0 特殊 / 首次会话门槛） | 无表（隐式） | ❓ |

**不做什么**（这些属其他模块，勿塞进本域）：

| 不做 | 归属 | 理由 |
|---|---|---|
| 掌握等级判定 | M06 | 复习反馈是 M06 的**输入**，不直接改等级（PRD §8.4「未复习不等于已经遗忘，不应自动扣减掌握等级」） |
| 学习活动记录 | M05 | 复习可产生 `LearningSession`（`activity_type=review`），但 session 归 M05；本域只存 `learning_session_id` 外键 |
| 内容本体 | M03 | 队列项引用 `content_id` / `project_content_id` |
| 错题本与题库 | M08 | 错题复习**双通道**：本域管「错题关联知识点进复习队列」，M08 管「错题本独立练习」 |
| 今日计划排期 | M04 `scheduled_activities` | M04 读 `review_items.next_review_at` 生成今日复习，但**不写**复习状态 |
| 间隔算法参数调优界面 | 本域（首版不暴露） | PRD §8.5「首版不向普通用户暴露复杂 FSRS 参数」 |

## 2. 目录与文件形态

```text
modules/review/               ⬜ 待建
├── mod.rs
├── dto.rs                    # ReviewItemDto / ReviewRecordDto / SubmitReviewRequest
│                             # RescheduleProposal / ReviewPolicyDto
├── handler.rs                # 队列查询、提交复习、管理动作（暂停/恢复/退出）、重排确认
├── service.rs                # 队列 CRUD、提交复习、重排
├── scheduler.rs              # 间隔计算（纯函数：输入上次状态+反馈，输出下次日期）
├── eligibility.rs            # 资格判定（内容类型、L0 特殊、首次会话门槛）
└── rules.rs                  # 反馈模板映射、重排建议的紧迫度分级
```

**为什么把 `scheduler.rs` 与 `eligibility.rs` 独立出来**：这两处是本域唯二有实质算法的地方，且都是**纯函数**——输入明确、无副作用、可表驱动测试。ERD §12 第 9 项说「不同类型的复习间隔算法及参数」未定，意味着这里会反复调参。把算法关在一个文件里，调参时不碰 SQL 与 HTTP。

## 4. 调用链与分层

**提交一次复习（核心路径）**：

```text
POST /api/v1/reviews/{id}/records
  request_id_middleware → auth_middleware → Extension<UserId>
  handler::submit(State, Extension<UserId>, Extension<RequestId>, Path(id), Json<SubmitReviewRequest>)
    → service::submit(&db, user_id, item_id, req)
       -- 单事务
       1. SELECT * FROM review_items
           WHERE id = $1 AND owner_id = $2
           FOR UPDATE                      -- 锁队列项，防并发提交
       2. 无行 → NotFound
       3. rules::map_feedback(content_type, raw_feedback)  -- → 统一反馈枚举
       4. scheduler::next(&item, feedback)                  -- 纯函数：算新间隔与下次日期
       5. INSERT INTO review_records (…) RETURNING …
       6. UPDATE review_items
              SET next_review_at = …, interval_seconds = …, ease_factor = …,
                  status = CASE 完成时 … END
       7. 可选：若 req.session_id 非空 → 校验属当前用户（不写 session，只引用）
    → ApiReply(Ok(ReviewRecordDto), req_id)
```

**逾期重排（不自动改日程）**：

```text
GET /api/v1/reviews?due=overdue
  → service::list
      1. 查出逾期项（next_review_at < now()）
      2. 对每项调 rules::reschedule_proposal(item, now, daily_budget)  -- 纯函数
           → { urgency: high/medium/low, suggested_date, reason }
      3. 响应中附 `proposal` 字段（**不写库**）
```

**关键设计**：PRD §8.4 明确「逾期后系统只生成重新安排建议，**不自动改变用户日程**」。因此重排是**读侧计算**，只有用户显式 `accept-proposal` 或 `reschedule` 才写 `next_review_at`。这样同一份逾期数据不会因为「系统心情」而变。

**分层约束**：`scheduler.rs` 与 `eligibility.rs` 不碰 `sqlx`，只接受纯数据结构，便于无 DB 单测。

## 5. 数据与不变量

**表（ERD §5.4 已定义 3 张，TAD §3.6 另有 2 张概念表 ERD 未落）**：

| 表 | 来源 | 关键字段 | 关键约束 |
|---|---|---|---|
| `review_items` | ERD | `owner_id`、`project_content_id`（可空）、`content_id`、`scope_type`（`project_content` / `personal_content`）、`review_type`（`spaced_repetition` / `wrong_question` / `manual`）、`status`（`active` / `paused` / `completed` / `disabled`）、`next_review_at`、`interval_seconds`、`ease_factor`、`algorithm_version`、`auto_review_enabled` | `scope_type=project_content` → `project_content_id` 非空；`scope_type=personal_content` → 该列为空；`content_id` 必须与 `project_content_id` 引用的内容一致；**每个 scope+content+review_type 的有效状态唯一**（防重复队列） |
| `review_records` | ERD | `review_item_id`、`learning_session_id`（可空）、`reviewed_at`、`performance`、`user_feedback`、`error_count`、`duration_minutes`、`resulting_level`、`scheduler_snapshot` JSONB | 历史只追加 |
| `review_shares` | ERD | `source_review_record_id`、`target_project_content_id`、`share_type`（`evidence_only` / `propose_schedule_update`）、`accepted_at` | **默认只作证据**；目标项目要改自己的复习状态必须产生自己的确认记录 |
| `review_policies` | **TAD 有，ERD 无** | `scope`（global/project/content）、`content_type`、`enabled`、`algorithm_type`、`policy_config` | 缺表 |
| `review_reschedule_history` | **TAD 有，ERD 无** | 原到期、建议新时间、用户确认时间、延期原因、操作来源 | 缺表。TAD 明确「复习队列不能只保存当前下一次日期而丢失延期历史」 |

**必须由服务层保证的规则**：

| 规则 | 为何 DB 无法独立保证 |
|---|---|
| `content_id` 与 `project_content_id` 引用同一内容 | 跨两表 |
| 每个 scope + content + review_type 只有一个有效项 | 部分唯一索引可兜底（`WHERE status IN ('active','paused')`），建议下放 DB |
| `review_records.resulting_level` 与 M06 的 `recognized_level` 一致 | 跨模块；本域只记录，不保证 |
| 共享记录不得直接改目标项目队列 | 语义约束，需在 service 拒绝 |

**ERD 与 TAD 的字段分歧（必须拍板）**：

TAD §3.6 的 `ReviewItem` 有 `eligibility_status`（资格）、`suspended_at`、`archived_at`、`last_reviewed_at`；ERD §5.4 把它们合并成 `status` 四值 + `auto_review_enabled`。

这不是等价替换，因为**「资格」与「管理状态」是两件事**：

| 概念 | 问题 | PRD 依据 |
|---|---|---|
| 资格（eligibility） | 这份内容**够不够条件**进自动复习？（类型是否支持、L0 特殊、是否已完成首次会话） | §8.1 |
| 管理状态（status） | 用户对这个队列项**做了什么**？（暂停、退出、完成） | §8.3 |

ERD 用「有无 `review_items` 行」隐式表达资格——没资格就不建行。这在「资格一旦满足就不撤销」的前提下可行，但 L0 的「独立策略」需要区分，而且「首次会话完成后才有资格」意味着资格是**后置到达**的，需要某种触发机制（由 M05 建 session 时触发本域建队列项）。

**建议**：v1 沿用 ERD（不建 `eligibility_status`），把资格判定放进 `eligibility.rs` 作为「是否创建队列项」的判断函数，由 M05 的 session 创建事件调用。若将来出现「有资格但暂不排」的需求，再加列。

## 6. 状态与副作用

**`review_items.status` 四值**：

| 当前 | 动作 | 目标 | 副作用 |
|---|---|---|---|
| （无行） | 首次会话完成 + 资格满足 | `active` | 建行，`next_review_at` 按算法给出 |
| `active` | `pause` | `paused` | `auto_review_enabled = false`；**不删历史** |
| `paused` | `resume` | `active` | 重算 `next_review_at`（从当前时间起算，不补历史欠账） |
| `active` / `paused` | `archive` | `disabled` | 退出自动复习并归档；**不删内容与历史** |
| `disabled` | 重新启用 | `active` | 新建或复用行（需决策） |
| `active` | 提交复习且算法判定结束 | `completed` | 仅当算法有「毕业」概念时；否则一直是 `active` |

**三条不可违背的规则（PRD 明文）**：

1. **逾期不自动扣减掌握等级**。PRD §8.4：「未复习不等于已经遗忘，不应自动扣减掌握等级。」这是最容易被"聪明"实现违反的一条——任何「逾期 N 天降一级」的逻辑都违规。
2. **逾期不自动改日程**。PRD §8.4：「逾期后系统只生成重新安排建议，不自动改变用户日程。」见 §4。
3. **暂停或退出不删除内容与历史记录**。PRD §8.3 明文。

**副作用**：

| 动作 | 写入 |
|---|---|
| 提交复习 | `review_records` 插入；`review_items` 更新 `next_review_at` / `interval_seconds` / `ease_factor` / 可能 `status` |
| 暂停 / 恢复 / 归档 | 只改 `status` 与 `auto_review_enabled`；不动 `review_records` |
| 接受重排建议 | `next_review_at`；建议写 `review_reschedule_history`（缺表） |
| 共享复习证据 | 插 `review_shares`；**不改目标项目的 `review_items`** |

## 7. 错误映射

| 场景 | 变体 | HTTP | 备注 |
|---|---|---|---|
| 队列项不存在 / 非本人 | `NotFound` | 404 | |
| 对 `disabled` 项提交复习 | `Conflict` | 409 | 或允许（「临时复习一次」需决策） |
| 对 `paused` 项提交复习 | 200 | — | 建议允许：暂停的是自动排期，不是禁止复习 |
| 反馈值不属该内容类型的模板 | `Validation` | 422 | 如给「解题类」传 `easy` |
| 手动安排的日期在过去 | `Validation` | 422 | 或允许（补录历史复习）；需决策 |
| 接受已过期的重排建议 | `Conflict` | 409 | 建议本身有时效 |
| 重复提交同一 `reviewed_at` | `Conflict` | 409 | 幂等键问题，需决策 |

## 8. 事务边界

| 操作 | 事务 |
|---|---|
| 提交复习 | **必须单事务**：插入 record + 更新 item。分开会出现「有记录但下次日期没变」或反之 |
| 暂停 / 恢复 / 归档 | 单语句 |
| 接受重排建议 | 单事务：更新 `next_review_at` + 写延期历史（缺表时只能打日志） |
| 批量生成今日复习队列 | **不建队列**。今日复习是**查询**（`WHERE next_review_at < end_of_today AND status='active'`），不写 `scheduled_activities`——写的话每天会产生大量行，且用户改日程后要清理 |
| 共享复习证据 | 单事务：校验源 record 归属 + 目标 project_content 归属 → 插行 |

**并发**：提交复习用 `SELECT … FOR UPDATE` 锁队列项。若两个设备同时提交（手机 + 电脑），第二个会读到已更新的状态再算一次间隔——这是**正确**行为（两次真实复习都应计入），但要注意 `algorithm_version` 一致，否则两次用不同算法算间隔会产生不可解释的结果。

## 10. 实现状态与缺口

**已实现**：无。

**阻塞项（按解除顺序）**：

| # | 阻塞 | 影响 |
|---|---|---|
| 1 | **间隔算法未定**（PRD §18 第 9 项） | `scheduler.rs` 无从写起。三列（`interval_seconds` / `ease_factor` / `algorithm_version`）已预留但公式未定 |
| 2 | **反馈模板到间隔的映射未定** | 能收反馈，但无法据此算下次日期 |
| 3 | **ERD 缺两张表** | `review_policies`（三级策略）与 `review_reschedule_history`（延期历史）只有 TAD 概念定义。TAD 明确说「不能只保存当前日期而丢失延期历史」，所以后者不是可选 |
| 4 | **`ReviewShare` 语义未定**（ERD §12 第 7 项） | 表结构在，但 `share_type` 的两种值行为未定 |
| 5 | **依赖 M08 的错题模型** | `review_type=wrong_question` 无法落地 |
| 6 | **依赖 M05 的 session 事件** | 「首次会话完成后才有资格」需要 M05 触发；当前 M05 正式模型未设计 |
| 7 | 目录 `modules/review` 不存在 | 需新建 |

**建议的实现策略**：与 M06 同样的三段式。

1. **最小切片**：只做 `review_items` + `review_records` + 提交复习，算法用最简单的固定递增（如 `good` → ×2.5、`again` → 复位到 1 天，SM-2 简化版），`algorithm_version = 'sm2-lite'`。**这不需要等算法定稿**，因为 `algorithm_version` 列本来就是为「算法可演进」准备的。
2. 第二阶段接 `review_policies`（三级策略）与 `review_reschedule_history`（重排历史）。
3. 第三阶段做 `review_shares` 与错题队列。

**一个必须避免的陷阱**：不要因为「算法未定」就不做队列管理。PRD §8.3 的暂停/恢复/归档、§8.4 的逾期建议，这些**与算法无关**，可以先落地。反之，如果先实现算法而不做管理动作，用户会被一个无法暂停的自动队列绑架。
