# ADR-010 学习活动的时长、计时、删除与证据边界

**状态：** 已采纳（2026-11-27）
**范围：** `learning_sessions` 的时长生成与计时形态、删除语义、`learning_evidence` 的边界与权限、M02 `purge` 时的归属处理（D-20）、过渡表 `learning_records` 的迁移与下线；对应 ERD §12 第 4、5、8 项

## 背景

正式 `LearningSession` 契约一直卡在 6 个未决问题上（M05 §3 / §10）。它们互相牵制，必须一起定：

| # | 未决 | 牵制关系 |
|---|---|---|
| 1 | 时长怎么生成 | 决定 PATCH 是否允许改时长，进而决定要不要审计 |
| 2 | 计时形态（前端计时 / 后端 timer 表 / 补录） | 决定是否需要 `active_timers` 表与状态机 |
| 3 | 删除语义 | 决定聚合查询是否要过滤，进而决定所有统计口径 |
| 4 | 与 `/records` 的迁移与下线 | 决定过渡字段 `content` / `subject` 的映射 |
| 5 | 证据的存储与权限 | `LocalStorage` 是 stub，决定 v1 能开放哪些证据类型 |
| 6 | **D-20**：项目 `purge` 时「主要归属学习记录」删还是解挂 | 决定 `primary_project_id` 的外键行为 |

硬约束：

- PRD §16.2：**创建时间、实际发生时间、有效时长三个概念必须分开**。
- ADR-006：删除语义分层；已有软删对象只有 `learning_tasks` 一张。
- ADR-007 §6：软删是 `UPDATE`，**不触发** `ON DELETE CASCADE`，依赖行须服务层显式处理。
- 安全与AI约束 §3：AI 不可用时核心功能必须可用（本 ADR 不引入外部依赖）。

## 决策

### 1. 有效时长 = `min(用户上报, 区间时长)`，用户上报可选

| 输入 | 结果 |
|---|---|
| 只给 `started_at` / `ended_at` | `duration_minutes = ⌊(ended_at − started_at) / 60⌋` |
| 给区间 + `duration_minutes`（≤ 区间） | 采信用户上报（区间内有暂停，正常预期） |
| 给区间 + `duration_minutes`（> 区间） | **422**，message 明说「上报 180 分钟，但区间只有 60 分钟」 |

- `duration_minutes` 允许**小于**区间，禁止大于——上界由服务端算，下界不设（学 5 分钟也是学了）。
- PATCH 改 `started_at` / `ended_at` / `duration_minutes` 时走同一校验，**不引入「改时长必须留痕」的审计表**：PRD 没有要求，而事件表属 ADR-008 待补第 3 项（审计表尚未设计）。
- 为什么不用方案 A（完全忽略上报）：计时段内的暂停（接电话、走神）是真实存在的，强迫用户接受虚高时长会让所有统计偏高。
- 为什么不用方案 B（只校验不采信）：那等于「用户填的数字永远不被存」，填了也白填。

### 2. 计时形态：客户端计时 + 事后补录，**不建 `active_timers` 表**

| 形态 | 判定 | 理由 |
|---|---|---|
| ① 客户端本地计时，结束一次性提交起止时间 | ✅ 采纳 | 零服务端状态；崩溃丢的是前端内存，不是数据库 |
| ③ 事后补录（手填区间） | ✅ 采纳（同一端点） | 用户忘了计时是常态，补录必须是一等路径 |
| ② 后端存 timer 状态（`active_timers` 表） | ❌ 放弃 | 引入新表 + 新状态机 + 心跳/超时清理 + 「忘记停表」的脏数据；单用户场景收益极低 |
| ④ 混合 | ❌ 放弃 | ①+③ 已覆盖全部使用场景，② 的复杂度换不来额外能力 |

`created_source` 语义：

| 值 | 含义 | 谁能写 |
|---|---|---|
| `user` | 手动补录 / 手填 | 客户端（默认值） |
| `timer` | 计时器产出（客户端自报） | 客户端可声明——这是**自报字段不是安全边界**，伪造只影响自己的统计 |
| `imported` | 迁移脚本写入 | **API 拒绝**（传 `imported` → 422），只允许迁移 SQL 用 |

不提供 `start / pause / resume / stop` 端点：那四个动作在没有服务端状态时没有意义，端点存在反而会诱导后续做成 ②。

### 3. 删除语义：软删 `deleted_at`，软删对象从 1 张扩到 2 张

| 候选 | 判定 | 理由 |
|---|---|---|
| 物理删 | ❌ | 学习记录是**统计基础**。删一条 3 月的记录，3 月报表数字立刻变化，且误删不可恢复 |
| 加 `archived_at` 之类新词 | ❌ | 会造出第二套「退出列表」的机制，所有查询要写两个条件 |
| **复用 `deleted_at`** | ✅ | 与 `learning_tasks` 同一列名、同一过滤规则：`WHERE deleted_at IS NULL` |

**判据统一为两条，两条都满足才软删**：① 有下游引用（`review_records.learning_session_id`、M06 证据链、M11 聚合）；② 参与聚合统计。刻意不写「凡是事实表都软删」——那会把软删扩散成默认选项。

软删的连带规则（ADR-007 §6 的落地）：

| 关联 | 软删 session 时 |
|---|---|
| `session_projects` / `session_contents` / `task_sessions` | **保留**（软删是 `UPDATE`，不触发级联；恢复语义未开放也无所谓） |
| `learning_evidence.session_id` | **保留**（证据是独立资产，见决策 4） |
| 列表 / 详情 / 聚合 | 全部按 `deleted_at IS NULL` 过滤；软删后详情返回 404 |

**不开放恢复端点**：软删的目的是「统计可复现 + 误删可救」，救的方式是直接 SQL 或将来的管理端点。开放 `POST /restore` 会把「删除」变成两步操作，而 PRD 没有恢复需求。

### 4. 证据：owner 级独立资源，v1 只开放「文本 / 链接 / 测试结果」三类

| 维度 | 决定 |
|---|---|
| 归属 | `owner_id`；`session_id` **可空**（证据有独立价值：随手拍的错题截图不必挂在某次活动上） |
| 路径 | 独立资源 `/api/v1/evidence`，**不**挂在 `/learning-sessions/{id}` 下（可空的父资源不该出现在路径里） |
| v1 类型 | `note` / `link` / `test_result`；`code` / `image` / `file` **延后**到 storage 层落地 |
| 内容载体 | `note` / `test_result` 用 `description` 文本；`link` 用 `external_url` |
| 不进契约的字段 | `storage_key` / `mime_type` / `size_bytes`（无生产者，ADR-007 契约最小承诺） |
| 权限 | 只有「本人」一个维度。**不存在跨用户可见性**，因此 ERD §12 第 8 项的「证据跨项目可见性」在本项目里是个伪问题：所有数据同一 owner，跨项目不是隔离边界 |
| 删除 | 物理删除（无下游引用）；session 软删**不解挂**证据 |

「v1 只开三类」不是砍功能，而是把不可实现的部分（文件）明确划出契约：`LocalStorage` 是 stub，写着「支持上传图片」的契约只会变成 500。

### 5. D-20：项目 `purge` 时学习记录**保留并解挂**

| 外键 | `ON DELETE` | 效果 |
|---|---|---|
| `learning_sessions.primary_project_id` | `SET NULL` | 记录保留，只是不再归因到项目 |
| `session_projects.project_id` | `CASCADE` | 纯关联行，随项目消失 |
| `learning_evidence.session_id` | `SET NULL` | session 若将来被物理删，证据留着 |
| `task_sessions.task_id` / `session_id` | `CASCADE` | 纯关联行 |

理由：项目是**容器**，学习记录是**事实**。「我 3 月学了 40 小时」这个事实不该因为容器被删而消失；解挂后仍可按时间统计，损失的只是归因维度。这与 ADR-006「删容器不删事实」同一条原则——反过来（级联删记录）会让 `purge` 变成一次不可逆的数据销毁。

### 6. `/records` 的迁移与下线：新建表 + 一次性迁移 + 不双写

| 过渡字段 | 去向 |
|---|---|
| `title` | `learning_sessions.title` |
| `content` | `summary` |
| `duration_minutes` | `duration_minutes`（区间合成后仍校验 `min` 规则，天然成立） |
| `subject` | **并入 `summary` 前缀**（`科目：<subject>\n<content>`），不丢弃 |
| `created_at` | `created_at`；同时合成 `started_at = created_at`、`ended_at = created_at + duration`，`created_source='imported'` |

- **不双写**：单用户、无并发客户端，双写只会带来「两处数据不一致」的新问题。
- 下线时点：新端点全绿 + 前端切换后 `/records` 立即下线；`learning_records` 表在迁移验证后由单独 migration 删除（保留一版以便回滚）。
- 区间合成是**近似**：过渡记录没有真实起止时间，只能拿录入时间当发生时间。迁移脚本必须在 `summary` 末尾追加一行「由过渡记录迁移，时间区间为估算」，不假装精确。

### 7. ERD 增补列

`learning_sessions` 需补 3 列（ERD 原表缺时间戳与软删标记，与 PRD §16.2「创建时间必须独立保存」直接冲突）：

| 列 | 类型 | 说明 |
|---|---|---|
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | 录入时间（可能远晚于 `started_at`，补录场景） |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | |
| `deleted_at` | `TIMESTAMPTZ NULL` | 第二个软删对象（决策 3） |

## 放弃的方案

| 方案 | 放弃原因 |
|---|---|
| 后端 timer 表 + `start/pause/resume/stop` 端点 | 见表 2：新表 + 状态机 + 脏数据处理，收益不抵成本 |
| 完全忽略客户端上报时长（方案 A） | 暂停无法表达，统计系统性偏高 |
| 学习记录物理删除 | 统计不可复现 + 误删不可恢复 |
| 给学习记录加 `archived_at` | 第二套退出机制，所有查询写两个条件 |
| 证据作为 session 子资源 | `session_id` 可空，父资源不该在路径里 |
| v1 支持图片/文件证据 | storage 是 stub，契约写了就是 500 |
| `purge` 时级联删学习记录 | 等于把删项目做成数据销毁（决策 5 的反面） |
| 迁移时丢弃 `subject` | 丢的是用户手写的信息；并入 `summary` 成本为零 |

## 影响

- ERD §5.3 `LearningSession` 补 `created_at` / `updated_at` / `deleted_at`；§8.2 补本域 4 根外键的 `ON DELETE` 行为；§12 第 4、5、8 项标记已定
- Migration 顺序：`0005` 内容与标签 → `0006` 学习活动与证据（本项目把题库/成果/生活顺延）
- 契约：`/api/v1/learning-sessions`（含三个 `PUT` 整体替换子资源）+ `/api/v1/evidence`；**不提供**计时端点
- 所有聚合查询（M11）必须带 `deleted_at IS NULL`，这是容易漏的一条；实现时建议在 repository 层统一提供过滤后的视图而不是让每个调用方手写
- `/records` 进入下线倒计时，前端需排一次切换

## 待补齐（不在本轮）

1. 改时长 / 删记录的审计事件表（ADR-008 待补第 3 项）
2. 文件类证据（等 `infrastructure/storage` + 统一附件登记表）
3. 「有效学习日」判定算法与阈值（PRD §5.4，属 M11）
4. 计时器跨设备同步（多设备场景才会出现，当前不存在）
5. 软删记录的管理端恢复入口
