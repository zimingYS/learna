# ADR-005 学习规划状态枚举合并与模型补列

**状态：** 已采纳（2026-11-27）
**范围：** LearningProject 状态枚举、LearningTask、ProjectGoal

## 背景

TASK-API-02 逐实体核对 PRD 与 ERD 时发现三处基线不一致，其中两处是**模型缺口**（PRD 承诺的能力在 ERD 无字段承载），一处是**枚举冲突**：

| 编号 | 冲突/缺口 | PRD | ERD V1.0 |
|---|---|---|---|
| D-16 | 项目状态枚举 | §4.3「确认采用五种状态」：草稿 / 进行中 / 暂停 / 已完成 / 已归档 | §9 枚举建议：`active / paused / completed / archived / deleting`（无 `draft`、多 `deleting`） |
| D-05 | 任务可直接隶属阶段 | §4.5「任务可以直接隶属于阶段」 | `LearningTask` 仅有 `project_id`、`milestone_id`，无 `stage_id` |
| D-06 | 一个主要目标 + 多个子目标 | §4.5 | `ProjectGoal` 无主目标标记、无父子关系字段 |

契约设计阶段不能自行选择其一（会构成对已确认领域模型的擅自改动），故先列为待决策；2026-11-27 负责人逐项确认如下。

## 决策

### 1. 项目状态：合并六值（D-16）

`ProjectStatus = draft | active | paused | completed | archived | deleting`

- `draft` 取自 PRD（「已创建，尚未正式开始」）；
- `deleting` 取自 ERD（受控彻底删除流程的中间态，见 ERD §3.5 / §12.5）；
- **v1 只产生前五个值**，`deleting` 为预留：受控删除流程本身仍待决策（D-02），实现前不得产生该状态。

> **后续修正（ADR-006）：** `deleting` 现由 `POST /projects/{id}/purge` 事务内部写入并随事务结束消失，不再是「v1 不会出现的值」；「禁止常规写入」的约束不变。

### 2. 状态机边缘迁移（D-01）

| 边缘迁移 | 结论 |
|---|---|
| 暂停 → 已完成 | 允许 |
| 草稿 → 已归档 | 允许 |
| 已完成 → 暂停 | 拒绝（409），回退须 reopen → pause |

### 3. fixed 截止日期改期（D-04）

新增专用端点 `POST /api/v1/projects/{id}/extend-deadline`，请求体必带 `new_deadline_at` 与 `reason`，服务端写审计事件。`PATCH /projects/{id}` 对 `deadline_type=fixed` 的 `deadline_at` 变更返回 422；`none` / `soft` 仍走 PATCH。

### 4. 模型补列（D-05 / D-06）

| 表 | 新增列 | 约束 |
|---|---|---|
| `learning_tasks` | `stage_id UUID NULL`（FK → `stages.id`） | 与 `milestone_id` 可同时为空；同时存在时阶段须与里程碑所属阶段一致 |
| `project_goals` | `parent_goal_id UUID NULL`（FK → `project_goals.id`） | 自引用；同一项目内；**层级上限两层**（子目标不得再有子目标）；不得自引用或成环 |

说明：
- 补列后 PRD §4.5 的两项能力具备承载字段，不改变 ERD 其它已确认规则（计量归属、时间约束、删除策略均未动）。
- **ERD V1.0 正文未修改**：字段在本文档与契约中先行生效，待 ERD 升版（V1.1）时同步补入 §5.1 与索引建议；实现 Migration 前必须先完成 ERD 修订，避免文档与表结构脱节。
- **后续（2026-11-27）**：ERD 已升 V1.1，`project_goals.parent_goal_id`、`learning_tasks.stage_id`、`learning_tasks.deleted_at` 已补入 §5.1，项目状态枚举补 `draft`，索引建议补 `(project_id, stage_id)` / `(project_id, milestone_id)`。本限制解除，可进入 Migration 阶段。

## 后果

- 正面：PRD 承诺的「任务直挂阶段」「主/子目标」不再是空话；状态枚举同时容纳两个来源的语义，`deleting` 预留避免受控删除落地时二次改契约。
- 负面：`deleting` 在 v1 是「定义了但不会出现」的值，需在实现侧显式禁止写入；`parent_goal_id` 的两层限制需要服务层校验（数据库层不易表达）。
- 待补齐：ERD V1.1 修订、`learning_tasks` / `project_goals` 的 Migration（均不在本任务范围）。
