# ADR-007 状态迁移统一规则与契约最小承诺

**状态：** 已采纳（2026-11-27）
**范围：** Stage / Milestone / LearningTask 状态迁移、时间戳副作用、GoalStage 接口形态、列表默认序、JSONB 字段取舍、创建默认值

## 背景

契约设计阶段遗留 9 项细节决策（D-08、D-11、D-13、D-14、D-15、D-17、D-18、D-19、D-20）。逐项看是 9 个无关的参数问题，放在一起看是同一个判断标准在三个对象上的应用：

> **契约只承诺「当前有执行者」的能力**——没有生产者的字段不进契约，没有依据的读参数不开放，没有明文的状态边由一条统一规则推导而非逐条枚举。

由此得到的分布是：5 项的正确答案是「契约什么都不加」，4 项需要改变已有设计。

| 事实 | 后果 |
|---|---|
| PRD §4.4 的「可跳过、可提前进入、可返回」只明文约束 Stage | Milestone / Task 的合法迁移无依据，逐条枚举会得到两套互不一致的矩阵 |
| ERD 无状态历史表，`completed_at` 是唯一完成痕迹 | 「离开终态是否清空」直接决定「完成次数能否统计」 |
| ERD §5.1 在 `target_definition` 旁自注「关键字段应另设列」 | ERD 自己承认该 JSONB 是兜底，不是设计 |
| PRD §4.4「AI 可以生成阶段完成条件」是 `completion_rule` 的唯一生产者，AI 线（P0-③）未启动 | v1 写入的值没有任何代码会读——死字段 |
| ERD §7 给了 `LearningTask (project_id, status, priority)` 与 `(project_id, due_at)` 两条索引 | 任务排序**有**依据；真正无依据的是 ProjectGoal 与 Milestone |

## 决策

### 1. 状态迁移：一条规则替代两张矩阵（D-11 / D-18）

对 Stage / Milestone / LearningTask 统一适用：

1. **允许跳过中间态**：未完态可直接进入终态。
2. **允许向未完态回退**：终态可回到 `todo` / `pending` / `in_progress`。
3. **终态之间不直转**：`completed ↔ cancelled`、`completed → skipped`、`skipped → completed` 一律 409，须先回退（与 ADR-006 §3 拒绝 `achieved → cancelled` 同理）。
4. **同态提交幂等 200**：`PATCH {status: 当前值}` 与「动作落在已达目标态」均返回 200 且不改任何字段。
5. **时间戳副作用**：进入 `completed` 写 `completed_at = now`；离开 `completed` 置 NULL；`started_at` **首次写入后不再变更、也不清空**。

推导结果（枚举取自 ERD §5.1）：

| 资源 | 允许的迁移 |
|---|---|
| Milestone | `pending → in_progress / completed / skipped`；`in_progress → pending / completed / skipped`；`completed → pending / in_progress`；`skipped → pending / in_progress` |
| LearningTask | `todo → in_progress / blocked / completed / cancelled`；`in_progress → todo / blocked / completed / cancelled`；`blocked → todo / in_progress / completed / cancelled`；`completed → todo / in_progress`；`cancelled → todo / in_progress` |
| Stage（动作端点，另有准入） | `pending → active`；`pending/active → skipped`；`active → completed`；`completed/skipped → active`（`reactivate` 清空 `completed_at`） |

**为什么选「允许跳过」而不是严格线性**：任务的核心交互是打勾。若禁止 `todo → completed`，每次完成任务都要两次点击（先标进行中）——为一个没有依据的严格性付出确定的体验代价。PRD §4.4「不强制严格顺序」是支持依据。

**为什么 `started_at` 不清空**：它是「首次开始」的事实记录，清空后无任何替代来源；而 `completed_at` 是「当前是否处于完成态」的派生标记，保留会造出 `status=active` 却有 `completed_at` 的自相矛盾行，使任何完成量统计出错。

### 2. 显式接受的损失：完成次数不可统计

`completed_at` 离开终态即清空，ERD 无状态历史表，因此 **v1 无法回答「完成过几次」「曾于何时完成」**。

若将来需要，须新增 `stage_status_history` / `task_status_history`（事件表），这是模型层面的增量，不在 v1 范围内。此损失在此登记，避免后续误以为「达成时间可以统计」——与 ADR-006 §3 的目标达成时间损失属同类取舍。

### 3. JSONB 字段不进契约（D-08）

`stage.completion_rule`、`milestone.completion_rule`、`goal.target_definition` 三个 JSONB 字段：

- **DTO 不出现该字段**，客户端无法读写；DB 列保留可空、v1 恒为 NULL。
- 判断依据是「无生产者 + 无消费者」：唯一生产者是 AI（PRD §4.4），AI 线未启动；`completion_method` 已能表达「由谁确认完成」，v1 只会产生 `user`。
- **不选「暴露为自由 `object`」的理由**：一旦承诺「任意结构合法」，将来收窄为封闭 schema 就是破坏性变更；不进契约则未来的引入是纯增量。

### 4. GoalStage 以 goal 为主语整体替换（D-13）

```
GET /api/v1/projects/{pid}/goals/{gid}/stages      # 读关联
PUT /api/v1/projects/{pid}/goals/{gid}/stages      # 整体替换
    { "links": [ { "stage_id": "...", "contribution": "primary" } ] }
```

取消原单条 `PUT .../stages/{sid}` 与 `DELETE .../stages/{sid}`。

**理由**：`contribution` 是二值枚举（`primary / supporting`，ERD §5.1），这个关联的编辑形态是「选中一个目标 → 勾选它覆盖哪些阶段」。整体替换天然批量、天然幂等，端点从 3 个降为 2 个；单条操作需要 N 次往返，且前端要维护中间态。

**代价**：单条修改须发全量，存在「读后写覆盖」窗口。个人工具单用户无并发写，可接受；若将来出现协作场景，须改为 ETag 或逐条操作。

### 5. 列表默认序固定，不开放 `sort` 参数（D-14）

| 列表 | 默认序 | 依据 |
|---|---|---|
| 项目 | `updated_at DESC, id DESC` | ERD §7 `(owner_id, status, updated_at DESC)` |
| 路线 | `version DESC, id DESC` | ERD §7 `(project_id, version DESC)` |
| 阶段 | `sequence_no ASC, id ASC` | ERD §7 `(roadmap_id, sequence_no)` UNIQUE |
| 任务 | `priority DESC, created_at DESC, id DESC` | ERD §7 `(project_id, status, priority)` |
| 目标 / 里程碑 | `created_at ASC, id ASC` | **无索引依据**（全表扫，量级 < 50/项目） |

**不开放 `sort` 的理由**：需要白名单校验 + 索引匹配 + 稳定分页 tiebreaker 三项成本，而 v1 任务量级 < 200/项目，前端全量拉取本地排序即可覆盖真实需求。真实诉求（「今天该做什么」）是 `due_at` 范围**过滤**，不是排序。

### 6. 软删除不暴露、读参数收敛（D-15 / D-17）

- `deleted_at` **不出现在任何响应**，无 `include_deleted` 参数、无回收站、无 restore 端点。软删除是**数据留存**，不是产品功能。
- **连带规则（必须实现，否则出错）**：软删任务不计入列表、依赖环路检测、`DeletionConflict` 影响面计数、结构解挂范围。否则用户删阶段时会看到一个永远清不掉的计数。
- 项目列表**默认排除** `archived`，`include_archived=true` 覆盖；不引入多值 `status`（会破坏 `(owner_id, status, updated_at DESC)` 索引）。

### 7. 创建默认值取 PRD 的中位与枚举首值（D-19）

| 字段 | 默认 | 依据 |
|---|---|---|
| `project.importance_level` | 3 | PRD §5.1 明确 I3 = **普通** |
| `project.project_type` | `study` | 四枚举中唯一通用值，其余三值为其特化 |
| `project.deadline_type` | `none` | ERD 约束「none 时 deadline_at IS NULL」，最安全 |
| `project.status` | `draft` | PRD §4.3 |
| `task.priority` | 3 | 1–5 中位，不偏置调度 |
| `task.status` / `created_source` | `todo` / `user` | ERD 枚举首值 |
| `stage.status` / `milestone.status` | `pending` | ERD 枚举首值 |

### 8. D-20 移交 P1

「项目彻底删除时主要归属学习记录如何处置」依赖 `LearningSession`（P1，未设计）。v1 `purge` 只删规划域数据——学习记录尚不存在，无对象可处置。届时在 `PurgeProjectRequest` 增加字段即可，不破坏现有语义。**从本模块待决策清单移出**。

## 后果

**正面**
- 9 项收敛为 1 条判断标准 + 1 条迁移规则，Milestone / Task 不再各有一套矩阵。
- 契约表面收窄：移除 7 处 JSONB 属性、2 个 GoalStage 端点、不引入 `sort` 与 `include_deleted`；学习者不必为不存在的功能写代码。
- 打勾交互一次点击完成，且误操作可撤销。

**负面**
- **完成次数与曾完成时间不可统计**（§2），且回退后连「曾完成过」也不可追溯。
- GoalStage 整体替换有读后写覆盖窗口（§4），协作场景须改协议。
- 任务默认按 `priority DESC` 排序，当全部任务取默认值 3 时退化为创建序——这是「不设 `sort`」的必然结果，需在 UI 侧提示用户按截止日期过滤。

**待补齐**
- ERD V1.1 需记录：三处补列、§8 软删除表述收窄为「仅 LearningTask」、§9 项目状态枚举补至六值。
- `deleting` 状态只存在于 `purge` 事务内部，实现时必须显式拒绝外部写入（ADR-006 §2）。
- 契约落盘位置：`docs/接口契约/openapi.yaml`（1.4.0）、`docs/接口契约/设计记录/学习规划模块契约设计.md` §2.4 / §2.5 / §4.2 / §4.6 / §10.1、`docs/接口契约/接口清单.md` §4。
