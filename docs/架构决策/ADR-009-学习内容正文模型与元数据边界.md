# ADR-009 学习内容正文模型与元数据边界

**状态：** 已采纳（2026-11-27）
**范围：** `learning_contents` 的正文列、`body_format` 取值与渲染责任、`metadata` 的读写边界、出处链接与附件的落位；对应 ERD V1.2 §12 第 16 项

## 背景

ERD V1.2 §5.2 的 `LearningContent` 只有 `title` / `description` / `metadata` 三个文本载体，**没有正文列**：

| 现有列 | ERD 原意 | 能否承载「这个知识点到底讲了什么」 |
|---|---|---|
| `title` | 名称 | 不能，200 字符 |
| `description` | 摘要 | 不能，它的定位是列表展示与检索命中摘要 |
| `metadata` JSONB | 「仅放类型扩展属性」 | 不应，它是类型维度的补充属性，不是内容载体 |

M03 §10 把这条列为阻塞 3。若不先定，实现时必然出现「先塞 `metadata`，以后再迁」——那会造出一批结构不可枚举的历史数据，且全文检索、渲染、导出三处都要写兼容分支。

前置约束：

- `infrastructure/storage`（`LocalStorage`）仍是 stub，附件读写**当前不可用**。
- M09 成果域已有 `artifact_assets`（复数附件）与 `artifact_links`，附件在那里有归属。
- 前端是 Vue，渲染层可选「受限 Markdown 渲染器」，不需要后端产出 HTML。

## 决策

### 1. 正文入库：`body TEXT NULL` + `body_format VARCHAR(20) NOT NULL DEFAULT 'markdown'`

枚举只有两个值：`markdown` / `plain_text`。

| 候选方案 | 判定 | 理由 |
|---|---|---|
| **正文列 + 格式列**（采纳） | ✅ | 纯文本可 diff、可迁移；`tsvector` 可直接建在 `body` 上；渲染责任留在前端，后端不需要 Markdown 解析器 |
| 全塞 `metadata` JSONB | ❌ | 结构不可枚举，检索要写 `metadata->>'body'`，等于把列定义藏进字符串键 |
| 结构化 blocks（Notion 式 JSONB 数组） | ❌ | 拖拽式编辑器、block 级 diff、schema 演进全是自研成本；v1 没有这个需求 |
| 正文存对象存储（`storage_key` 指向 `.md`） | ❌ | 正文是**业务事实**不是附件：它要参与检索、排序、事务；对象存储不做事务，也没有 `tsvector` |
| 存渲染后的 HTML | ❌ | 存储型 XSS + 渲染结果无法回改（编辑器拿不回源文本）。见决策 6 |

`body` 允许为 `NULL`（只有标题的占位内容），提交空串归一为 `NULL`——避免 `''` 与 `NULL` 两种「空」并存导致渲染分支翻倍。

### 2. `description` 与 `body` 分工，且不互为兜底

| 列 | 上限 | 用途 | 列表接口是否返回 |
|---|---|---|---|
| `description` | 500 字符 | 摘要：列表条目、搜索结果、复用提示里的辨识信息 | 返回 |
| `body` | 100 000 字符 | 正文 | **不返回**（只有详情接口返回） |

- 列表不返回 `body` 不是优化而是契约：内容列表可能一次 100 条，正文各 100KB 会让响应到 10MB 量级。
- `description` 为空时**不得**自动截断 `body` 填充——那是派生值，派生值不入库（与「光照不持久化」同一条原则）。

### 3. `metadata` 在 v1 不对外暴露、不接受写入，DB 列恒为 `NULL`

| 维度 | 决定 |
|---|---|
| 读写 | 不出现在任何请求 / 响应 DTO 中 |
| DB | 列保留（ERD 已有），值恒 `NULL` |
| 校验 | 请求体出现 `metadata` 字段 → `422`（`extra="deny"` 语义），不静默忽略 |

理由与 D-08（`ProjectGoal.target_definition` v1 不暴露、恒 `NULL`）完全同构：**没有生产者的字段不进契约**（ADR-007 契约最小承诺）。等某个具体 `content_type` 有了明确扩展属性需求（如语言点的词性、音标），再按「一属性一决策」开放白名单键，而不是先开一个 JSONB 任意写。

推论：M03 §3 待决策 1 的「子类型放枚举还是 metadata」在 v1 里两处都不放——`content_type` 只保留 ERD 的三值（`knowledge_point` / `skill_point` / `language_item`），子类型整体延后。

### 4. 出处链接独立成列：`source_url VARCHAR(2048) NULL`

- 只允许 `http://` / `https://`，服务层校验（含大小写与大写协议头），不合法 → `422`。
- 单项而非多项：一个内容对应一个「主要出处」（教材章节、课程视频、文档）是最常见形态。多项链接属附件域（M09 `artifact_links`），不在内容域复制。
- 不放 `metadata`：它是有检索与展示价值的一等字段，不是类型扩展属性。

### 5. 附件边界：v1 内容**不带附件**，附件归 M09 / M05

| 位置 | 承载 |
|---|---|
| 内容正文 | `body`（文本，含代码块与公式的 Markdown 源文本） |
| 内容出处 | `source_url`（单链接） |
| 截图 / 文件 / 多链接 | **M09 成果档案**（`artifact_assets` / `artifact_links`），或 M05 学习证据 |
| 笔记类长文 | 就是 `body`，不另设表 |

三条理由：

1. **两处真相**：同一张截图既「属于内容」又「属于成果」时，删除任一侧都要问另一侧，级联链会绕成环。
2. **生命周期不同**：内容是长期资产，证据是一次活动的附件、成果是长期档案，三者的删除语义在 ADR-006 里本就分层。
3. **当前不可实现**：`LocalStorage` 是 stub，写着「支持附件」的契约只会变成 500。

解除条件：storage 层落地 **且** ADR-008 待补第 4 项（是否收敛统一附件登记表）有结论。届时新增独立资源（如 `content-assets`），**不**在 `learning_contents` 上加 `storage_key` 列。

### 6. 后端不净化、不渲染；契约承诺 `body` 是源文本

| 责任 | 归属 |
|---|---|
| Markdown → HTML 渲染 | 前端（受限渲染器，禁用 raw HTML 与 `javascript:`） |
| 存储与回显 | 原样存储、原样返回（不做 HTML 转义，否则代码块会被二次转义） |
| XSS 防护 | 渲染层。后端不产出 HTML，因此不引入净化解码链 |

- 未知 `body_format`（DB 被手工改动等）→ **按 `plain_text` 渲染**，不报 500。降级方向必须选「更安全」的一侧。
- `body_format` 切换（`markdown` → `plain_text`）不迁移正文内容，只切换解释方式；这是用户显式选择，不做自动探测。

### 7. `created_source` 沿用 ERD 的 `user / ai_confirmed / template`，与阶段的 `user / ai / template` 并存

| 域 | 取值 | 为什么不同 |
|---|---|---|
| 内容 | `user` / `ai_confirmed` / `template` | AI 产物**只在提案被接受后落库**（安全与AI约束 §2），落库那一刻即已确认，不存在「未确认的 AI 内容行」 |
| 阶段 | `user` / `ai` / `template` | `ai` 表示「AI 生成、尚在 draft 路线里」，路线本身未生效，因此有未确认态 |

两条词表语义不同，**不强行统一**：统一要么给内容造一个永不出现的 `ai` 值，要么把阶段已发布的 CHECK 改成 `ai_confirmed` 并重新解释 draft 路线里的未确认态。前者是无意义枚举值，后者要改已落地迁移 `0004` 且会让「未确认」失去表达。

## 放弃的方案

| 方案 | 放弃原因 |
|---|---|
| 正文塞 `metadata` | 见决策 1 |
| 结构化 blocks JSONB | 见决策 1 |
| 正文进对象存储 | 正文是业务事实，需要事务与检索 |
| 存渲染后 HTML | XSS + 源文本丢失 |
| 引入 `content_versions` 内容版本表 | v1 没有「多人协作 / 审核 / 回滚」需求；先做版本表会造出一张只写不读的表（同 M12「不写 ai_tasks」的判断） |
| 给 `metadata` 开通用白名单 | 白名单本身要有人维护；没有生产者的键开了就是第二个垃圾抽屉 |
| 内容附件列（`storage_key`） | 见决策 5 |

## 影响

- ERD §5.2 `LearningContent` 补 3 列：`body TEXT NULL`、`body_format VARCHAR(20) NOT NULL DEFAULT 'markdown'`、`source_url VARCHAR(2048) NULL`；同步修订 §12 第 16 项状态
- Migration 顺序不变（`0005` 内容与标签），但 `0005` 必须按本 ADR 建列与 CHECK：`body_format IN ('markdown','plain_text')`、`source_url` 长度上限
- 契约：详情接口返回 `body` / `body_format` / `source_url`；列表接口**不返回** `body`；请求体出现 `metadata` → `422`
- 全文检索：后续可在 `body` 上建 `GIN(to_tsvector(...))`，本轮不做（检索口径属 M11）
- 前端渲染器选型成为可验证项：必须有「禁 raw HTML」选项，否则本 ADR 的 XSS 结论不成立

## 待补齐（不在本轮）

1. 富文本 / 结构化 blocks 的引入时机（若引入，`body_format` 加 `blocks` 值并为 `body` 换成 JSONB 列，不混用）
2. 内容版本历史（需要「谁改了什么」的审计需求出现时再做）
3. 内容附件（等 storage 落地 + ADR-008 待补第 4 项）
4. `content_type` 子类型的枚举扩张或白名单键（等真实使用场景）
5. `body` 的全文检索与相似度阈值调优（M11 分析域）
