# ADR-008 模型缺口补齐与新增域边界

**状态：** 已采纳（2026-11-27）
**范围：** ERD V1.2 新增的 27 张表与 2 个列：项目调度配置与事件、内容标签、复习策略与延期历史、题库与练习、实践成果档案、生活记录与数据授权

## 背景

模块设计文档（M01–M12）逐模块核对 PRD 与 ERD 时，发现 6 处「PRD 明文要求、模型里没有对应表或列」的缺口：

| 模块 | 缺口 | 原本的状态 |
|---|---|---|
| M02 | `theory_enabled` / `practice_enabled` | PRD §6.1 硬要求，ERD 无列 |
| M02 | 临时标记、投入保障、项目事件 | 仅 TAD §3.10 有字段建议，ERD 无表 |
| M03 | 内容标签 | PRD §6.3 要求，ERD 无表（TAD §3.3 有实体名） |
| M07 | 复习策略、延期历史 | 仅 TAD §3.6 有实体名，ERD 无表 |
| M08 | 题库与练习全域 | ERD 一张表都没有 |
| M09 | 实践成果档案全域 | 仅 TAD §3.8 有字段建议 |
| M10 | 生活记录与 AI 数据授权 | ERD 一张表都没有 |

这些不是「以后再说」的增强项：`theory_enabled` 决定 M03 / M05 的实践类记录如何归类，M08 / M09 / M10 缺表意味着对应模块无法写 Migration。V1.1 已把「先出 ERD 再写 Migration」定为纪律，因此这一轮必须先补模型。

## 决策

### 1. 补不补，看「有没有人生产」，不看「PRD 提没提」

| 判定 | 处理 | 例子 |
|---|---|---|
| PRD 明文要求 + 有明确生产者 | **建表 / 补列** | 标签（用户打标）、投入保障规则（用户设定）、错题状态（练习产生） |
| TAD 只有概念名、无字段定义 | **按 PRD 反推字段**，不照抄概念 | 题库 10 张表、成果 4 张表 |
| PRD 只写「等」字，未列举 | **不建**，留在 §12 待补 | 身体数据的「体重等」→ 只落体重，不加 JSONB 兜底 |
| 派生值（可由原始事实算出） | **不建表** | 投入达标进度、未达标风险、掌握快照 |

这条与 ADR-007「契约只承诺当前有执行者的能力」是同一判断在模型层的应用：**没有生产者的字段不进模型**。

### 2. 27 张表怎么分域

| 域 | 表数 | 边界 |
|---|---|---|
| 项目调度配置与事件（§5.6） | 3 | 项目级配置，不进路线结构：改的是调度权重与可追溯性 |
| 内容标签（§5.2） | 2 | 只用于内容；题目↔知识点、成果↔技能点各有专表，不共用 |
| 复习策略与延期历史（§5.4） | 2 | 策略是配置（可覆盖），延期历史是事实（只追加） |
| 题库与练习（§5.7） | 11 | 题目、版本、选项、素材、知识点、题组、练习、作答、错题、审核 |
| 实践成果（§5.8） | 4 | 成果、附件、外链、技能点关联 |
| 生活记录与授权（§5.9） | 5 | 四类记录 + 授权表 |

### 3. 五个必须记住的设计取舍

**(1) `ProjectEvent` 与审计表的外键方向相反。**
`project_events` 是**业务可追溯**记录，随项目 `purge` 级联删除（`ON DELETE CASCADE`）。审计事件属独立审计表（尚未设计），**不得有指向业务表的外键**——否则 `purge` 会把审计一起删掉，审计形同虚设。这两类表看着都叫「历史」，语义相反。

**(2) 选项与作答指向「版本」，不指向「题目」。**
`QuestionOption` 挂 `QuestionVersion`，`PracticeAnswer` 锁 `question_version_id`。题目可修订，历史作答不能因修订而改变判分依据——否则用户回看三个月前的错题，看到的题干与当时不同。

**(3) `PracticeAnswer.graded_by` 是产品规则的最小实现。**
PRD §9.3 要求「AI 评分必须标明为辅助结果」。只有 `score` 字段时前端无法区分「AI 给的 3 分」与「我给的 3 分」，这条规则就落空。四个取值 `auto` / `self` / `ai_assisted` / `user_corrected` 是这条需求的下限，不是可选项。

**(4) 生活记录建模选「四张类型表」，且不允许被反向引用。**
四类记录字段差异是「四种不同的东西」，不是同一实体的可选属性；JSONB 化会让「体重必须 > 0」退化为应用层校验，统计也要写 `payload->>'weight'`。同时硬性禁止其他模块有指向生活表的外键——否则「不开启生活模块」会变成「数据库不完整」。

**(5) 不新增软删除对象。**
延续 ADR-006：新增 27 张表**全部不设 `deleted_at`**。题库用 `archived_at` 退出列表、错题用 `status` 表达处置、成果与关联行物理删除。软删对象仍只有 `learning_tasks` 一张。

### 4. 对 TAD 的两处收窄

| TAD 原设想 | V1.2 处理 | 理由 |
|---|---|---|
| `Artifact.asset_id`（单个附件） | 拆成 `ArtifactAsset` 复数表 | PRD §10.2「运行截图、图片和文档」是复数 |
| `Artifact.external_url`（单个链接） | 统一走 `ArtifactLink` | 保留单值会出现「一个链接在 artifact 表、另一个在 links 表」的两处真相 |

## 放弃的方案

| 方案 | 放弃原因 |
|---|---|
| 题库用「题目表 + 答案 JSONB」两列解决 | 选项需要排序与逐项正确性判断，JSONB 里做等于把 DB 约束换成应用层校验；且无法按选项统计 |
| 生活记录用一张主表 + JSONB（路线 B） | 见决策 3(4)；PRD §13.1 的分析本就按维度查询，不需要混排 |
| 为「体重等」预留 JSONB 扩展槽 | ADR-007 同一理由：没有生产者的字段不进模型 |
| 给新增表统一加 `deleted_at` | 会引入 27 处查询过滤，且与 ADR-006 的分层原则冲突 |
| 建统一 `stored_assets` 登记表 | 现有 `LearningEvidence` 已是 `storage_key` 内联形态，现在收敛要连带改造它；留作 §12 第 13 项 |

## 影响

- ERD 由 26 张表扩到 **53 张表**，业务上下文由 6 个扩到 **9 个**（新增题库与练习、成果、生活记录与授权）
- 契约层（`openapi.yaml`）**不受影响**：本轮只补模型，D-20 之外的契约决策未变；M08 / M09 / M10 的接口仍未设计
- Migration 顺序随之明确：`0004` 规划域 → `0005` 内容与标签 → `0006` 题库 → `0007` 成果 → `0008` 生活记录（生活域必须最后，且可整体不做）

## 待补齐（不在本轮）

1. 9 种题型的 `answer_payload` JSON Schema
2. 「有效学习日」的判定算法与阈值（PRD §5.4 要求 AI 评估 + 用户可纠正）
3. 审计事件表（设计时不得有指向业务表的外键）
4. 是否收敛统一附件登记表
5. 成果是否允许无项目归属（当前定为 `NOT NULL`）
6. 生活记录的其他身体指标（体脂率、围度等）
