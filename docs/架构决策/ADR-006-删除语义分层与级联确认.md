# ADR-006 删除语义分层与级联确认

**状态：** 已采纳（2026-11-27）
**范围：** LearningProject / ProjectGoal / Roadmap / Stage / Milestone / LearningTask / GoalStage / TaskDependency

## 背景

契约设计阶段遗留 6 项删除决策（D-02、D-03、D-07、D-09、D-10、D-12）。逐项看是 6 个独立问题，放在一起看是同一个问题的 6 个切面：

| 事实 | 后果 |
|---|---|
| ERD §8 只有一句「Stage / Milestone / Task 软删除或取消，保留执行历史引用」 | 未区分「草稿规划」与「执行中结构」，也没说任务是否随之消失 |
| ERD §5.1 的字段表**没有任何表**列出 `deleted_at`（§5 开头只说「需要软删除的表额外包含」） | 「软删除」目前只是概念，落成 DDL 需补列 |
| ERD §8.1 的彻底删除流程第 7 步要处置 `LearningSession.primary_project_id` | LearningSession 属 P1、尚未设计，v1 无对象可处置 |
| ERD §8 只保护 superseded 路线，未提 draft 路线 | 草稿路线能否删除无依据 |

若逐项单独决策，会出现「删阶段是物理删、删里程碑是软删、删任务是第三种」的分叉。因此先立分层原则，再让各项归位。

## 决策

### 1. 四层删除语义（核心）

删除语义由「该对象**是否已参与执行**」决定，不由对象类型决定：

| 层 | 判据 | 对象 | 语义 | 理由 |
|---|---|---|---|---|
| L1 编辑区 | 容器未生效（`draft`） | draft 项目、draft 路线及其下 stage / milestone | **物理删除** | 从未参与执行，无历史可损；软删只会带来全表 `deleted_at` 过滤成本 |
| L2 已生效结构 | 容器已 confirm | active / superseded 路线内的 stage / milestone | **不提供删除** | 结构是承诺；调整意图用状态动作（skip）表达 |
| L3 原子执行单元 | 自身承载 `completed_at` | LearningTask | **软删除**（唯一软删对象） | 执行历史必须保留可引用 |
| L4 成果 | 达成事实 | achieved 目标、completed / archived 项目 | **禁止删除** | 删除后不可追溯；用状态/归档替代 |

### 2. 项目删除双轨（D-02a / D-02b / D-03）

| 端点 | 准入 | 行为 |
|---|---|---|
| `DELETE /projects/{id}` | 仅 `status=draft` | 单事务级联物理删除 goal / roadmap / stage / milestone / task / goal_stage / dependency |
| `POST /projects/{id}/purge` | 任意状态 | 请求体 `confirm_name` 须与项目 `name` 完全一致（否则 422）→ `status=deleting` 加行锁拦并发写 → 同上事务级联 → 删除项目行 |

- **D-03 合并**：草稿项目不设「无子数据」前置条件——草稿子数据均为编辑中空壳。
- **为何不做 `DELETE ?force=true`**：确认体需要项目名（可能含特殊字符，放 query 不优雅）；且该端点是将来承载「学习记录是否一并删除」（D-20）的位置，用动作端点便于加字段而不破坏 DELETE 语义。
- **`deleting` 的定位修正**：ADR-005 记为「v1 不产生」，现修正为「只由 `purge` 事务内部写入、随事务结束消失、不对外持久可见」。任何常规写入（PATCH / 动作端点）置 `deleting` 一律拒绝，避免僵尸态。

### 3. 目标删除与回退（D-07a / D-07b）

- **删除**：物理删除 + 同事务删 GoalStage 关联行。`achieved` 返回 409（成果保护）；`active` / `cancelled` 允许（「建错了」/「不做了」）。
  **删主目标时子目标一并删除**（有子目标须 `?cascade=true`，否则 409 带 `impact.goals`）。**不采用**「子目标 `parent_goal_id` 置 NULL」——那会把子目标升格为第二个主目标，直接破坏 D-06「每项目最多一个主目标」。此补正于 2026-11-27 核对时落地（原文只写了「删 GoalStage 关联行」，未覆盖子目标处置）。
- **回退**：允许 `achieved → active`、`cancelled → active`；拒绝 `achieved → cancelled`（须先回 active，保留判定的两步痕迹）。
- **已知损失**：ERD `ProjectGoal` 无 `achieved_at`，v1 也不补。因此「何时达成」不可追溯，回退后连「曾达成过」也不可追溯。这是为换取「零补列 + 无时间戳清理逻辑」而显式接受的成本；若后续需要达成时间统计，须补列并另立决策。

### 4. 级联确认形态（D-21）

带子项的删除**默认 409**，`data` 返回影响面；调用方显式追加 `?cascade=true` 才执行。

```
DELETE /projects/{pid}/roadmaps/{rid}/stages/{sid}
→ 409 { "data": { "impact": { "milestones": 3, "tasks": 7 }, "hint": "..." } }
DELETE .../stages/{sid}?cascade=true
→ 200 { "data": null }
```

选它而不选「静默级联」或「有子项一律拒绝」：前者影响面不可见，后者让草稿重排（删一个阶段要先手工删 3 个里程碑和 7 个任务）不可用。这是 ERD §8.1 第 3–4 步「展示影响范围 + 二次确认」的轻量落地，**不需要** `deleting` 中间态。

级联范围内的固定动作：stage / milestone **物理删除**，其下任务**解挂保留**（`stage_id` / `milestone_id` 置 NULL），goal_stage 关联行删除。解挂由服务层显式执行 + DB `ON DELETE SET NULL` 兜底；**已软删的任务同样会被解挂**（外键不看 `deleted_at`）——若把这两根外键写成 `RESTRICT`，删阶段会因一条用户看不见的软删任务而外键违约（500 而非语义正确的解挂）。

**边界例外**：项目级删除（`DELETE` 草稿 / `purge`）会连带删除任务行——任务 `project_id` 为 NOT NULL，无法脱离项目存在。因此「任务永不随结构消失」的准确表述是「不随**上层结构**（路线 / 阶段 / 里程碑）消失」，项目本身是任务的归属根，不在保护范围内。

### 5. 409 携带结构化详情（D-22）

`接口契约/README.md` §4 规定「失败时 `data` 为 `null`」。删除影响面需要结构化返回，故只对**删除类端点的 409** 开一处明文例外（`DeletionConflictEnvelope`），其余 409 不变。不新增 `details` 字段、不扩通用错误信封。

### 6. 随原则推导出的准入规则（无独立编号）

| 规则 | 依据 |
|---|---|
| `superseded` 路线及其 stage / milestone **全程只读**（写操作 409） | ERD §8「保留路线历史」的唯一保障 |
| 阶段状态动作（start / complete / skip / reactivate）要求**所属路线 active** | 与「删除仅限 draft 路线」互斥 → skip 与 delete 不构成二选一 |
| 里程碑删除仅限 draft 路线，无 `cascade` 参数 | 任务解挂即可，不存在需要级联的子项 |
| 路线版本号取 `MAX(version)+1`，草稿删除后允许空档复用 | 空档不承载已确认历史 |

## 后果

**正面**
- 6 项决策收敛为 1 条原则 + 3 处例外，后续新模块（学习内容、复习、证据）可直接套用四层。
- 软删对象从「3 张表」降为「1 张表」（`learning_tasks`），ERD V1.1 补列从 3 个减到 1 个，查询过滤逻辑也只需实现一处。
- 级联影响面可被用户看见，且不需要 `deleting` 中间态与后台清理任务。

**负面**
- 目标达成时间不可追溯（§3）。
- 项目级删除会连带删除其下任务（含已 `completed` 的），这是「项目是归属根」的必然结果；想保留执行历史只能归档而非删除。
- `purge` 在 v1 只删规划域数据，"彻底"一词名不副实，需在 UI 文案与文档中明确（D-20 承载未来扩展）。
- `deleting` 成为「只存在于事务内部」的状态值，实现时必须显式拒绝外部写入，否则会造出无法恢复的项目行。
