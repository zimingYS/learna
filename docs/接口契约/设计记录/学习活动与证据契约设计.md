# 学习活动与证据契约设计（TASK-API-04）

**范围：** LearningSession、SessionProject、SessionContent、TaskSession、LearningEvidence
**依据：** PRD §11.2（学习活动记录）、§11.3（每日学习时间）、§15（数据删除）、§16.2（计划/实际/创建时间分离）；ERD V1.2 §5.3（五实体）、§8.3（活动域外键行为）、§12 第 4/5/8 项；`接口契约/README.md`（全局规范）；ADR-006 / ADR-007 / ADR-010

## 1. 领域实体与不变量

### 1.1 LearningSession（学习活动）

| 维度 | 内容 | 依据 |
|---|---|---|
| 字段 | title（可空）、activity_type、started_at、ended_at、duration_minutes、summary / what_done / problems / next_steps、created_source、created_at、updated_at、deleted_at | ERD §5.3 + ADR-010 §7（补 3 列） |
| 不变量 | `ended_at >= started_at`；`duration_minutes >= 0` 且 `<= ⌊(ended_at − started_at)/60⌋`；`primary_project_id` 非空时项目 owner 必须一致 | ERD §5.3；ADR-010 §1 |
| 三个时间 | `created_at` 录入时间（补录可远晚于实际）/ `started_at`-`ended_at` 实际发生 / `duration_minutes` 有效时长 | PRD §16.2 |
| 状态 | **无状态机**。写入即事实，不做 `draft / completed` 流转 | M05 §6 |
| 删除 | 软删（`deleted_at`）；软删后列表、详情、聚合全部排除 | ADR-010 决策 3（D-33） |
| 归属 | `owner_id` → 当前用户；`primary_project_id` 可空（项目被 `purge` 后解挂） | ERD §8.3；D-20 |

### 1.2 SessionProject（关联项目，只存 related）

| 维度 | 内容 | 依据 |
|---|---|---|
| 字段 | session_id、project_id、relation_role、created_at | ERD §5.3 |
| 不变量 | `UNIQUE(session_id, project_id)`；所有项目属同一 owner；**不含 primary** | ERD §5.3「更推荐只保留 `primary_project_id` 作为权威字段」 |
| 写入规则 | `relation_role` **恒写 `related`**；主要项目只存在于 `learning_sessions.primary_project_id` | 双重事实会分叉（M05 §5 已指出 ERD 的这处冗余） |

### 1.3 SessionContent（活动关联内容）

| 维度 | 内容 | 依据 |
|---|---|---|
| 字段 | session_id、content_id、contribution_type（`primary` / `covered` / `practiced`）、note | ERD §5.3 |
| 不变量 | 复合主键 `(session_id, content_id)`；内容与 session 同 owner | ERD §5.3 |
| 关系形态 | 整体替换（`PUT`），不做逐条增删 | §4.2 |

### 1.4 TaskSession（任务贡献分摊）

| 维度 | 内容 | 依据 |
|---|---|---|
| 字段 | task_id、session_id、contribution_minutes、note | ERD §5.3 |
| 不变量 | 复合主键 `(task_id, session_id)`；**同一 session 的分摊总和 ≤ `duration_minutes`**（服务层，跨行聚合 CHECK 表达不了）；任务必须属于该 session 的 `primary_project_id` 或某个 related 项目 | ERD §5.3；M05 §5 |
| 语义 | 分摊只是归因，**不累加成第二个时长** | ERD §5.3 明文 |

### 1.5 LearningEvidence（学习证据）

| 维度 | 内容 | 依据 |
|---|---|---|
| 字段 | evidence_type、title、description、external_url、created_at | ERD §5.3 + ADR-010 §4（`storage_key` / `mime_type` / `size_bytes` v1 不进契约） |
| 类型（v1） | `note` / `link` / `test_result` | ADR-010 §4 |
| 不变量 | `note` / `test_result` 必须有 `description`；`link` 必须有 `external_url`（仅 http(s)） | §5 |
| 归属 | `owner_id`；`session_id` **可空** | ADR-010 §4 |
| 删除 | 物理删除（无下游引用）；session 软删**不解挂**证据 | ADR-010 §4 |
| 与成果的区别 | 证据是「这次学习留下了什么」，成果是「长期档案」（M09，PRD §10.2） | M05 §1 |

## 2. 状态与生命周期

### 2.1 无状态机，只有两个生命周期事件

| 事件 | 触发 | 效果 |
|---|---|---|
| 创建 | `POST /learning-sessions` | 写主表 + 三类关联行（单事务） |
| 软删 | `DELETE /learning-sessions/{id}` | `deleted_at = now()`；关联行与证据保留；重复删除幂等 200 |

**不提供**「进行中 / 已结束 / 已取消」之类的状态：那会让「一次活动是否结束」变成可编辑的状态，而它本来就是由 `ended_at` 表达的客观事实。

### 2.2 `activity_type` 五值（ERD）

`theory` / `practice` / `review` / `mixed` / `other`，默认 `mixed`。

- 与 M04 `ProjectType`（项目性质）不是一回事：项目是长期方向，活动是这一次干了什么。
- `review` 表示「这次活动主要是复习」，**不代表**已写入 M07 复习队列（复习状态归 M07）。

### 2.3 `created_source` 三值（ADR-010 §2）

| 值 | 语义 | 可写性 |
|---|---|---|
| `user` | 手动补录 / 手填 | 客户端可传（默认） |
| `timer` | 计时器产出 | 客户端可声明（自报字段，非安全边界） |
| `imported` | 迁移脚本 | **API 传即 422** |

## 3. 资源路径决策

| 资源 | 路径 | 为什么 |
|---|---|---|
| 学习活动 | `/api/v1/learning-sessions` | 顶层；一次活动可以关联多个项目，挂在 `/projects/{id}` 下会让「主要项目」变成唯一归属 |
| 三类关联 | `/learning-sessions/{id}/{contents\|projects\|tasks}` | 关联行的生命周期完全从属于 session，且**不需要独立 id**（复合主键） |
| 证据 | `/api/v1/evidence` | `session_id` 可空 → 父资源不该出现在路径里；证据还能独立存在（随手截图） |

**只提供 `PUT` 不提供 `GET`**（三类关联）：详情接口已经把三组关联内联返回，再开 `GET` 是同一份数据的第二条路径。`PUT` 的响应直接回替换后的集合，前端一次往返即可渲染。

## 4. 接口总表

### 4.1 学习活动

| 方法 | 路径 | 要点 |
|---|---|---|
| GET | `/learning-sessions` | 过滤 `primary_project_id` / `content_id` / `activity_type` / `from` / `to`；分页；排序 `started_at DESC, id DESC`；不含软删 |
| POST | `/learning-sessions` | 主表 + 关联一次提交（`related_project_ids` / `contents` / `tasks` 均可选）；时长按 §2 规则生成 |
| GET | `/learning-sessions/{session_id}` | 详情，内联 `related_project_ids` / `contents` / `tasks` |
| PATCH | `/learning-sessions/{session_id}` | 三态；改时间或时长走同一校验；**不接受** `created_source` / `owner_id` |
| DELETE | `/learning-sessions/{session_id}` | 软删，幂等 200 |

`from` / `to` 过滤 `started_at` 区间（半开区间 `[from, to)`），用于「本月学了什么」这类查询；不提供按 `created_at` 过滤（那是录入时间，对统计无意义）。

### 4.2 关联整体替换（三个 `PUT`）

| 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|
| PUT | `/learning-sessions/{id}/contents` | `{items: [{content_id, contribution_type, note?}]}` | 替换后的 `items` + `total` |
| PUT | `/learning-sessions/{id}/projects` | `{project_ids: [uuid]}` | 替换后的 `project_ids` |
| PUT | `/learning-sessions/{id}/tasks` | `{items: [{task_id, contribution_minutes, note?}]}` | 替换后的 `items` + `total` |

- 传空数组 = 清空该组关联（幂等）。
- `contents` 里重复 `content_id` → 422；`project_ids` 含主要项目 → 422（主要项目由主字段表达，不重复出现在 related 里）；`tasks` 分摊总和超时长 → 422。
- 为什么整体替换而不是 `POST` / `DELETE` 逐条：一次活动关联的内容通常一次选完，逐条增删会让前端维护差集，且失败时容易留下半成品（与 GoalStage 同构）。

### 4.3 证据

| 方法 | 路径 | 要点 |
|---|---|---|
| GET | `/evidence` | 过滤 `session_id` / `evidence_type` / `from` / `to`；分页；排序 `created_at DESC, id DESC` |
| POST | `/evidence` | `{session_id?, evidence_type, title?, description?, external_url?}` |
| GET | `/evidence/{evidence_id}` | 详情 |
| DELETE | `/evidence/{evidence_id}` | 物理删除，幂等 200 |

**不提供 `PATCH`**：证据是快照（当时的笔记 / 链接 / 测试结果），改它就等于换一条证据。要改先删后建，语义清晰且不产生「证据被悄悄改写」的问题。

## 5. 认证与错误码

所有端点要求 `Bearer JWT`；归属校验写进 SQL `WHERE … owner_id = $n`，越权与不存在同为 404。

| 场景 | HTTP / code | 备注 |
|---|---|---|
| session / evidence 不存在、非本人、已软删 | 404 `NOT_FOUND` | 软删对客户端表现为「不存在」 |
| `ended_at < started_at` | 422 | |
| `duration_minutes` 为负 | 422 | |
| `duration_minutes` > 区间分钟数 | 422 | message 带两个数：「上报 180 分钟，但区间只有 60 分钟」 |
| PATCH 无任何字段 | 422 | `no fields to update` |
| `primary_project_id` / `related_project_ids` 含他人项目 | 404 | 不区分「不存在」与「不是你的」 |
| `contents` 含他人内容 | 404 | |
| `contents` 重复 `content_id` | 422 | |
| `related_project_ids` 含 `primary_project_id` | 422 | 主要项目不重复出现在关联里 |
| `tasks` 的任务不属于该 session 的任何关联项目 | 422 | 跨三表校验 |
| 分摊总和 > `duration_minutes` | 422 | |
| `created_source = imported`（API） | 422 | ADR-010 §2 |
| 证据 `note` / `test_result` 缺 `description` | 422 | |
| 证据 `link` 缺 `external_url` 或非 http(s) | 422 | |
| 证据 `evidence_type` 为 `code` / `image` / `file` | 422 | v1 未开放（storage 未落地，ADR-010 §4） |
| 重复删除同一 session / evidence | **幂等 200** | |

## 6. 删除语义

| 资源 | 行为 |
|---|---|
| session | 软删 `deleted_at`；三类关联与证据保留；列表 / 详情 / 聚合全部按 `deleted_at IS NULL` 过滤 |
| session 的三类关联 | 随 session 物理删除时 `CASCADE`（ERD §8.3）；软删时不触发 |
| evidence | 物理删除；`session_id` 指向软删 session 时保持原值 |

**聚合的红线**：M11 的所有统计（日 / 周 / 月学时、连续学习天数）必须带 `deleted_at IS NULL`。漏一处就会出现「日报与月报对不上」，且极难排查——建议实现时在 repository 层提供已过滤的查询函数，而不是让每个调用方手写条件。

## 7. 事务边界

| 操作 | 事务 | 说明 |
|---|---|---|
| 创建 session | **必须单事务** | 主表 + `session_projects` + `session_contents` + `task_sessions`；任一归属校验失败整体回滚，否则会出现「有活动没关联」 |
| 三类 `PUT` 替换 | **必须单事务** | 删旧关联 → 校验新关联 → 插入；分两步会在失败时留下空关联 |
| PATCH session | 单语句（条件更新带 `WHERE id AND owner_id AND deleted_at IS NULL`） | 时长校验先用 `SELECT … FOR UPDATE` 取当前区间 |
| DELETE session | 单语句 `UPDATE … SET deleted_at` | 不碰关联行（ADR-007 §6） |
| 创建证据 | 单语句 | v1 无文件上传，因此没有「对象存储不进事务」的三段式问题 |
| 删除证据 | 单语句 | 同上 |

## 10. 决策记录

### D-30 过渡字段 `content` / `subject` 的去留（2026-11-27）

`content` → `summary`；`subject` **并入 `summary` 前缀**（`科目：<subject>\n<content>`），不丢弃。新模型不保留自由文本 `content` 字段——正文归 `summary`，结构化描述归四段式。

### D-31 四段式描述字段（2026-11-27）

沿用 ERD 的 `summary` / `what_done` / `problems` / `next_steps`，**四个字段全部可空、全部暴露**，创建时不要求「至少填一个」。
理由：补录场景里用户常常只记得时长；强制填写会让「记录」变成「写作文」，最终结果是用户不记。PRD §11.2 说的是「结构化字段和简短备注」，没有必填要求。

### D-32 时长生成规则（2026-11-27）

`duration_minutes = min(用户上报, ⌊(ended_at − started_at)/60⌋)`；用户上报可选，超区间 → 422。详见 **ADR-010 §1**。

### D-33 删除语义（2026-11-27）

软删 `deleted_at`；软删对象集合从 `learning_tasks` 扩到 `learning_sessions` 两张。判据：有下游引用 + 参与聚合。详见 **ADR-010 §3**。

### D-34 与 `/records` 的共存与迁移（2026-11-27）

新建表 + 一次性迁移脚本 + **不双写**；`/records` 在新端点全绿且前端切换后下线，`learning_records` 表随后由单独 migration 删除。字段映射与「区间合成属估算」的标注见 **ADR-010 §6**。

### D-35 计时形态（2026-11-27）

客户端本地计时 + 事后补录，同一端点提交；**不建 `active_timers` 表**、不提供 `start/pause/resume/stop` 端点；`created_source` 由客户端声明 `user` / `timer`，`imported` 仅迁移使用。详见 **ADR-010 §2**。

### D-36 证据的存储与授权（2026-11-27）

证据是 owner 级独立资源（`session_id` 可空），走 `/api/v1/evidence`；v1 只开放 `note` / `link` / `test_result`，`storage_key` 系列字段不进契约；「跨项目可见性」不存在（同一 owner，跨项目不是隔离边界）。详见 **ADR-010 §4**。

## 12. 实施结果（2026-11-28）

13 个操作全部落地，契约未做任何事后变更（本文档所列路径、字段、错误码、事务边界即最终实现）。

**落地位置**：主资源 `modules/learning_session`（`dto` / `rules` / `service` / `associations` / `handler`），证据 `modules/evidence`（`dto` / `rules` / `service` / `handler`）；路由 `router/session.rs` 提供 `sessions_router()` + `evidence_router()`；Migration `0006`（5 表）→ `0007`（旧记录迁移）→ `0008`（旧表删除）。

**实现期落定的三处口径**（设计文档未规定、实现必须选）：

| # | 口径 | 理由 |
|---|---|---|
| 1 | 请求侧枚举（`activity_type` / `contribution_type` / `evidence_type` / `created_source`）一律用 `String` 接，由 `rules::parse_*` 转 422 | axum 的 `JsonRejection` 返回纯文本 422，会破坏统一信封（M03 已踩过）；只有让枚举在 DTO 层「不参与派生」，才能保证错误走 `AppError` |
| 2 | `PUT /projects` 与 `PATCH primary_project_id` 变更项目集合时，先校验既有任务分摊不会失去归属，否则 422 | 静默删除用户填过的 `task_sessions` 行属于「悄悄丢数据」；让用户先调整分摊更诚实 |
| 3 | 软删重复删幂等 200；证据重复删 404 | 软删是 `UPDATE … WHERE deleted_at IS NULL`，天然幂等；证据是物理删，删后无法区分「删过」与「从未存在」，只能 404 |

**未做（刻意）**：任务自动完成、审计事件、软删恢复端点、文件类证据——分别归属用户显式动作 / ADR-008 待补 / ADR-010 §3 / ADR-010 §4。
