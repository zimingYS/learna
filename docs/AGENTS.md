# AGENTS.md

本文件是 Learna 项目 Agent 开发硬约束。开始任务前必须阅读。

详细规范位于 `docs/工程规范/`。优先级：

```text
项目负责人明确指令 > 本文件 > docs/工程规范/* > 现有代码风格
```

当任务要求、本文件、详细规范或正式设计文档之间冲突时，必须暂停并向项目负责人报告，不得自行选择性忽略。

---

## 1. 技术栈与项目边界

Learna 是 Monorepo，包含：

- Frontend：Vue 3、TypeScript、Vite、Vue Router、Pinia、Axios
- Backend：Rust、Axum、Tokio、SQLx、Serde、Tracing
- AI Service：Python、FastAPI、Pydantic
- Infrastructure：PostgreSQL、Docker、Docker Compose、Nginx、GitHub Actions

未经项目负责人批准，不得更换核心技术栈、引入新的核心框架或大型依赖、修改许可证、修改公共 API 契约或核心领域模型。

---

## 2. 强制工作流

### 2.1 编码前

必须：

1. 阅读本文件、任务相关设计文档和 `docs/工程规范/` 中相关规范。
2. 检查当前模块目录结构。
3. 阅读同模块至少两个代表性现有源文件；不足两个则检查全部相关文件。
4. 识别现有命名、注释、格式、错误处理、类型定义、测试组织风格。
5. 搜索已有函数、Service、Repository、DTO、类型、组件、Composable、Store、API Client、工具模块和测试。
6. 明确本次修改范围。
7. 禁止未检查现有实现就新建文件或重复实现已有功能。

### 2.2 中大型任务

涉及多个文件、数据库、API 或模块边界时，编码前必须提交实施方案，至少包括：

- 修改目标
- 预计修改和新增文件
- 现有模块复用情况
- 数据库影响
- API 影响
- 模块依赖变化
- 测试方案
- 潜在风险

等待批准后再实施。范围明确、风险低的局部修改可直接执行，但不得扩大范围。

### 2.3 编码中

必须：

- 只修改任务相关内容。
- 优先复用已有实现。
- 遵循同模块现有代码风格，尤其是注释语言、注释格式和注释密度。
- 保持模块职责单一。
- 避免重复代码、无用代码和无关文件修改。
- 为重要业务规则补充测试。
- 同步维护必要文档。
- 不得为了完成当前任务擅自重构整个模块。

### 2.4 编码后

必须：

1. 检查完整 Git Diff。
2. 检查重复实现、无用代码、过长文件/函数、注释准确性和架构一致性。
3. 运行格式检查、静态检查和相关测试。
4. 按 `docs/工程规范/交付报告模板.md` 提供交付报告。
5. 完成后停止，等待下一项任务。

## 3. 代码质量硬规则

- 正确性优先。禁止忽略错误、吞异常、绕过权限、硬编码业务数据、空实现伪装完成、降低测试标准。
- 一致性优先。新增代码必须遵循同模块现有命名、注释、格式、import 顺序、错误处理、类型定义、测试组织和 API 设计方式。
- 复用优先。新增函数、Service、Repository、DTO、类型、组件、Composable、Store、工具前必须搜索已有实现。
- 简单优先。避免不必要设计模式、过度抽象、多层包装、无调用路径的预留模块。
- 禁止死代码、未使用依赖、未使用变量、无意义类型、永远不执行的分支。
- 不得为满足行数机械拆分代码。文件超过 500 行、函数超过 80 行必须说明原因并评估重构。
- 重要业务规则必须有测试；测试必须验证真实行为，不得伪造通过。

---

## 4. 注释与现有风格（重点）

必须维持现有项目代码风格，不得借当前任务顺手统一或重写注释风格。

具体要求：

- 新增或修改注释时，注释语言、格式、位置和密度必须与同文件或相邻文件的主流风格一致。
- 现有模块注释少，不要新增大量解释性注释；现有模块注释详细，按同风格补充必要说明。
- 不得批量把英文注释改为中文、把中文注释改为英文，或重排无关注释。
- 不得为每一行代码、简单赋值、简单 getter 添加无意义注释。
- 注释只解释：为什么这样设计、业务规则、边界条件、非直观原因、特殊约束。
- 涉及重要业务规则时必须添加必要注释，但应简洁说明规则本身，不机械复制设计文档。
- 如果代码必须依靠大量注释才能理解，应优先改善命名、拆分函数或调整结构。
- 项目文档和业务说明默认中文；代码标识符使用英文；代码注释优先延续所在模块现有语言和表达风格。

详细要求见 `docs/工程规范/代码风格与质量规范.md`。

## 5. 架构与安全硬约束

- Rust Backend 是正式业务数据的唯一写入权威。
- Python AI Service 不直接连接业务数据库。
- Vue Frontend 不得绕过 Backend 直接写业务数据。
- Handler 负责 HTTP 请求与响应适配；Service 负责业务流程与规则；Repository 负责数据访问；DTO 负责外部数据结构。
- 禁止 Handler 承担复杂业务逻辑。
- 禁止跨领域模块随意访问其他模块 Repository；模块间优先通过公开 Service 或明确接口协作。
- 禁止循环依赖。
- 所有用户数据必须经过身份认证和资源级授权。
- 不同用户数据必须严格隔离。
- 密钥必须保存在服务端；不得在前端暴露 `LLM_API_KEY`。
- `AI_SERVICE_TOKEN` 与 `LLM_API_KEY` 必须区分。
- 不得提交真实密钥、密码或隐私数据。
- 不得绕过现有权限机制。

## 6. AI Proposal 硬约束

AI 生成的业务变更必须经过：

1. 创建 AI Task。
2. 构建必要上下文。
3. 调用 AI Workflow。
4. 校验输出结构。
5. 执行业务规则校验。
6. 执行权限校验。
7. 生成 Proposal。
8. 根据 Proposal 审批规则由用户确认。
9. 由 Rust Backend 领域服务应用变更。
10. 保留必要操作记录。

AI 不得直接覆盖或删除历史学习记录。AI Task 和 Proposal 是不同的领域实体，不得合并。AI 服务不可用时，核心学习管理功能仍然必须可用。

---

## 7. 领域不变量摘要

必须遵守 `docs/工程规范/领域模型不变量.md`，尤其注意：

- 学习内容允许重复创建和跨项目共享；不强制 owner + title 唯一。
- 每个项目拥有独立学习计划、学习目标、目标掌握等级、项目上下文掌握状态和复习状态。
- 个人总体掌握度与项目上下文掌握度必须分离。
- 必须区分 LearningSession、ScheduledActivity、LearningTask，三者不可合并。
- LearningSession 拥有一个主要项目，可关联多个其他项目、多个知识点或技能点，可不关联任务，也可关联多个任务。
- 只有主要项目计入学习时长；关联项目不得重复累计。
- 掌握度采用 L0-L4；系统评价与用户自评共同参与；保留历史，不得静默覆盖。
- 默认按项目独立复习调度；支持显式共享复习结果；共享结果默认作为参考证据；不得静默覆盖目标项目复习状态。
- 错题必须有独立领域模型；题库、练习、错题记录和 AI 生成题目边界清晰。
- 项目删除默认归档；彻底删除需额外确认；项目允许无阶段、多最终目标；阶段可跳过、提前进入或返回；软截止日期允许调整；固定事件不得当普通软截止日期延期。
- 每日学习时间是目标不是强制上限；支持按日期自定义；默认均衡安排；支持复习优先和用户自定义复习日期；超预算时推荐调整方案由用户确认；不得硬编码考试日期或特定学习周期。

修改以上规则必须先提交 ADR 或设计变更说明。

## 8. 数据库、API、测试与变更管理

- 数据库变更必须通过 SQLx Migration。
- 不得修改已经执行的历史 Migration。
- 不得未经批准执行破坏性数据库操作。
- Migration 必须考虑已有数据、用户归属、数据隔离、外键、唯一约束、索引和事务边界。
- 避免冗余字段和 N+1 查询。
- API 必须明确 Method、Endpoint、Request DTO、Response DTO、Error Code、认证、授权、分页、校验和数据归属。
- 修改 API 必须同步更新 OpenAPI 和相关文档。
- 重要业务逻辑必须有测试，覆盖正常路径、异常路径、边界条件、权限边界、用户数据隔离、数据一致性、历史数据保护和适用时的并发事务边界。
- 禁止删除失败测试使 CI 通过、跳过必要校验、使用无意义断言或伪造通过结果。
- 不得擅自修改无关模块、顺手大规模重构、删除未确认功能、改变公共接口、改变领域模型、引入无关依赖或扩大任务范围。
- 遵循 `docs/工程规范/变更管理.md` 和 `docs/工程规范/测试与验证.md`。

## 9. 禁止操作

未经项目负责人批准，禁止：

1. 大规模重构整个项目。
2. 删除现有业务功能。
3. 修改核心领域模型。
4. 更换核心技术栈。
5. 修改项目许可证。
6. 修改 Git 分支保护策略。
7. 执行破坏性数据库操作。
8. 直接修改已执行的历史 Migration。
9. 将 Python AI Service 改为直接写业务数据库。
10. 移除 AI Proposal 审批机制。
11. 绕过身份认证和权限校验。
12. 提交真实密钥和用户隐私数据。
13. 通过删除测试或忽略错误使检查通过。
14. 在没有检查现有代码的情况下重复实现功能。
15. 为满足文件长度要求机械拆分代码。
16. 未经批准引入大型第三方依赖。
17. 将当前任务扩展为无关功能开发。

---

## 10. 停止条件

出现以下情况必须暂停相关修改并向项目负责人报告：

- 设计文档之间存在冲突。
- 现有实现与正式领域模型存在重大冲突。
- 需要修改核心数据库结构。
- 需要改变公共 API 契约。
- 需要引入新的核心依赖。
- 无法确认业务规则。
- 无法确定用户数据归属。
- 需要执行不可逆操作。
- 发现可能影响其他模块的重大架构问题。
- 任务要求与本文件存在冲突。

不得通过猜测关键业务规则继续开发。

## 11. 交付报告

每项任务完成后必须按 `docs/工程规范/交付报告模板.md` 提供完整交付报告，包括任务摘要、修改文件、实现细节、代码质量、数据库/API 变化、测试结果、已知问题、设计偏差和下一步建议。

完成后停止，等待下一项任务。
