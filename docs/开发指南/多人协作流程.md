# 多人协作流程

本文说明 Learna 团队协作的标准流程与约定。分支、Commit、PR、审查的细则见 `CONTRIBUTING.md`，本文是流程导览，冲突时以 `CONTRIBUTING.md` 为准。

## 1. 角色

| 角色 | 职责 |
|---|---|
| 项目负责人 | 任务派发、方案批准、最终合并、停止条件裁决 |
| 贡献者 | 认领任务、开发、自查、提交 PR、响应审查 |
| AI Agent | 按 `docs/AGENTS.md` 与 `docs/工程规范/AI任务执行模板.md` 执行任务并交付报告 |

模块负责人见 `.github/CODEOWNERS`（frontend / backend / ai-service / deploy / docs / scripts），敏感路径改动自动请求对应负责人审查。

## 2. 标准流程

```text
Issue 讨论 → 建分支 → 开发 + 自查 → 提 PR → CI 全绿 → 审查通过（1 人审批）→ Squash Merge → 删分支
```

1. **Issue 讨论**：新功能或非平凡修复先开 Issue 对齐目标与范围，避免返工。
2. **建分支**：从最新 `main` 拉出，命名遵守 CONTRIBUTING §1.2（`feat/` `fix/` `docs/` `chore/` `refactor/`）。
3. **开发 + 自查**：只做该分支的事；提交前跑对应栈的质量命令（见 `docs/开发指南/本地开发环境.md` 第 5 节）。
4. **提 PR**：使用 PR 模板，如实填写接口变更、数据库变更、测试结果三节；PR 标题符合 Conventional Commits（Semantic PR 检查会拦截）。
5. **CI 全绿**：三栈检查 + `CI` 汇总闸门全部通过。
6. **审查通过**：至少 1 名非作者审批；触及 CODEOWNERS 敏感路径需对应负责人批准。
7. **合并**：一律 **Squash Merge** 进 `main`，保持线性历史；合并后删除功能分支。
8. **收尾**：涉及 API / 数据库 / 架构的变更，确认文档已同步；遗留问题转 Issue，不夹带进下一个 PR。

## 3. 分支模型

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 稳定主分支，受保护，线性历史 | 永久 |
| `feat/*` | 新功能 | 合并后删除 |
| `fix/*` | 缺陷修复 | 合并后删除 |
| `refactor/*` | 重构（不改变外部行为） | 合并后删除 |
| `docs/*` | 文档变更 | 合并后删除 |
| `chore/*` | 工程维护、配置、依赖 | 合并后删除 |

- 一个分支只做一件事，保持 PR 小而可审。
- 禁止向 `main` 直接推送，禁止 force push 共享分支。
- 历史只进不退：回退用 `revert`，不改写已合并历史。

## 4. 提交与 PR 约定

- **Commit**：Conventional Commits（`feat: / fix: / docs: / chore: / refactor: ...`），格式与示例见 CONTRIBUTING §2；一次提交只做一件事。
- **PR 标题**：同样符合 Conventional Commits（Semantic PR 检查强制）。
- **PR 模板三节必须如实填写**（`.github/pull_request_template.md`）：
  - 接口变更：Method / Endpoint / 契约是否同步；
  - 数据库变更：Migration 名称 / 数据迁移 / 回滚方案；
  - 测试结果：真实执行的命令与结果，禁止未跑先报。
- **合并方式**：Squash Merge，单 PR 单提交进主干。

## 5. CI 闸门清单

| 检查 | 内容 |
|---|---|
| backend | `cargo fmt --check`、`cargo clippy -D warnings`、`cargo test` |
| ai-service | `ruff format --check`、`ruff check`、`pytest` |
| frontend | `vue-tsc` 构建（类型静态闸门） |
| **CI（汇总）** | 上述全部绿才通过；分支保护的必需检查就是它 |

本地预跑命令见 `docs/开发指南/本地开发环境.md` 第 5 节，CI 红了先本地复现再推修。

## 6. 代码审查

- **1 人审批**：合并前必须至少 1 名非 PR 作者的批准；PR 作者不能自批。
- **敏感路径**：触及 `CODEOWNERS` 指定路径必须对应负责人批准。
- 审查关注点（完整清单见 CONTRIBUTING §4.2）：正确性、范围控制、测试覆盖、文档同步、领域不变量、安全。
- 发现问题修复后再合并；审查意见与规范冲突时暂停并上报项目负责人。

## 7. 特殊情况处理

| 场景 | 处理 |
|---|---|
| 合并冲突 | 在功能分支上 `git rebase main` 或 `git merge main` 解决后重推，禁止直接改 main |
| 紧急修复 | 仍走 `fix/*` → PR → 审查，可加急但不省流程 |
| 合并后发现问题 | 新开 `fix/*` 用 `revert` 回退或修复，禁止改写历史 |
| CI 误判 / 基础设施问题 | 在 PR 说明情况并 @负责人，不得跳过检查合并（`--no-verify` 禁用） |

## 8. AI 参与协作

- AI Agent 任务的输入与交付按 `docs/工程规范/AI任务执行模板.md` 执行。
- AI 产出的代码与人工代码走**完全相同**的分支、PR、审查、CI 流程，不享受豁免。
- 任务要求与 `docs/AGENTS.md` 冲突时，AI 必须暂停报告，不得自行取舍。
